## Context

這是一個全新、獨立的 Python 專案（與本 repo 內既有的 `PXB2E.*` .NET 專案無關），目標是在使用者本機（可能是 Win7）啟動一個網站，透過瀏覽器操作。核心限制：
- 必須相容 Win7 可執行的 Python 版本。
- 不依賴雲端服務、資料庫或需要編譯的第三方套件。
- 樹狀結構與筆記內容都直接對應本機檔案系統（見 `markdown-file-storage` spec）。

詳見 proposal.md 的 Why / What Changes。

## Goals / Non-Goals

**Goals:**
- 提供一個可在 Win7 上以雙擊或簡單指令啟動的本機 Web 應用。
- 前後端皆使用最少、風險最低的相依套件，降低在舊系統上安裝失敗的機率。
- 樹狀索引與大綱編輯器的資料一律即時反映為本機檔案系統上的實體檔案/資料夾。

**Non-Goals:**
- 不實作全文搜尋（proposal 已明確排除）。
- 不支援多使用者同時編輯或任何形式的權限/帳號系統（單機單使用者情境）。
- 不實作留言/註解功能（使用者已確認不需要）：需要獨立的留言資料模型、歸屬（誰留言）、顯示與後端儲存，超出單機單人筆記工具的範圍。
- 不將編輯器的摺疊/展開等純 UI 狀態持久化為檔案的一部分。

## Decisions

### Python 版本：3.8
Python 3.8 是官方最後一個提供 Windows 7 安裝版的版本（Python 3.9 起官方安裝程式不再支援 Win7）。所有相依套件版本須確認其對應的 wheel 有支援到可在 Win7 上執行的 CPython 3.8。

### 後端框架：Flask（搭配 Werkzeug 內建開發伺服器）
選擇 Flask 而非自行以 `wsgiref`/`http.server`手刻路由，理由：
- Flask 與其相依套件（Werkzeug、Jinja2、MarkupSafe、click、itsdangerous）皆為純 Python 實作，不需要編譯 C 擴充套件，Win7 上的相容風險與零相依方案相近。
- 相較於自行手刻 WSGI 路由，Flask 可大幅減少樣板程式碼與出錯機會，且文件與生態成熟，利於長期維護。
- 相較 Bottle（單檔零相依），Flask 生態更成熟；由於两者在 Win7 上的相依風險相近，優先選擇維護性更好的 Flask。

伺服器僅綁定 `127.0.0.1`（不對外開放網路），因為此工具設計為本機單人使用，不需要對外提供服務。

### 前端：純 Vanilla HTML/CSS/JavaScript，無建置流程
不使用需要 Node.js/npm 建置的前端框架（React/Vue 等），理由：
- 目標環境（Win7）不一定有 Node.js 可用於建置，且執行期也不需要任何前端建置產物之外的東西。
- 樹狀索引與大綱編輯器的互動邏輯規模有限，純 JavaScript 即可勝任，避免引入外部 CDN 相依（本工具需可離線本機執行）。

大綱編輯器（區塊、縮排層級、摺疊狀態、排序）以自訂的最小化 JavaScript 元件實作，不引入第三方富文本編輯器函式庫，以降低相依風險與授權/版本相容疑慮。

### 資料模型：檔案系統即單一事實來源
不另外建立資料庫或中介的 metadata 儲存。樹狀結構節點 = 本機資料夾／`.md` 檔案，讀取樹狀索引時即時掃描筆記根目錄。摺疊/展開狀態純粹是前端執行期的 UI 狀態，不寫回檔案，以維持 `.md` 檔案的純文字可攜性（對應 `markdown-file-storage` 的「Markdown 純文字格式相容性」需求）。

### 大綱區塊 ⇄ Markdown 序列化規則
編輯器內部以區塊樹（block tree，含層級與順序）表示筆記內容；儲存時序列化為標準 Markdown 語法：
- 具有子項目的區塊層級 → 巢狀項目符號清單（依縮排層級對應清單縮排）。
- 標題型態區塊 → `#`～`######` 標題語法。
- 一般文字區塊 → 純段落文字。

載入既有 `.md` 檔案時，以同一套規則的反向解析，將 Markdown 文字還原為區塊樹。此規則只涵蓋標題、清單（含巢狀）、段落三種區塊型態，不支援其餘 Markdown 語法（如表格、程式碼區塊）的專屬區塊化編輯；若檔案含有這類語法，載入時以純文字段落區塊呈現，儲存時原樣保留純文字內容，不做語意轉換。

### 路徑安全性
所有涉及檔案系統的 API（讀取、寫入、建立、重新命名、刪除、搬移）一律：
1. 將請求路徑與設定的筆記根目錄組合後，取其正規化絕對路徑（resolve symlink、`..` 等）。
2. 檢查該絕對路徑是否仍位於筆記根目錄之內，否則直接拒絕並回傳錯誤，不執行任何檔案系統操作。

### 筆記根目錄設定
筆記根目錄透過環境變數（例如 `NOTES_ROOT`）或同層設定檔指定；未設定時預設為執行檔所在目錄下的 `notes/` 資料夾，若該資料夾不存在則於啟動時自動建立。

### UI 視覺風格：類 Outline 的簡潔版面
前端版面與視覺風格參考 Outline 筆記軟體的呈現方式（僅取版面配置與視覺風格，不採用其功能或內容）：
- 左側側欄：可摺疊的樹狀結構，資料夾／筆記節點以簡潔的清單呈現，選中節點有明顯的高亮背景。
- 右側編輯區：頁面頂部為大字級的筆記標題，內文以清爽的無襯線字體、充足留白呈現；區塊化內容（標題、清單、段落）之間有清楚的視覺層級。
- 整體配色簡單、乾淨，避免多餘的裝飾線條或圖示，聚焦於內容本身的可讀性。

此為前端 CSS/版面設計的依據，不影響 API 或資料模型的行為（不新增 spec 需求）。

### 區塊格式選單（Hover Toolbar）
考量單靠輸入 `#` 前綴切換標題層級的方式不易被使用者發現，於每個區塊列滑鼠移入時顯示一個小型「Aa」格式按鈕，點擊展開下拉選單（標題 1／標題 2／標題 3／一般文字），可直接切換該區塊的型態與層級，等效於輸入對應的 Markdown 前綴語法，兩者可互換使用、不衝突。

### 原始 Markdown 原始碼檢視/編輯模式
為支援使用者直接貼上既有 Markdown 內容，或編輯區塊編輯器尚未支援的語法（如表格、程式碼區塊），於編輯區加入「檢視原始碼」切換鈕：
- 切換至原始碼模式：將目前區塊樹序列化為 Markdown 文字，顯示於一個可編輯的 `<textarea>`。
- 切換回區塊模式：將 textarea 內容重新解析為區塊樹並渲染。
- 自動儲存機制在兩種模式下皆生效（原始碼模式下先將 textarea 內容解析為區塊樹，再走既有的儲存流程）。

為避免每次切換都往返後端，解析/序列化邏輯以 JavaScript 複寫一份（`static/js/markdown.js`），邏輯與後端 `noteapp/markdown_blocks.py` 保持一致（相同的標題/清單/段落規則與縮排寬度）。兩份實作各自獨立維運，若未來修改解析規則需同步更新兩處。

### 區塊型態擴充：引用／編號清單／待辦清單
在既有的標題／清單／段落三種區塊型態之外，新增：
- `quote`：對應 Markdown `> text`，不參與縮排巢狀（每行各自成一個獨立的引用區塊）。
- `ordered_item`：對應 Markdown `N. text`，與 `list_item` 共用同一套縮排巢狀機制；序號於序列化時依「同層級中連續的 `ordered_item` 」重新計算，因此使用者調整順序或刪除項目後，編號會自動重新排列，不需手動維護。
- `checklist_item`：對應 Markdown `- [ ] text` / `- [x] text`，新增 `checked` 布林欄位；使用者可直接點擊區塊前的核取方塊切換勾選狀態，勾選後套用刪除線樣式。

這三種型態皆可透過既有的區塊格式選單（Aa）切換，也可比照標題的做法，之後視需要加入輸入時的即時偵測（例如打 `1. ` 或 `- [ ] ` 自動轉換），目前僅支援透過格式選單手動切換。

按 `Enter` 新增區塊時，若目前區塊型態為 `list_item`／`ordered_item`／`checklist_item`，新區塊會延續相同型態（避免每輸入一個編號/待辦項目都要重新選一次格式）；其餘型態（標題、引用）之後預設回到一般清單項目。

### 行內文字格式（Bold／Italic／Strikethrough／Code／Link）
新增選取文字時浮現的懸浮工具列，提供 5 個行內格式操作，對齊常見富文本編輯器（如 Notion）的體驗：
- 粗體／斜體／刪除線：透過瀏覽器原生 `document.execCommand('bold'|'italic'|'strikeThrough')` 實作，具備原生的「切換」語意（已格式化的選取範圍再次點擊會取消格式），相容性與穩定度高於自行實作。
- 行內程式碼：`execCommand` 沒有對應指令，改為手動操作 Selection Range：若選取範圍已在 `<code>` 內則解開，否則以 `range.surroundContents` 包裹一個 `<code>` 元素。
- 連結：跳出既有的 `NotesModal.prompt` 詢問網址，輸入後以 `execCommand('createLink', ...)` 套用；若選取範圍已在連結內，則改為 `execCommand('unlink', ...)` 解除連結。點擊工具列按鈕時，會在 `mousedown` 階段呼叫 `preventDefault()`，避免點擊瞬間造成 contenteditable 失焦、清空選取範圍。

**資料模型與儲存的關鍵設計**：區塊的 `text` 欄位在磁碟／API 層級「一律」是純文字並直接內嵌 Markdown 行內語法（例如 `**粗體** 一般文字`），與既有的區塊層級序列化模型完全相容——**後端完全不需要修改**：`noteapp/markdown_blocks.py` 本來就只是把整行文字（含標題/清單前綴後的部分）視為不透明字串照抄，不理解也不需要理解行內語法。所有「HTML（contenteditable 編輯中所見）⇄ 行內 Markdown 文字（儲存格式）」的轉換，都只發生在前端 `static/js/markdown.js` 新增的 `inlineMarkdownToHtml` / `htmlToInlineMarkdown` 兩個函式：
- 渲染區塊供編辑時：`block.text`（純文字，含行內 Markdown 語法）→ `inlineMarkdownToHtml()` → 設為 contenteditable 的 `innerHTML`。
- 使用者編輯或套用行內格式後：讀取 contenteditable 目前的 DOM（`innerHTML`）→ `htmlToInlineMarkdown()` 遞迴走訪節點 → 寫回 `block.text`（純文字）。

`htmlToInlineMarkdown` 對巢狀標籤採遞迴組合（例如 `<b><i>x</i></b>` 會先得到 `*x*` 再包成 `**\*x\***` = `***x***`，恰好符合標準 Markdown 粗斜體語法），`inlineMarkdownToHtml` 則以正規表示式依序處理（先保護行內程式碼片段、再處理連結、粗斜體組合、粗體、斜體、刪除線），只涵蓋這 5 種語法，不支援其餘 Markdown 行內語法（如圖片、跳脫字元的完整規則）。

### Undo / Redo（復原／取消復原）
編輯器內建一個純前端的復原歷史堆疊（不經過後端），純粹針對區塊編輯器（`static/js/editor.js`）的 `blocks` 狀態：
- 每次有意義的變更（輸入文字、Enter/Tab/Backspace/上移下移、切換區塊型態、勾選待辦清單、套用行內格式）都會對目前 `blocks` 的深層快照（JSON 字串）做一次記錄。
- 連續輸入文字時，若與上一次記錄的時間間隔在 600ms 內，直接覆蓋合併為同一個復原步驟（避免每個字都各自成一步，貼近使用者對「復原一步＝復原一個有意義的動作」的預期）；其餘結構性操作（Enter、縮排、刪除、排序、格式切換、行內格式、待辦勾選）一律視為獨立步驟，不與其他操作合併。
- 歷史堆疊上限 100 筆，超過時捨棄最舊的紀錄。
- 歷史紀錄的範圍是「單一筆記」：每次從樹狀索引開啟一篇筆記時，歷史會重設為只包含剛載入的狀態（無法復原到開啟這篇筆記之前）；切換到原始碼模式編輯後切回區塊模式，會將該次原始碼變更視為一個獨立的復原步驟，但不會重設整個歷史。
- 快捷鍵：`Ctrl+Z` 復原、`Ctrl+Shift+Z` 或 `Ctrl+Y` 取消復原，僅在區塊編輯器（`.block-text`）取得焦點時生效；原始碼模式的 `<textarea>` 使用瀏覽器原生的復原機制，兩者互不影響、也不共用歷史。
- 復原/取消復原後會照常觸發自動儲存，讓磁碟上的檔案內容與復原後的畫面狀態一致。

### 鍵盤快捷鍵
除了既有的 `Tab`/`Shift+Tab`（縮排）、`Enter`（新增區塊）、`Backspace`（刪除空區塊）、`Ctrl+↑`/`Ctrl+↓`（排序）之外，新增：
- `Ctrl+Alt+1`／`Ctrl+Alt+2`／`Ctrl+Alt+3`：將目前區塊設為標題 1/2/3。
- `Ctrl+Alt+0`：將目前區塊還原為一般文字（`list_item`）。
- `Ctrl+B`／`Ctrl+I`／`Ctrl+Shift+X`：套用粗體／斜體／刪除線，內部直接呼叫與浮動工具列相同的 `applyInlineCommand`，確保行為一致、不重複實作。

這些快捷鍵的判斷邏輯內嵌在既有的 `handleKeydown`（每個區塊各自綁定）中，不需要額外的全域鍵盤監聽器，天然限定只在區塊編輯器內生效，不會與其他頁面元件（如 Modal 輸入框、原始碼模式的 textarea）的鍵盤行為衝突。

### API 形式
後端提供簡單的 JSON API 供前端呼叫：
- `GET /api/tree`：取得目前樹狀結構
- `POST /api/nodes`：新增節點（筆記或資料夾）
- `PATCH /api/nodes/<path>`：重新命名或搬移節點
- `DELETE /api/nodes/<path>`：刪除節點
- `GET /api/notes/<path>`：讀取筆記內容（回傳區塊樹或原始 Markdown）
- `PUT /api/notes/<path>`：儲存筆記內容

前端頁面（HTML/CSS/JS）由同一個 Flask 應用以靜態檔案方式提供。

### 選取文字調整大小（行內字級）
延續行內格式（粗體/斜體/刪除線/程式碼/連結）的作法：使用者於浮動工具列選擇「小／一般／大／特大」其中之一，僅套用於目前選取的那段文字（而非整個區塊，這點與標題 H1/H2/H3 是「整個區塊變大」不同，用來滿足「選取局部文字調整大小」的需求）。

標準 Markdown 沒有原生的行內字級語法，因此比照既有的行內格式作法，直接以內嵌 HTML `<span style="font-size:Npx">text</span>` 儲存在 `block.text` 裡（同樣是「後端完全不需要修改」——`markdown_blocks.py` 只把整行文字當不透明字串照抄）。`static/js/markdown.js` 的 `inlineMarkdownToHtml`/`htmlToInlineMarkdown` 新增對這個特定 `<span>` 樣式的辨識與還原，且會遞迴處理 span 內部的其餘行內格式（例如字級內還有粗體），與既有的程式碼片段保護機制（先抽出、處理完再放回）採同一套手法。

字級只提供 4 個離散選項（12px/一般/20px/26px），不提供任意像素數值輸入，理由：
- 對齊既有格式選單（標題/引用/清單）的「選單挑選」互動模式，操作一致。
- 避免使用者存出大量不同的隨機字級值，讓筆記的視覺風格失控。

### 區塊間游標導航（ArrowUp / ArrowDown）
每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設不會在按上下鍵時把游標從一個區塊的 `<div>` 移到另一個區塊的 `<div>`（這與單一大文字框的編輯器不同）。因此明確攔截未搭配 Ctrl/Shift/Alt 的 `ArrowUp`/`ArrowDown`：先把目前的樹狀結構依「展開順序」（摺疊的子項目不計入）攤平成一個陣列，找出目前區塊的位置，將游標移至前一個／後一個區塊。

簡化決策：不論區塊內容是否換行（過長文字被瀏覽器自動包行），一律視為「上一個/下一個區塊」而非「上一個/下一個視覺行」，即使區塊內容跨多行也一樣直接跳到相鄰區塊。這對應大多數大綱編輯器（如 Workflowy）的慣例，換取實作簡單、行為可預期，避免另外量測游標在換行文字中的視覺列位置。`Ctrl+↑`/`Ctrl+↓`（調整區塊順序）維持原本行為不變，兩者可並存不衝突。

### Enter 依游標位置切開文字（而非永遠新增空白區塊）
使用者實測回報：在一個有子項目的區塊（如 `123`，子項為 `456`）最前面按 Enter，新的空白區塊出現在 `456` 之後、`789` 之前，而不是緊接在 `123` 下面，覺得不符合預期。這是因為原始實作不論游標在文字哪個位置，一律「在目前區塊後面插入一個新空白區塊」，從不真正依游標位置切開文字；而子項目在畫面上永遠緊接在父區塊自己那一行之後，導致新區塊被子項目擋在後面。

在採取修正前，先研究了 Workflowy、Notion、Logseq、Outline 等大綱/筆記工具與其使用者討論（見下方 Sources），確認業界慣例的 Enter 行為：
- 游標在文字**結尾**：新增一個空白區塊在**後面**，原區塊文字與子項目不變（多數工具的最常見情境）。
- 游標在文字**最前面**：新增一個空白區塊在**前面**，原文字與子項目維持不變、只是位置往後挪一格；游標留在原文字上（Logseq 使用者論壇的功能請求明確描述了這個行為：<https://discuss.logseq.com/t/arrow-movements-left-to-previous-point-and-new-point-when-pressing-enter-at-first-character/120>）。
- 游標在文字**中間**：把游標後面的文字移到新插入（在後面）的區塊，原區塊保留游標前面的文字，兩者都是同一層級的區塊（Logseq issue 對這個情境有明確描述：<https://github.com/logseq/logseq/issues/8945>）。

依此設計 `splitAtCaret(textEl)`：以游標所在的 Range 為界，取得「游標前」與「游標後」兩段 DOM 內容（若目前有選取範圍而非單純游標，先呼叫 `range.deleteContents()` 清空選取範圍再切開，比照一般文字編輯器「輸入會取代選取範圍」的行為）。子項目一律留在**原本的區塊物件**上不移動——這代表若游標剛好在「有子項目的區塊」文字中間切開，兩半都會是同層級的區塊，但子項目仍跟著原區塊（現在文字變成游標前半段），可能造成子項目看起來夾在兩個新切出的區塊之間；這是為了保留最常見情境（游標在結尾/開頭）正確行為所做的取捨，中間切開且該區塊有子項目是相對少見的組合。

### 修正：只有一個子項目時 Backspace 沒反應
使用者回報：一個區塊如果是其父區塊「唯一的子項目」，把內容清空後按 Backspace 完全沒有反應，不會被刪除。

原因：`removeBlock` 原本有一個保護機制——「如果目前區塊所在的清單只剩 1 個項目，就不執行刪除」，目的是避免使用者把整份筆記的最後一個區塊也刪掉，導致畫面上沒有任何區塊可以繼續編輯（沒有游標可停靠的地方）。但這個保護被套用到**任何**清單，包括某個區塊的子項目清單——只要一個父區塊只有一個子項目，這個保護就會誤判成「不能刪」，即使刪掉之後父區塊仍然存在、游標可以正常移回父區塊。

修正：保護只保留給**頂層清單**（`list === blocks`），子項目清單允許刪到剩 0 個（父區塊就變成沒有子項目，這是正常狀態）。刪除後若子項目清單變空，游標移回其父區塊（原本的邏輯是移到前一個同層兄弟節點，清單變空時沒有兄弟節點可移，需另外處理）。

### 樹狀索引排序：資料夾優先於檔案
使用者詢問左側樹狀索引是否支援拖拉調整順序。討論後確認實際需求並非拖拉（拖拉排序需要引入一套「自訂順序」的儲存機制，與「檔案系統即單一事實來源、不額外存 metadata」的既有設計原則衝突，詳見上方設計決策），而是單純希望資料夾一律排在檔案前面。

修正方式：`noteapp/tree.py` 的 `build_tree` 掃描每一層目錄時，將資料夾與 `.md` 檔案分開累積成兩個清單，各自依名稱排序後，回傳「資料夾清單 + 檔案清單」，取代原本「不分型態、單純依檔名字母排序」的做法。前端 `tree.js` 沒有另外排序，單純依後端回傳的順序渲染，因此只需修改後端。

### 樹狀索引視覺調整：展開箭頭放大、資料夾筆記數徽章
- 展開/摺疊箭頭字級從 11px 放大 1.5 倍至 16.5px（連同容器寬度從 12px 調整為 18px，避免放大後被裁切）。
- 資料夾節點右側新增一個筆記數徽章：遞迴計算該資料夾（含所有子資料夾）底下的筆記總數，count 為 0 時不顯示徽章。此計算完全在前端 `tree.js` 進行（`countNotes(node)` 走訪 `node.children`），因為 `GET /api/tree` 回傳的樹本身已含完整的巢狀子節點資料，不需要後端額外計算或新增欄位。

### 樹狀索引拖曳搬移
使用 HTML5 原生拖放 API（`draggable`、`dragstart`/`dragover`/`drop` 事件），不引入額外的拖放函式庫：
- 每個節點（資料夾與筆記皆可）皆可拖曳，`dragstart` 時把該節點的路徑存進 `event.dataTransfer`。
- 只有資料夾節點接受放置（`dragover`/`drop`），放置時計算目標路徑（目標資料夾路徑 + 拖曳節點的檔名），呼叫既有的 `PATCH /api/nodes/<path>`（與右鍵選單「搬移」共用同一個 `performMove` 函式，兩者合併去重）。
- 拖到目前所在的父資料夾（等同原地不動）時，前端直接短路不送出請求，避免後端把它當成「目標已存在」的衝突錯誤。
- 拖曳中的節點套用半透明樣式，拖到有效的資料夾上方時該資料夾列會顯示高亮外框，提供視覺回饋。

新增後端防呆（`noteapp/tree.py` 的 `move_or_rename_node`）：若搬移目標路徑是來源資料夾自己的子路徑（把資料夾拖進自己的子資料夾），明確拋出 `NodeConflictError` 並給出清楚訊息，取代原本會讓 `shutil.move` 拋出未經處理例外的行為。這個防呆不只保護拖放操作，也同時保護既有的「搬移」文字輸入路徑。

### 拖曳搬回最外層（拖到樹狀索引空白處）
初版拖放只支援「拖到某個資料夾上」，沒有對應「拖到空白處＝搬回根目錄」的放置區，這是右鍵選單「搬移」（手動輸入路徑）原本就能做到、拖放做不到的落差之一。修正：在 `NotesTree.init()` 對整個樹狀容器（`#tree-root`）額外註冊 `dragover`/`drop`，接住所有「沒有落在特定資料夾列上」的放置，一律視為「搬回筆記根目錄」；同時讓資料夾列自己的 `dragover`/`drop` 呼叫 `event.stopPropagation()`，避免事件往上冒泡到容器層，導致同一次放置被兩層邏輯各處理一次。

**與「搬移」選單的比較（結論：拖放無法完全取代手動搬移）**：補上這個缺口後，拖放已能覆蓋「搬到某資料夾」「搬回根目錄」兩種最常見情境，但仍有兩項手動輸入路徑才能做到、拖放做不到的能力，因此兩者並存，不移除既有的「搬移」選單：
- **搬移時順便改名**：拖放固定保留原檔名（只換路徑），手動輸入路徑可以在同一步驟內把檔名也改掉（例如搬到 `archive/2024/新名字.md`）。
- **不需滑鼠也能操作**：HTML5 原生拖放需要滑鼠手勢，觸控裝置或鍵盤操作使用者無法拖放，仍需仰賴選單輸入路徑完成搬移。

### 複製原始碼按鈕
編輯區右上角新增「複製原始碼」按鈕，與「檢視原始碼」並排，不需先切換到原始碼模式即可一鍵複製整篇筆記目前的 Markdown 原始碼到剪貼簿。內容來源依目前檢視模式決定：區塊模式下呼叫 `NotesEditor.getMarkdownSource()`（從目前的區塊樹序列化），原始碼模式下直接讀取 `<textarea>` 目前的即時內容（可能包含尚未切回區塊模式、尚未存檔的編輯），確保複製到的一定是「畫面上看到的」內容。

複製優先使用 `navigator.clipboard.writeText`（需安全情境，`http://127.0.0.1` 被視為安全來源，可正常使用）；若瀏覽器不支援 Clipboard API（考量 Win7 上可能安裝較舊的瀏覽器），退回建立暫時的 `<textarea>` + `document.execCommand('copy')` 的傳統作法。複製成功後按鈕文字短暫變成「已複製！」，1.5 秒後恢復。

### 樹狀節點操作選單：移除右鍵，改為 hover 顯示「⋮」按鈕 + 浮動選單
原本樹狀節點的重新命名／搬移／刪除是透過右鍵（`contextmenu`）叫出一個置中的 Modal 選單。使用者參考聊天室列表常見的互動模式（滑鼠移到項目上時，右側浮現一個「⋮」按鈕，點擊後貼著該項目彈出一個小的浮動選單），要求改成同樣的模式，且明確表示右鍵這個入口不需要保留。

調整內容：
- 移除 `tree-node-row` 的 `contextmenu` 監聽；右鍵一個節點現在會顯示瀏覽器原生的右鍵選單（不再被攔截）。
- 每個節點列右側新增一個「⋮」按鈕，預設透明（`opacity: 0`），滑鼠移到該列上才顯示，與既有的區塊格式選單、字級選單使用同一種「hover 才顯示的觸發按鈕」設計語言保持一致。
- 點擊「⋮」會在該按鈕正下方彈出一個小的浮動選單（不是螢幕置中的 Modal），內容仍是重新命名／搬移／刪除三項，各自附一個小圖示；選單的顯示/關閉邏輯（同時只能開一個、點擊外部關閉）與區塊格式選單共用相同的實作模式，分別在 `tree.js` 與 `editor.js` 各自維護一份（兩者是不同模組，暫不合併抽象，避免過度提前設計）。
- 圖示為手繪的極簡線條 SVG（`stroke="currentColor"`，無填色），不引入外部圖示庫或 CDN 字型——符合本專案「不依賴外部資源」的既有原則，也避免任何圖示授權疑慮。
- `NotesModal.menu()`（原本用來顯示「重新命名／搬移／刪除」置中選單的通用函式）已無其他呼叫者，隨之移除，避免死程式碼。

新增「⋮」按鈕後，資料夾節點右側同時存在「筆記數徽章」與「⋮」按鈕兩個元素，原本各自佔用自己的版面空間，滑鼠移到列上時兩者會並排擠在一起。修正：把兩者包進同一個固定 22×22px 大小的容器（`.tree-node-trailing`），內部皆以 `position: absolute; top: 0; right: 0;` 錨定在同一個右上角座標，兩者互斥顯示（預設顯示筆記數，`.tree-node-row:hover` 時筆記數 `display: none`、「⋮」按鈕 `opacity` 變為 1），視覺上共用同一個插槽、不會同時出現、也不會有版面跳動。

### 修正：拖到樹狀索引下方空白處實際上沒有反應（游標顯示禁止圖示）
使用者實測回報：把節點拖到左側樹狀索引下方視覺上看起來空白的區域，游標顯示禁止（no-drop）圖示，放開後什麼事也沒發生——雖然先前已針對「拖曳搬回最外層」功能驗證過，但先前的驗證方式是直接對 `#tree-root` 這個 DOM 元素本身派發合成事件，沒有測試「使用者實際看到的空白區域，是否真的屬於 `#tree-root` 的可視範圍」。

實際排查發現：`#tree-root` 本身沒有任何高度相關的 CSS，只會撐到樹狀節點內容本身的高度，並不會延伸填滿 `#sidebar` 剩餘的垂直空間。畫面上看起來的「空白處」其實是 `#sidebar`（`#tree-root` 的父層）自己的背景，`#tree-root` 的 `dragover`/`drop` 監聽器根本接不到那個區域的事件——瀏覽器對「沒有註冊 drop 監聽、且沒有呼叫 `preventDefault()`」的區域，預設就是顯示禁止圖示、drop 不會觸發任何行為，恰好對應使用者描述的現象。

修正：讓 `#sidebar` 改為 `display: flex; flex-direction: column;`，並讓 `#tree-root` 設為 `flex: 1`，使其確實撐滿 `#sidebar` 扣除頂部 `#sidebar-header` 之後的剩餘空間（`#sidebar-header` 另外補上 `flex-shrink: 0` 避免筆記很多、内容擠壓時被壓縮）。修正後以 `document.elementFromPoint()` 在畫面下方視覺空白處取樣，確認該座標確實回傳 `#tree-root`（或其內部），並用該座標為基準派發 `dragover`/`drop` 合成事件（而非直接對 DOM 參照派發），驗證搬回最外層確實成功——這種「以視覺座標定位再派發事件」的驗證方式比先前「直接對元素參照派發」更貼近真實使用者操作，之後測試拖放相關功能應優先採用此方式。

### Backspace 於區塊文字最前面時併入上一個區塊
先前 `Backspace` 只處理「區塊文字已清空」這一種情況（`removeBlock`）；游標在非空文字最前面按 `Backspace` 時，因為每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設行為在該元素起始位置無事可刪，實際上什麼也不會發生，不符合一般大綱編輯器（Workflowy/Notion/Logseq）「併入上一個區塊」的直覺。

新增 `isCaretAtStart(textEl)`：以 `Range` 量測游標所在位置到區塊起點之間是否有任何文字內容，取代單純比對 `range.startOffset === 0`（避免游標落在巢狀行內格式標籤內時誤判）。命中後呼叫 `mergeIntoPreviousBlock(block, textEl)`：取得依展開順序排列的上一個可視區塊（`adjacentVisibleBlockId(..., -1)`），將目前區塊的 Markdown 文字接在該區塊文字之後、移除目前區塊（原有子項目升級補位，作法與 `removeBlock` 一致），並將編輯焦點移至合併後文字中「原上一個區塊文字結尾」的交接處。若已是依展開順序排列的第一個區塊（找不到上一個可視區塊），則不做任何事，避免拋錯。

游標落點的計算：因為區塊內文字可能包含巢狀行內格式標籤（`<b>`、`<code>` 等），無法直接用單一文字節點的 offset 定位，因此另外實作 `focusBlockAtTextOffset(id, offset)`，以 `TreeWalker` 走訪目標區塊內所有文字節點、依純文字字數（不含標籤）累加找到對應的節點與位移，再設定 `Range`／`Selection`。已透過隔離測試伺服器以真實鍵盤事件（而非直接呼叫內部函式）驗證：合併結果、`Ctrl+Z` 復原、以及「已是第一個區塊」時的 no-op 均符合預期。

### 修正：在已清空的清單項目上不斷按 Enter 會無限新增空 bullet
使用者實測回報：對著一個內容已清空的清單項目（一般清單／編號清單／待辦清單）持續按 `Enter`，畫面會不斷往下新增空的清單項目，並附上與參考編輯器（Notion／Outline 等區塊編輯器）的對照截圖——那些工具在文字結尾按下 Enter 會先延續清單型態新增一個空項目（與本專案現有行為一致），但若使用者在那個仍是空的項目上「再按一次」Enter，工具會把該項目轉成不帶標記的一般段落並跳出清單，而不是繼續往下疊加空的清單項目。

原因：`splitAtCaret` 對「整個區塊文字本來就是空的」這種情況，`atStart` 與 `atEnd` 會同時為 `true`，原本的判斷式 `if (split.atStart && !split.atEnd)` 因此不成立、一律落到 `insertSiblingAfter(block, '')`，對清單型態區塊（`CONTINUABLE_TYPES` 內的型態）而言會延續同型態，等於每按一次 Enter 就多一個空 bullet，沒有終止條件。

修正：在 Enter 的處理最前面加入一個攔截分支——若目前區塊文字已清空（`textEl.textContent === ''`）且型態屬於 `CONTINUABLE_TYPES`，就直接把該區塊的 `type` 改成 `paragraph`（Python/JS 兩端序列化早已支援、原本用於一般純文字行的型態，畫面上不帶任何標記），焦點留在原區塊，不建立新區塊、也不呼叫 `splitAtCaret`。同時把 `insertSiblingAfter` 在「非延續」情境下新建區塊的預設型態，由原本寫死的 `list_item`（會生成新 bullet）改為 `paragraph`——否則使用者在轉換後的空段落上再按一次 Enter，又會因為這個預設值重新生出一個 bullet，形成「清單→段落→清單→段落…」的另一種無限增生。修正後，一般段落本身仍可無限按 Enter 新增空白段落（這是所有文件編輯器的常見、可接受行為，不會有視覺上的清單符號堆積），符合使用者提供的參考截圖行為。

已透過隔離測試伺服器以真實鍵盤事件驗證：非空清單項目按 Enter 延續清單型態（行為不變）→ 空清單項目再按 Enter 轉為無標記段落、不新增區塊 → 空段落再按 Enter 才新增新的空段落（無標記）。

### 修正：標題／段落區塊看起來像被多插入一個 tab
使用者比對真實筆記檔案（無任何前導空白的 `# 千萬`）與畫面渲染結果，發現標題文字比原始檔案「多縮進一段」，懷疑排版有問題。

排查發現：每一行區塊（`renderBlock`）無論型態，一律固定附加三個欄位在文字前面——調整格式鈕（20px）、摺疊箭頭（16px）、清單標記（16px，只有一般清單／編號清單／待辦清單會在裡面畫東西）。標題、引用、一般段落沒有標記內容，但 `renderMarker` 原本仍會回傳一個文字為空的 `<span class="block-bullet">`，CSS 對 `.block-bullet` 設有固定 `width:16px`，所以這個空白欄位照樣占用版面，讓沒有標記的區塊文字也被往右推了一段（約 22px，含欄位間距），視覺上就像多了一個 tab，即便原始 Markdown 完全沒有前導空白。

修正（先採取影響範圍較小的做法）：`renderMarker` 對非 `list_item`／`ordered_item` 型態直接回傳 `null`，`renderBlock` 只在 `renderMarker` 有回傳值時才把它加進 `row`，不再為空欄位保留寬度。調整格式鈕與摺疊箭頭這兩個所有型態共用的欄位維持原狀不動（不同型態之間的縮排差異只縮小到「少了清單標記欄位」的 22px，尚未做到與一般 Markdown 檢視器完全貼齊最左邊——那需要把調整格式鈕與摺疊箭頭改成絕對定位懸浮在文字外側，且子項目縮排目前只有 22px／層、不足以容納這兩顆按鈕的浮動欄位，屬於較大範圍的改動，先不做）。已用使用者的真實筆記複本＋隔離測試伺服器驗證：標題文字左邊界從 412px 減少為 390px，剛好少了原本清單標記欄位的 22px。
## Risks / Trade-offs

- [Python 3.8 已停止官方安全更新] → 僅作為本機離線工具使用，不對外部網路開放服務，降低此風險的實際影響；於文件中註明此限制。
- [第三方套件版本可能於後續釋出中放棄 Win7/舊版 wheel 支援] → 將相依套件數量降到最低（僅 Flask 及其核心相依），並於專案文件中明確釘選（pin）已驗證可在 Win7 上運作的版本號。
- [自訂大綱 ⇄ Markdown 序列化規則覆蓋語法有限] → 明確定義並文件化支援的區塊型態（標題/清單/段落），非支援語法以純文字段落保留，避免使用者資料遺失。
- [路徑安全檢查若實作不慎可能被跳脫] → 統一透過單一共用的路徑正規化與範圍檢查函式處理所有檔案系統 API，不允許個別端點自行組合路徑。
- [中文檔名/內容在 Win7 舊版檔案系統下的編碼疑慮] → 一律以 Python 3 的 Unicode 路徑 API 與 UTF-8 讀寫檔案內容，不依賴系統 ANSI 預設編碼。
- [樹狀拖曳搬移使用 HTML5 原生拖放 API，觸控裝置（無滑鼠）不支援拖放手勢] → 右鍵選單的「搬移」（手動輸入目標路徑）維持保留作為替代操作方式，觸控裝置使用者仍可完成搬移。
- [前端（JS）與後端（Python）各自維護一份 Markdown 解析/序列化邏輯，可能因修改不同步而產生行為落差] → 兩者的規則刻意保持極簡（僅標題/清單/段落三種型態），並在測試中涵蓋相同案例；未來若擴充語法支援，需同時更新 `noteapp/markdown_blocks.py` 與 `static/js/markdown.js`。
- [行內字級以內嵌 HTML `<span>` 存檔，不是標準 Markdown 語法] → 大多數 Markdown 檢視器都支援內嵌 HTML 直接渲染，相容性風險低；但若使用者拿去不支援內嵌 HTML 的檢視器開啟，會直接看到原始的 `<span>` 標籤文字，已於 README 的已知限制中註明。

## Migration Plan

全新專案，無既有系統或資料需要遷移。初次部署步驟：
1. 在目標機器安裝 Python 3.8（Win7 相容版本）。
2. 安裝已釘選版本的相依套件（`pip install -r requirements.txt`）。
3. 設定筆記根目錄（環境變數或設定檔），或使用預設的 `notes/` 資料夾。
4. 啟動本機伺服器，於瀏覽器開啟 `http://127.0.0.1:<port>` 使用。

無需回滾（rollback）機制：本工具不修改既有系統，移除即完成復原。

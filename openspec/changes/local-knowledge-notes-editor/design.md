## Context

這是一個全新、獨立的 Python 專案（與本 repo 內既有的 `PXB2E.*` .NET 專案無關），目標是在使用者本機（可能是 Win7）啟動一個網站，透過瀏覽器操作。核心限制：
- 必須相容 Win7 可執行的 Python 版本。
- 不依賴雲端服務、資料庫或需要編譯的第三方套件。
- 樹狀結構與筆記內容都直接對應本機檔案系統（見 `markdown-file-storage` spec）。

詳見 proposal.md 的 Why / What Changes。

## Goals / Non-Goals

**Goals:**
- 提供一個可在 Win7 上以雙擊或簡單指令啟動的本機 Web 應用。
- 前後端皆使用最少、風險最低的相依套件，降低在舊系統上安裝失敗的機率。
- 樹狀索引與大綱編輯器的資料一律即時反映為本機檔案系統上的實體檔案/資料夾。

**Non-Goals:**
- 不實作全文搜尋（proposal 已明確排除）。
- 不支援多使用者同時編輯或任何形式的權限/帳號系統（單機單使用者情境）。
- 不實作留言/註解功能（使用者已確認不需要）：需要獨立的留言資料模型、歸屬（誰留言）、顯示與後端儲存，超出單機單人筆記工具的範圍。
- 不將編輯器的摺疊/展開等純 UI 狀態持久化為檔案的一部分。

## Decisions

### Python 版本：3.8
Python 3.8 是官方最後一個提供 Windows 7 安裝版的版本（Python 3.9 起官方安裝程式不再支援 Win7）。所有相依套件版本須確認其對應的 wheel 有支援到可在 Win7 上執行的 CPython 3.8。

### 後端框架：Flask（搭配 Werkzeug 內建開發伺服器）
選擇 Flask 而非自行以 `wsgiref`/`http.server`手刻路由，理由：
- Flask 與其相依套件（Werkzeug、Jinja2、MarkupSafe、click、itsdangerous）皆為純 Python 實作，不需要編譯 C 擴充套件，Win7 上的相容風險與零相依方案相近。
- 相較於自行手刻 WSGI 路由，Flask 可大幅減少樣板程式碼與出錯機會，且文件與生態成熟，利於長期維護。
- 相較 Bottle（單檔零相依），Flask 生態更成熟；由於两者在 Win7 上的相依風險相近，優先選擇維護性更好的 Flask。

伺服器僅綁定 `127.0.0.1`（不對外開放網路），因為此工具設計為本機單人使用，不需要對外提供服務。

### 前端：純 Vanilla HTML/CSS/JavaScript，無建置流程
不使用需要 Node.js/npm 建置的前端框架（React/Vue 等），理由：
- 目標環境（Win7）不一定有 Node.js 可用於建置，且執行期也不需要任何前端建置產物之外的東西。
- 樹狀索引與大綱編輯器的互動邏輯規模有限，純 JavaScript 即可勝任，避免引入外部 CDN 相依（本工具需可離線本機執行）。

大綱編輯器（區塊、縮排層級、摺疊狀態、排序）以自訂的最小化 JavaScript 元件實作，不引入第三方富文本編輯器函式庫，以降低相依風險與授權/版本相容疑慮。

### 資料模型：檔案系統即單一事實來源
不另外建立資料庫或中介的 metadata 儲存。樹狀結構節點 = 本機資料夾／`.md` 檔案，讀取樹狀索引時即時掃描筆記根目錄。摺疊/展開狀態純粹是前端執行期的 UI 狀態，不寫回檔案，以維持 `.md` 檔案的純文字可攜性（對應 `markdown-file-storage` 的「Markdown 純文字格式相容性」需求）。

### 大綱區塊 ⇄ Markdown 序列化規則
編輯器內部以區塊樹（block tree，含層級與順序）表示筆記內容；儲存時序列化為標準 Markdown 語法：
- 具有子項目的區塊層級 → 巢狀項目符號清單（依縮排層級對應清單縮排）。
- 標題型態區塊 → `#`～`######` 標題語法。
- 一般文字區塊 → 純段落文字。

載入既有 `.md` 檔案時，以同一套規則的反向解析，將 Markdown 文字還原為區塊樹。此規則只涵蓋標題、清單（含巢狀）、段落三種區塊型態，不支援其餘 Markdown 語法（如表格、程式碼區塊）的專屬區塊化編輯；若檔案含有這類語法，載入時以純文字段落區塊呈現，儲存時原樣保留純文字內容，不做語意轉換。

### 路徑安全性
所有涉及檔案系統的 API（讀取、寫入、建立、重新命名、刪除、搬移）一律：
1. 將請求路徑與設定的筆記根目錄組合後，取其正規化絕對路徑（resolve symlink、`..` 等）。
2. 檢查該絕對路徑是否仍位於筆記根目錄之內，否則直接拒絕並回傳錯誤，不執行任何檔案系統操作。

### 筆記根目錄設定
筆記根目錄透過環境變數（例如 `NOTES_ROOT`）或同層設定檔指定；未設定時預設為執行檔所在目錄下的 `notes/` 資料夾，若該資料夾不存在則於啟動時自動建立。

### UI 視覺風格：類 Outline 的簡潔版面
前端版面與視覺風格參考 Outline 筆記軟體的呈現方式（僅取版面配置與視覺風格，不採用其功能或內容）：
- 左側側欄：可摺疊的樹狀結構，資料夾／筆記節點以簡潔的清單呈現，選中節點有明顯的高亮背景。
- 右側編輯區：頁面頂部為大字級的筆記標題，內文以清爽的無襯線字體、充足留白呈現；區塊化內容（標題、清單、段落）之間有清楚的視覺層級。
- 整體配色簡單、乾淨，避免多餘的裝飾線條或圖示，聚焦於內容本身的可讀性。

此為前端 CSS/版面設計的依據，不影響 API 或資料模型的行為（不新增 spec 需求）。

### 區塊格式選單（Hover Toolbar）
考量單靠輸入 `#` 前綴切換標題層級的方式不易被使用者發現，於每個區塊列滑鼠移入時顯示一個小型「Aa」格式按鈕，點擊展開下拉選單（標題 1／標題 2／標題 3／一般文字），可直接切換該區塊的型態與層級，等效於輸入對應的 Markdown 前綴語法，兩者可互換使用、不衝突。

### 原始 Markdown 原始碼檢視/編輯模式
為支援使用者直接貼上既有 Markdown 內容，或編輯區塊編輯器尚未支援的語法（如表格、程式碼區塊），於編輯區加入「檢視原始碼」切換鈕：
- 切換至原始碼模式：將目前區塊樹序列化為 Markdown 文字，顯示於一個可編輯的 `<textarea>`。
- 切換回區塊模式：將 textarea 內容重新解析為區塊樹並渲染。
- 自動儲存機制在兩種模式下皆生效（原始碼模式下先將 textarea 內容解析為區塊樹，再走既有的儲存流程）。

為避免每次切換都往返後端，解析/序列化邏輯以 JavaScript 複寫一份（`static/js/markdown.js`），邏輯與後端 `noteapp/markdown_blocks.py` 保持一致（相同的標題/清單/段落規則與縮排寬度）。兩份實作各自獨立維運，若未來修改解析規則需同步更新兩處。

### 區塊型態擴充：引用／編號清單／待辦清單
在既有的標題／清單／段落三種區塊型態之外，新增：
- `quote`：對應 Markdown `> text`，不參與縮排巢狀（每行各自成一個獨立的引用區塊）。
- `ordered_item`：對應 Markdown `N. text`，與 `list_item` 共用同一套縮排巢狀機制；序號於序列化時依「同層級中連續的 `ordered_item` 」重新計算，因此使用者調整順序或刪除項目後，編號會自動重新排列，不需手動維護。
- `checklist_item`：對應 Markdown `- [ ] text` / `- [x] text`，新增 `checked` 布林欄位；使用者可直接點擊區塊前的核取方塊切換勾選狀態，勾選後套用刪除線樣式。

這三種型態皆可透過既有的區塊格式選單（Aa）切換，也可比照標題的做法，之後視需要加入輸入時的即時偵測（例如打 `1. ` 或 `- [ ] ` 自動轉換），目前僅支援透過格式選單手動切換。

按 `Enter` 新增區塊時，若目前區塊型態為 `list_item`／`ordered_item`／`checklist_item`，新區塊會延續相同型態（避免每輸入一個編號/待辦項目都要重新選一次格式）；其餘型態（標題、引用）之後預設回到一般清單項目。

### 行內文字格式（Bold／Italic／Strikethrough／Code／Link）
新增選取文字時浮現的懸浮工具列，提供 5 個行內格式操作，對齊常見富文本編輯器（如 Notion）的體驗：
- 粗體／斜體／刪除線：透過瀏覽器原生 `document.execCommand('bold'|'italic'|'strikeThrough')` 實作，具備原生的「切換」語意（已格式化的選取範圍再次點擊會取消格式），相容性與穩定度高於自行實作。
- 行內程式碼：`execCommand` 沒有對應指令，改為手動操作 Selection Range：若選取範圍已在 `<code>` 內則解開，否則以 `range.surroundContents` 包裹一個 `<code>` 元素。
- 連結：跳出既有的 `NotesModal.prompt` 詢問網址，輸入後以 `execCommand('createLink', ...)` 套用；若選取範圍已在連結內，則改為 `execCommand('unlink', ...)` 解除連結。點擊工具列按鈕時，會在 `mousedown` 階段呼叫 `preventDefault()`，避免點擊瞬間造成 contenteditable 失焦、清空選取範圍。

**資料模型與儲存的關鍵設計**：區塊的 `text` 欄位在磁碟／API 層級「一律」是純文字並直接內嵌 Markdown 行內語法（例如 `**粗體** 一般文字`），與既有的區塊層級序列化模型完全相容——**後端完全不需要修改**：`noteapp/markdown_blocks.py` 本來就只是把整行文字（含標題/清單前綴後的部分）視為不透明字串照抄，不理解也不需要理解行內語法。所有「HTML（contenteditable 編輯中所見）⇄ 行內 Markdown 文字（儲存格式）」的轉換，都只發生在前端 `static/js/markdown.js` 新增的 `inlineMarkdownToHtml` / `htmlToInlineMarkdown` 兩個函式：
- 渲染區塊供編辑時：`block.text`（純文字，含行內 Markdown 語法）→ `inlineMarkdownToHtml()` → 設為 contenteditable 的 `innerHTML`。
- 使用者編輯或套用行內格式後：讀取 contenteditable 目前的 DOM（`innerHTML`）→ `htmlToInlineMarkdown()` 遞迴走訪節點 → 寫回 `block.text`（純文字）。

`htmlToInlineMarkdown` 對巢狀標籤採遞迴組合（例如 `<b><i>x</i></b>` 會先得到 `*x*` 再包成 `**\*x\***` = `***x***`，恰好符合標準 Markdown 粗斜體語法），`inlineMarkdownToHtml` 則以正規表示式依序處理（先保護行內程式碼片段、再處理連結、粗斜體組合、粗體、斜體、刪除線），只涵蓋這 5 種語法，不支援其餘 Markdown 行內語法（如圖片、跳脫字元的完整規則）。

### Undo / Redo（復原／取消復原）
編輯器內建一個純前端的復原歷史堆疊（不經過後端），純粹針對區塊編輯器（`static/js/editor.js`）的 `blocks` 狀態：
- 每次有意義的變更（輸入文字、Enter/Tab/Backspace/上移下移、切換區塊型態、勾選待辦清單、套用行內格式）都會對目前 `blocks` 的深層快照（JSON 字串）做一次記錄。
- 連續輸入文字時，若與上一次記錄的時間間隔在 600ms 內，直接覆蓋合併為同一個復原步驟（避免每個字都各自成一步，貼近使用者對「復原一步＝復原一個有意義的動作」的預期）；其餘結構性操作（Enter、縮排、刪除、排序、格式切換、行內格式、待辦勾選）一律視為獨立步驟，不與其他操作合併。
- 歷史堆疊上限 100 筆，超過時捨棄最舊的紀錄。
- 歷史紀錄的範圍是「單一筆記」：每次從樹狀索引開啟一篇筆記時，歷史會重設為只包含剛載入的狀態（無法復原到開啟這篇筆記之前）；切換到原始碼模式編輯後切回區塊模式，會將該次原始碼變更視為一個獨立的復原步驟，但不會重設整個歷史。
- 快捷鍵：`Ctrl+Z` 復原、`Ctrl+Shift+Z` 或 `Ctrl+Y` 取消復原，僅在區塊編輯器（`.block-text`）取得焦點時生效；原始碼模式的 `<textarea>` 使用瀏覽器原生的復原機制，兩者互不影響、也不共用歷史。
- 復原/取消復原後會照常觸發自動儲存，讓磁碟上的檔案內容與復原後的畫面狀態一致。

### 鍵盤快捷鍵
除了既有的 `Tab`/`Shift+Tab`（縮排）、`Enter`（新增區塊）、`Backspace`（刪除空區塊）、`Ctrl+↑`/`Ctrl+↓`（排序）之外，新增：
- `Ctrl+Alt+1`／`Ctrl+Alt+2`／`Ctrl+Alt+3`：將目前區塊設為標題 1/2/3。
- `Ctrl+Alt+0`：將目前區塊還原為一般文字（`list_item`）。
- `Ctrl+B`／`Ctrl+I`／`Ctrl+Shift+X`：套用粗體／斜體／刪除線，內部直接呼叫與浮動工具列相同的 `applyInlineCommand`，確保行為一致、不重複實作。

這些快捷鍵的判斷邏輯內嵌在既有的 `handleKeydown`（每個區塊各自綁定）中，不需要額外的全域鍵盤監聽器，天然限定只在區塊編輯器內生效，不會與其他頁面元件（如 Modal 輸入框、原始碼模式的 textarea）的鍵盤行為衝突。

### API 形式
後端提供簡單的 JSON API 供前端呼叫：
- `GET /api/tree`：取得目前樹狀結構
- `POST /api/nodes`：新增節點（筆記或資料夾）
- `PATCH /api/nodes/<path>`：重新命名或搬移節點
- `DELETE /api/nodes/<path>`：刪除節點
- `GET /api/notes/<path>`：讀取筆記內容（回傳區塊樹或原始 Markdown）
- `PUT /api/notes/<path>`：儲存筆記內容

前端頁面（HTML/CSS/JS）由同一個 Flask 應用以靜態檔案方式提供。

### 選取文字調整大小（行內字級）
延續行內格式（粗體/斜體/刪除線/程式碼/連結）的作法：使用者於浮動工具列選擇「小／一般／大／特大」其中之一，僅套用於目前選取的那段文字（而非整個區塊，這點與標題 H1/H2/H3 是「整個區塊變大」不同，用來滿足「選取局部文字調整大小」的需求）。

標準 Markdown 沒有原生的行內字級語法，因此比照既有的行內格式作法，直接以內嵌 HTML `<span style="font-size:Npx">text</span>` 儲存在 `block.text` 裡（同樣是「後端完全不需要修改」——`markdown_blocks.py` 只把整行文字當不透明字串照抄）。`static/js/markdown.js` 的 `inlineMarkdownToHtml`/`htmlToInlineMarkdown` 新增對這個特定 `<span>` 樣式的辨識與還原，且會遞迴處理 span 內部的其餘行內格式（例如字級內還有粗體），與既有的程式碼片段保護機制（先抽出、處理完再放回）採同一套手法。

字級只提供 4 個離散選項（12px/一般/20px/26px），不提供任意像素數值輸入，理由：
- 對齊既有格式選單（標題/引用/清單）的「選單挑選」互動模式，操作一致。
- 避免使用者存出大量不同的隨機字級值，讓筆記的視覺風格失控。

### 區塊間游標導航（ArrowUp / ArrowDown）
每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設不會在按上下鍵時把游標從一個區塊的 `<div>` 移到另一個區塊的 `<div>`（這與單一大文字框的編輯器不同）。因此明確攔截未搭配 Ctrl/Shift/Alt 的 `ArrowUp`/`ArrowDown`：先把目前的樹狀結構依「展開順序」（摺疊的子項目不計入）攤平成一個陣列，找出目前區塊的位置，將游標移至前一個／後一個區塊。

簡化決策：不論區塊內容是否換行（過長文字被瀏覽器自動包行），一律視為「上一個/下一個區塊」而非「上一個/下一個視覺行」，即使區塊內容跨多行也一樣直接跳到相鄰區塊。這對應大多數大綱編輯器（如 Workflowy）的慣例，換取實作簡單、行為可預期，避免另外量測游標在換行文字中的視覺列位置。`Ctrl+↑`/`Ctrl+↓`（調整區塊順序）維持原本行為不變，兩者可並存不衝突。

### Enter 依游標位置切開文字（而非永遠新增空白區塊）
使用者實測回報：在一個有子項目的區塊（如 `123`，子項為 `456`）最前面按 Enter，新的空白區塊出現在 `456` 之後、`789` 之前，而不是緊接在 `123` 下面，覺得不符合預期。這是因為原始實作不論游標在文字哪個位置，一律「在目前區塊後面插入一個新空白區塊」，從不真正依游標位置切開文字；而子項目在畫面上永遠緊接在父區塊自己那一行之後，導致新區塊被子項目擋在後面。

在採取修正前，先研究了 Workflowy、Notion、Logseq、Outline 等大綱/筆記工具與其使用者討論（見下方 Sources），確認業界慣例的 Enter 行為：
- 游標在文字**結尾**：新增一個空白區塊在**後面**，原區塊文字與子項目不變（多數工具的最常見情境）。
- 游標在文字**最前面**：新增一個空白區塊在**前面**，原文字與子項目維持不變、只是位置往後挪一格；游標留在原文字上（Logseq 使用者論壇的功能請求明確描述了這個行為：<https://discuss.logseq.com/t/arrow-movements-left-to-previous-point-and-new-point-when-pressing-enter-at-first-character/120>）。
- 游標在文字**中間**：把游標後面的文字移到新插入（在後面）的區塊，原區塊保留游標前面的文字，兩者都是同一層級的區塊（Logseq issue 對這個情境有明確描述：<https://github.com/logseq/logseq/issues/8945>）。

依此設計 `splitAtCaret(textEl)`：以游標所在的 Range 為界，取得「游標前」與「游標後」兩段 DOM 內容（若目前有選取範圍而非單純游標，先呼叫 `range.deleteContents()` 清空選取範圍再切開，比照一般文字編輯器「輸入會取代選取範圍」的行為）。子項目一律留在**原本的區塊物件**上不移動——這代表若游標剛好在「有子項目的區塊」文字中間切開，兩半都會是同層級的區塊，但子項目仍跟著原區塊（現在文字變成游標前半段），可能造成子項目看起來夾在兩個新切出的區塊之間；這是為了保留最常見情境（游標在結尾/開頭）正確行為所做的取捨，中間切開且該區塊有子項目是相對少見的組合。

### 修正：只有一個子項目時 Backspace 沒反應
使用者回報：一個區塊如果是其父區塊「唯一的子項目」，把內容清空後按 Backspace 完全沒有反應，不會被刪除。

原因：`removeBlock` 原本有一個保護機制——「如果目前區塊所在的清單只剩 1 個項目，就不執行刪除」，目的是避免使用者把整份筆記的最後一個區塊也刪掉，導致畫面上沒有任何區塊可以繼續編輯（沒有游標可停靠的地方）。但這個保護被套用到**任何**清單，包括某個區塊的子項目清單——只要一個父區塊只有一個子項目，這個保護就會誤判成「不能刪」，即使刪掉之後父區塊仍然存在、游標可以正常移回父區塊。

修正：保護只保留給**頂層清單**（`list === blocks`），子項目清單允許刪到剩 0 個（父區塊就變成沒有子項目，這是正常狀態）。刪除後若子項目清單變空，游標移回其父區塊（原本的邏輯是移到前一個同層兄弟節點，清單變空時沒有兄弟節點可移，需另外處理）。

### 樹狀索引排序：資料夾優先於檔案
使用者詢問左側樹狀索引是否支援拖拉調整順序。討論後確認實際需求並非拖拉（拖拉排序需要引入一套「自訂順序」的儲存機制，與「檔案系統即單一事實來源、不額外存 metadata」的既有設計原則衝突，詳見上方設計決策），而是單純希望資料夾一律排在檔案前面。

修正方式：`noteapp/tree.py` 的 `build_tree` 掃描每一層目錄時，將資料夾與 `.md` 檔案分開累積成兩個清單，各自依名稱排序後，回傳「資料夾清單 + 檔案清單」，取代原本「不分型態、單純依檔名字母排序」的做法。前端 `tree.js` 沒有另外排序，單純依後端回傳的順序渲染，因此只需修改後端。

### 樹狀索引視覺調整：展開箭頭放大、資料夾筆記數徽章
- 展開/摺疊箭頭字級從 11px 放大 1.5 倍至 16.5px（連同容器寬度從 12px 調整為 18px，避免放大後被裁切）。
- 資料夾節點右側新增一個筆記數徽章：遞迴計算該資料夾（含所有子資料夾）底下的筆記總數，count 為 0 時不顯示徽章。此計算完全在前端 `tree.js` 進行（`countNotes(node)` 走訪 `node.children`），因為 `GET /api/tree` 回傳的樹本身已含完整的巢狀子節點資料，不需要後端額外計算或新增欄位。

### 樹狀索引拖曳搬移
使用 HTML5 原生拖放 API（`draggable`、`dragstart`/`dragover`/`drop` 事件），不引入額外的拖放函式庫：
- 每個節點（資料夾與筆記皆可）皆可拖曳，`dragstart` 時把該節點的路徑存進 `event.dataTransfer`。
- 只有資料夾節點接受放置（`dragover`/`drop`），放置時計算目標路徑（目標資料夾路徑 + 拖曳節點的檔名），呼叫既有的 `PATCH /api/nodes/<path>`（與右鍵選單「搬移」共用同一個 `performMove` 函式，兩者合併去重）。
- 拖到目前所在的父資料夾（等同原地不動）時，前端直接短路不送出請求，避免後端把它當成「目標已存在」的衝突錯誤。
- 拖曳中的節點套用半透明樣式，拖到有效的資料夾上方時該資料夾列會顯示高亮外框，提供視覺回饋。

新增後端防呆（`noteapp/tree.py` 的 `move_or_rename_node`）：若搬移目標路徑是來源資料夾自己的子路徑（把資料夾拖進自己的子資料夾），明確拋出 `NodeConflictError` 並給出清楚訊息，取代原本會讓 `shutil.move` 拋出未經處理例外的行為。這個防呆不只保護拖放操作，也同時保護既有的「搬移」文字輸入路徑。

### 拖曳搬回最外層（拖到樹狀索引空白處）
初版拖放只支援「拖到某個資料夾上」，沒有對應「拖到空白處＝搬回根目錄」的放置區，這是右鍵選單「搬移」（手動輸入路徑）原本就能做到、拖放做不到的落差之一。修正：在 `NotesTree.init()` 對整個樹狀容器（`#tree-root`）額外註冊 `dragover`/`drop`，接住所有「沒有落在特定資料夾列上」的放置，一律視為「搬回筆記根目錄」；同時讓資料夾列自己的 `dragover`/`drop` 呼叫 `event.stopPropagation()`，避免事件往上冒泡到容器層，導致同一次放置被兩層邏輯各處理一次。

**與「搬移」選單的比較（結論：拖放無法完全取代手動搬移）**：補上這個缺口後，拖放已能覆蓋「搬到某資料夾」「搬回根目錄」兩種最常見情境，但仍有兩項手動輸入路徑才能做到、拖放做不到的能力，因此兩者並存，不移除既有的「搬移」選單：
- **搬移時順便改名**：拖放固定保留原檔名（只換路徑），手動輸入路徑可以在同一步驟內把檔名也改掉（例如搬到 `archive/2024/新名字.md`）。
- **不需滑鼠也能操作**：HTML5 原生拖放需要滑鼠手勢，觸控裝置或鍵盤操作使用者無法拖放，仍需仰賴選單輸入路徑完成搬移。

### 複製原始碼按鈕
編輯區右上角新增「複製原始碼」按鈕，與「檢視原始碼」並排，不需先切換到原始碼模式即可一鍵複製整篇筆記目前的 Markdown 原始碼到剪貼簿。內容來源依目前檢視模式決定：區塊模式下呼叫 `NotesEditor.getMarkdownSource()`（從目前的區塊樹序列化），原始碼模式下直接讀取 `<textarea>` 目前的即時內容（可能包含尚未切回區塊模式、尚未存檔的編輯），確保複製到的一定是「畫面上看到的」內容。

複製優先使用 `navigator.clipboard.writeText`（需安全情境，`http://127.0.0.1` 被視為安全來源，可正常使用）；若瀏覽器不支援 Clipboard API（考量 Win7 上可能安裝較舊的瀏覽器），退回建立暫時的 `<textarea>` + `document.execCommand('copy')` 的傳統作法。複製成功後按鈕文字短暫變成「已複製！」，1.5 秒後恢復。

### 樹狀節點操作選單：移除右鍵，改為 hover 顯示「⋮」按鈕 + 浮動選單
原本樹狀節點的重新命名／搬移／刪除是透過右鍵（`contextmenu`）叫出一個置中的 Modal 選單。使用者參考聊天室列表常見的互動模式（滑鼠移到項目上時，右側浮現一個「⋮」按鈕，點擊後貼著該項目彈出一個小的浮動選單），要求改成同樣的模式，且明確表示右鍵這個入口不需要保留。

調整內容：
- 移除 `tree-node-row` 的 `contextmenu` 監聽；右鍵一個節點現在會顯示瀏覽器原生的右鍵選單（不再被攔截）。
- 每個節點列右側新增一個「⋮」按鈕，預設透明（`opacity: 0`），滑鼠移到該列上才顯示，與既有的區塊格式選單、字級選單使用同一種「hover 才顯示的觸發按鈕」設計語言保持一致。
- 點擊「⋮」會在該按鈕正下方彈出一個小的浮動選單（不是螢幕置中的 Modal），內容仍是重新命名／搬移／刪除三項，各自附一個小圖示；選單的顯示/關閉邏輯（同時只能開一個、點擊外部關閉）與區塊格式選單共用相同的實作模式，分別在 `tree.js` 與 `editor.js` 各自維護一份（兩者是不同模組，暫不合併抽象，避免過度提前設計）。
- 圖示為手繪的極簡線條 SVG（`stroke="currentColor"`，無填色），不引入外部圖示庫或 CDN 字型——符合本專案「不依賴外部資源」的既有原則，也避免任何圖示授權疑慮。
- `NotesModal.menu()`（原本用來顯示「重新命名／搬移／刪除」置中選單的通用函式）已無其他呼叫者，隨之移除，避免死程式碼。

新增「⋮」按鈕後，資料夾節點右側同時存在「筆記數徽章」與「⋮」按鈕兩個元素，原本各自佔用自己的版面空間，滑鼠移到列上時兩者會並排擠在一起。修正：把兩者包進同一個固定 22×22px 大小的容器（`.tree-node-trailing`），內部皆以 `position: absolute; top: 0; right: 0;` 錨定在同一個右上角座標，兩者互斥顯示（預設顯示筆記數，`.tree-node-row:hover` 時筆記數 `display: none`、「⋮」按鈕 `opacity` 變為 1），視覺上共用同一個插槽、不會同時出現、也不會有版面跳動。

### 修正：拖到樹狀索引下方空白處實際上沒有反應（游標顯示禁止圖示）
使用者實測回報：把節點拖到左側樹狀索引下方視覺上看起來空白的區域，游標顯示禁止（no-drop）圖示，放開後什麼事也沒發生——雖然先前已針對「拖曳搬回最外層」功能驗證過，但先前的驗證方式是直接對 `#tree-root` 這個 DOM 元素本身派發合成事件，沒有測試「使用者實際看到的空白區域，是否真的屬於 `#tree-root` 的可視範圍」。

實際排查發現：`#tree-root` 本身沒有任何高度相關的 CSS，只會撐到樹狀節點內容本身的高度，並不會延伸填滿 `#sidebar` 剩餘的垂直空間。畫面上看起來的「空白處」其實是 `#sidebar`（`#tree-root` 的父層）自己的背景，`#tree-root` 的 `dragover`/`drop` 監聽器根本接不到那個區域的事件——瀏覽器對「沒有註冊 drop 監聽、且沒有呼叫 `preventDefault()`」的區域，預設就是顯示禁止圖示、drop 不會觸發任何行為，恰好對應使用者描述的現象。

修正：讓 `#sidebar` 改為 `display: flex; flex-direction: column;`，並讓 `#tree-root` 設為 `flex: 1`，使其確實撐滿 `#sidebar` 扣除頂部 `#sidebar-header` 之後的剩餘空間（`#sidebar-header` 另外補上 `flex-shrink: 0` 避免筆記很多、内容擠壓時被壓縮）。修正後以 `document.elementFromPoint()` 在畫面下方視覺空白處取樣，確認該座標確實回傳 `#tree-root`（或其內部），並用該座標為基準派發 `dragover`/`drop` 合成事件（而非直接對 DOM 參照派發），驗證搬回最外層確實成功——這種「以視覺座標定位再派發事件」的驗證方式比先前「直接對元素參照派發」更貼近真實使用者操作，之後測試拖放相關功能應優先採用此方式。

### Backspace 於區塊文字最前面時併入上一個區塊
先前 `Backspace` 只處理「區塊文字已清空」這一種情況（`removeBlock`）；游標在非空文字最前面按 `Backspace` 時，因為每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設行為在該元素起始位置無事可刪，實際上什麼也不會發生，不符合一般大綱編輯器（Workflowy/Notion/Logseq）「併入上一個區塊」的直覺。

新增 `isCaretAtStart(textEl)`：以 `Range` 量測游標所在位置到區塊起點之間是否有任何文字內容，取代單純比對 `range.startOffset === 0`（避免游標落在巢狀行內格式標籤內時誤判）。命中後呼叫 `mergeIntoPreviousBlock(block, textEl)`：取得依展開順序排列的上一個可視區塊（`adjacentVisibleBlockId(..., -1)`），將目前區塊的 Markdown 文字接在該區塊文字之後、移除目前區塊（原有子項目升級補位，作法與 `removeBlock` 一致），並將編輯焦點移至合併後文字中「原上一個區塊文字結尾」的交接處。若已是依展開順序排列的第一個區塊（找不到上一個可視區塊），則不做任何事，避免拋錯。

游標落點的計算：因為區塊內文字可能包含巢狀行內格式標籤（`<b>`、`<code>` 等），無法直接用單一文字節點的 offset 定位，因此另外實作 `focusBlockAtTextOffset(id, offset)`，以 `TreeWalker` 走訪目標區塊內所有文字節點、依純文字字數（不含標籤）累加找到對應的節點與位移，再設定 `Range`／`Selection`。已透過隔離測試伺服器以真實鍵盤事件（而非直接呼叫內部函式）驗證：合併結果、`Ctrl+Z` 復原、以及「已是第一個區塊」時的 no-op 均符合預期。

### 修正：在已清空的清單項目上不斷按 Enter 會無限新增空 bullet
使用者實測回報：對著一個內容已清空的清單項目（一般清單／編號清單／待辦清單）持續按 `Enter`，畫面會不斷往下新增空的清單項目，並附上與參考編輯器（Notion／Outline 等區塊編輯器）的對照截圖——那些工具在文字結尾按下 Enter 會先延續清單型態新增一個空項目（與本專案現有行為一致），但若使用者在那個仍是空的項目上「再按一次」Enter，工具會把該項目轉成不帶標記的一般段落並跳出清單，而不是繼續往下疊加空的清單項目。

原因：`splitAtCaret` 對「整個區塊文字本來就是空的」這種情況，`atStart` 與 `atEnd` 會同時為 `true`，原本的判斷式 `if (split.atStart && !split.atEnd)` 因此不成立、一律落到 `insertSiblingAfter(block, '')`，對清單型態區塊（`CONTINUABLE_TYPES` 內的型態）而言會延續同型態，等於每按一次 Enter 就多一個空 bullet，沒有終止條件。

修正：在 Enter 的處理最前面加入一個攔截分支——若目前區塊文字已清空（`textEl.textContent === ''`）且型態屬於 `CONTINUABLE_TYPES`，就直接把該區塊的 `type` 改成 `paragraph`（Python/JS 兩端序列化早已支援、原本用於一般純文字行的型態，畫面上不帶任何標記），焦點留在原區塊，不建立新區塊、也不呼叫 `splitAtCaret`。同時把 `insertSiblingAfter` 在「非延續」情境下新建區塊的預設型態，由原本寫死的 `list_item`（會生成新 bullet）改為 `paragraph`——否則使用者在轉換後的空段落上再按一次 Enter，又會因為這個預設值重新生出一個 bullet，形成「清單→段落→清單→段落…」的另一種無限增生。修正後，一般段落本身仍可無限按 Enter 新增空白段落（這是所有文件編輯器的常見、可接受行為，不會有視覺上的清單符號堆積），符合使用者提供的參考截圖行為。

已透過隔離測試伺服器以真實鍵盤事件驗證：非空清單項目按 Enter 延續清單型態（行為不變）→ 空清單項目再按 Enter 轉為無標記段落、不新增區塊 → 空段落再按 Enter 才新增新的空段落（無標記）。

### 修正：標題／段落區塊看起來像被多插入一個 tab
使用者比對真實筆記檔案（無任何前導空白的 `# 千萬`）與畫面渲染結果，發現標題文字比原始檔案「多縮進一段」，懷疑排版有問題。

排查發現：每一行區塊（`renderBlock`）無論型態，一律固定附加三個欄位在文字前面——調整格式鈕（20px）、摺疊箭頭（16px）、清單標記（16px，只有一般清單／編號清單／待辦清單會在裡面畫東西）。標題、引用、一般段落沒有標記內容，但 `renderMarker` 原本仍會回傳一個文字為空的 `<span class="block-bullet">`，CSS 對 `.block-bullet` 設有固定 `width:16px`，所以這個空白欄位照樣占用版面，讓沒有標記的區塊文字也被往右推了一段（約 22px，含欄位間距），視覺上就像多了一個 tab，即便原始 Markdown 完全沒有前導空白。

修正（先採取影響範圍較小的做法）：`renderMarker` 對非 `list_item`／`ordered_item` 型態直接回傳 `null`，`renderBlock` 只在 `renderMarker` 有回傳值時才把它加進 `row`，不再為空欄位保留寬度。調整格式鈕與摺疊箭頭這兩個所有型態共用的欄位維持原狀不動（不同型態之間的縮排差異只縮小到「少了清單標記欄位」的 22px，尚未做到與一般 Markdown 檢視器完全貼齊最左邊——那需要把調整格式鈕與摺疊箭頭改成絕對定位懸浮在文字外側，且子項目縮排目前只有 22px／層、不足以容納這兩顆按鈕的浮動欄位，屬於較大範圍的改動，先不做）。已用使用者的真實筆記複本＋隔離測試伺服器驗證：標題文字左邊界從 412px 減少為 390px，剛好少了原本清單標記欄位的 22px。

### 重新整理頁面後恢復先前開啟的筆記
使用者回報：點選一篇筆記後按重新整理，畫面會回到「請從左側選擇一篇筆記」的首頁狀態，之前選的筆記就不見了，希望重新整理後能留在原本開啟的筆記。

原因：`app.js` 原本完全沒有把「目前開啟哪篇筆記」這件事反映到瀏覽器可以感知的任何狀態（URL、localStorage 皆無），純粹是記憶體裡的 `currentNode` 變數，重新整理必然清空。

作法：選用 URL hash（例如 `#資料夾A/筆記.md`，每個路徑片段以 `encodeURIComponent` 編碼）而非 query string 或 localStorage，原因是 hash 完全不會送到伺服器，Flask 現有唯一的 `/` 路由不需要任何改動就能在帶著任意 hash 重新整理時正常回應同一份頁面；相較 localStorage，hash 這種作法還能讓網址本身就可以分享/加入書籤直達某篇筆記（雖然目前是純本機工具，暫時用不到分享，但不需要額外成本就能保留這個可能性）。

實作：`selectNode` 選取筆記時呼叫 `setHashForPath`，用 `history.replaceState` 而非直接指派 `location.hash`——避免每切換一篇筆記就多一筆瀏覽器歷史紀錄（否則使用者按「上一頁」會在筆記之間跳來跳去，而不是離開這個網站，不符合預期）。頁面載入時 `reloadTree()` 取得完整樹狀資料後，呼叫新增的 `restoreFromHash(tree)`：解析目前 URL hash 還原成路徑、以新增的 `findNodeByPath` 遞迴搜尋樹狀資料找出對應節點，找到且型態為筆記時，呼叫 `NotesTree.revealPath()`（新增，展開該路徑上所有祖先資料夾，否則筆記雖然選中了，但因為所在資料夾是收合的，畫面上會看不到左側樹狀索引反白在哪）再呼叫 `selectNode` 正常走一般選取流程。找不到對應節點（筆記已被刪除、或網址被手動改壞）時單純不做任何事，維持預設的空白畫面，不拋錯。另外在 `onNodeMoved`／`onNodeDeleted` 也同步更新／清除 hash，確保網址列不會殘留一個指向舊路徑或已刪除筆記的 hash。

已透過隔離測試伺服器＋真實瀏覽器導航（`navigate` 到含 hash 的網址，非單純 JS 內部呼叫）驗證：選取筆記後 hash 正確更新 → 重新整理／重新導覽到同網址後，資料夾自動展開、筆記正確重新載入且區塊內容一致 → 網址沒有 hash 時維持原本空白畫面 → hash 指向不存在的筆記時安全 no-op、不出錯。

### 表格區塊（第一階段：先求正確顯示，可編輯既有儲存格，暫不做新增/刪除列欄與插入表格）
使用者需求：筆記需要能編輯 Markdown 表格。目前完全沒有表格支援——`parse_markdown_to_blocks`／`markdown.js` 的 `parseMarkdownToBlocks` 對 `| ... |` 這種行沒有任何特殊判斷，逐行當成一般段落處理，畫面上顯示的是原始 pipe 語法文字而非真正的表格。

先研究了 Obsidian（本機 `.md` 檔案編輯器中最相近的參照對象）、Notion、以及本專案命名由來的 Outline（底層為 ProseMirror + `prosemirror-tables`）三者的表格 UX，三者收斂到同一套慣例：插入時選列數欄數 → 點擊儲存格直接編輯純文字（不支援儲存格內再放清單/標題等區塊）→ `Tab`/`Shift+Tab`、`Enter`/`↑`/`↓` 在儲存格間移動 → hover 列/欄邊界出現「+」快速新增、也可刪除整列/整欄。因為要把這整套（插入表格的列數/欄數選擇器、儲存格間鍵盤導覽、hover 新增/刪除列欄按鈕）一次做完範圍很大，與使用者討論後拆成兩階段：**第一階段只做「正確顯示既有表格＋可編輯既有儲存格文字」**，鍵盤導覽與新增/刪除列欄、插入新表格的選單留到下一階段。

資料模型：`Block`（Python）新增 `rows`（二維陣列，每列是儲存格文字字串陣列）與 `align`（每欄對齊設定：`'left'`/`'center'`/`'right'`/`None`，來自分隔列的 `:---`/`---:`/`:---:`）欄位；JS 端的 block 物件比照新增同名欄位。兩邊 `Block`/plain object 其餘型態不使用這兩個欄位時保持空陣列，不影響既有行為。

Parser（Python `parse_markdown_to_blocks` 與 JS `parseMarkdownToBlocks`）都從原本单純的逐行 `for`／`forEach` 迴圈，改成可以「向前多看一行」的索引式迴圈：只有當目前行符合 `| ... |` 格式、且**下一行**是合法的分隔列（每個儲存格都是 `:?-+:?` 的形式）時，才開始收集一個表格區塊，持續吃進後續同樣是 `| ... |` 格式的行，直到遇到空行或不符合表格格式的行為止；否則（沒有合法分隔列）該行仍照舊被當成一般段落，避免把使用者原本就想打的、剛好含有 `|` 字元的一般文字誤判成表格。

Serializer（Python `blocks_to_markdown` 與 JS `blocksToMarkdown`）新增表格分支：依 `align` 重新產生分隔列（沒有對齊設定的欄輸出 `---`），並把每一列的儲存格數補齊到該表格最長的那一列（不足的欄位補空字串），確保輸出永遠是欄數一致的合法 GFM 表格，即使儲存格被個別編輯到參差不齊也不會產生語法錯誤的表格。

編輯器渲染（`editor.js`）：新增 `renderTableBlock`，對 `type === 'table'` 的區塊整個改渲染成一個 `<table>`（表頭列用 `<th>`，其餘用 `<td>`），略過一般區塊共用的調整格式鈕／摺疊箭頭／清單標記（表格沒有子項目、也還沒有把自己納入格式選單的可轉換型態），每個儲存格都是獨立的 `contenteditable`，`input` 事件直接更新 `block.rows[r][c]` 並呼叫 `commitChange(false)`（不觸發整棵樹重新 render，跟一般文字區塊的 `handleInput` 行為一致，避免每打一個字就整個重繪、把游標位置弄丟）。儲存格文字比照一般區塊使用 `inlineMarkdownToHtml`/`htmlToInlineMarkdown` 顯示與讀回，所以粗體/斜體等行內格式在儲存格裡一樣能正確顯示與編輯。

因為表格區塊沒有走一般區塊共用的 `.block-text`/keydown 處理路徑，第一階段這些既有功能對錶格區塊是安全的無作用（no-op），不會出錯，但也還沒有支援：
- `ArrowUp`/`ArrowDown` 從相鄰區塊移動到表格：`focusBlock` 找不到表格內的 `.block-text`（表格用的是 `<td>`/`<th>`，不是 `.block-text`），會安全地什麼都不做，游標不會移進表格，也不會壞掉。
- `Backspace` 合併上一個區塊：`mergeIntoPreviousBlock` 特別加了守衛，若「上一個可視區塊」是表格，直接視為找不到上一個區塊（不合併）——否則原本合併邏輯會把目前區塊的文字寫進表格區塊的 `.text` 欄位，但表格渲染完全不使用 `.text`，會造成使用者的文字被無聲吞掉、找不到跑去哪了。
- 表格整個區塊本身目前沒有鍵盤或滑鼠刪除方式；要移除一個表格，暫時只能切到「檢視原始碼」手動刪掉對應的 Markdown 文字。

「插入新表格」在第一階段沒有專門的按鈕/選單，但因為 parser 已經認得表格語法、且原始碼模式與區塊模式雙向切換本來就會重新解析/序列化，使用者可以切到「檢視原始碼」直接貼上或手動輸入一個 Markdown 表格，切回區塊模式就會正確渲染成真正的表格——已用隔離測試伺服器實測這個路徑可行。

已用使用者提供的真實表格內容驗證：Python 端 `parse_markdown_to_blocks`/`blocks_to_markdown` 往返（round-trip）測試（新增於 `tests/test_markdown_blocks.py`，含基本解析、三種對齊標記、表格結束於空行或非表格行、沒有分隔列時退回一般段落、往返穩定性、序列化時補齊參差列數）全數通過，既有 30 個測試也維持全過（共 36 個）；並用隔離測試伺服器＋真實瀏覽器操作驗證：表格正確渲染成 `<table>`（含右/左/置中對齊、粗體儲存格）、點擊編輯儲存格文字後背景自動儲存回檔案內容正確、切到原始碼模式看到的 pipe 語法正確、在原始碼模式貼上一個全新表格切回區塊模式後正確渲染。

### 修正：標題／段落與清單項目的文字沒有對齊、窄表格右側留白
使用者用一份混合標題、清單、表格的真實內容實測後回報兩個現象：（1）標題跟旁邊清單項目的文字看起來沒對齊，「縮排不正常」；（2）內容較短的表格（如「年度支出」那個兩欄表）右側有一塊明顯的空白，跟其他內容的右邊界對不齊。

排查（1）的原因：這是先前「修正標題像多一個 tab」那次改動故意先擱置、當時就講明的取捨——當時只讓標題/表格/引用/段落不再保留清單標記（`.block-bullet`）那 22px 的欄位，但調整格式鈕（20px）與摺疊箭頭（16px）這兩個所有型態共用的欄位並沒有動，所以標題文字落在「欄位寬度 48px」的位置，清單項目文字則落在「48px + 22px 標記欄位 = 70px」的位置——兩者從「一起被推到 70px、彼此對齊」變成「一個在 48px、一個在 70px，彼此不對齊」，改完後反而更顯眼。

這次採用先前提過、當時評估為風險較高而暫緩的「方案 2」：把調整格式鈕與摺疊箭頭從 flex 版面裡的「保留欄位」改成 `position: absolute`（`.block-row` 加上 `position: relative` 作為定位基準），使其懸浮在文字欄位外側、不再佔用任何版面空間；清單標記（`.block-bullet`/`.block-checkbox`）維持原本在 flex 流程中的正常欄位。效果是：所有型態的文字現在統一從區塊自身最左邊（`left: 0`，即 row 本身的框線位置）開始，只有清單型態會因為前面多一個標記欄位而多縮進 22px——這正是一般 Markdown 檢視器的慣例（標題與段落貼齊最左邊，清單的縮排只來自標記本身），而不是先前「大家一起被往右推」的樣子。

先前評估「方案2」時，曾擔心巢狀子項目縮排只有 22px／層，不夠放調整格式鈕+摺疊箭頭合計約 48px 寬的浮動欄位，可能在深層巢狀時互相蓋到。這次改用 `position: absolute` 之後重新驗算：因為每一列的浮動控制項是相對於**該列自己**的框線定位（`left: -48px`／`-22px`），而不是相對於編輯區最外層的固定欄位，所以深度 d 的列，其浮動控制項的絕對水平位置會落在 `d × 22 - 48` px——隨著深度增加，這個值只會往「更靠右、更安全」的方向移動（不會变得更負、更容易被裁切），且不同深度的列本來就分別畫在不同的垂直位置，彼此之間本來就不會有水平方向的視覺重疊。因此不需要放寬 22px 的縮排步階，直接套用到所有深度都是安全的；先前判斷「巢狀時有風險」是評估過程中對「浮動位置是否隨深度固定」想岔了，這次搭配隔離測試伺服器對含巢狀子項目的內容實測，確認每一層的縮排、標記欄位、浮動控制項位置都符合預期。

排查（2）的原因：`.block-table` 沒有設定 `width`，`<table>` 預設依內容自動撐開寬度，內容較短的表格自然比旁邊的標題/段落窄，形成視覺上的落差。這其實是 GitHub／VSCode／Obsidian 等多數 Markdown 檢視器的共同慣例（表格預設不會被強制拉滿版面），嚴格來說不算錯，但使用者希望視覺上跟其他內容對齊，所以直接幫 `.block-table` 加上 `width: 100%`，讓表格一律撐滿到跟標題/段落文字同樣的右邊界，不論內容多短。

已用隔離測試伺服器＋真實瀏覽器（含一個有巢狀子項目、兩個表格、多種標題層級混合的測試筆記）驗證：所有標題與段落文字的左邊界統一落在區塊自身框線位置；清單/巢狀清單項目的文字統一比同一層的區塊框線多縮進 22px、且巢狀層級間的相對縮排量不變；兩個表格不論內容長短，右邊界都精準對齊到跟標題/段落文字相同的座標；調整格式鈕（含下拉選單點擊套用格式）與摺疊箭頭（點擊摺疊/展開子項目）在浮動定位後功能與可點擊性都正常，並確認瀏覽器主控台沒有任何錯誤。

### 表格區塊（第二階段：插入新表格、新增/刪除列與欄）
第一階段只做到「正確顯示既有表格＋編輯既有儲存格」，插入新表格只能靠切到「檢視原始碼」貼上/手打 pipe 語法。這次要補上「從介面新增表格、新增/刪除列與欄」，先簡短研究了幾個同類工具在「新增/刪除列欄」這個具體操作上的做法：Notion／Google Docs 是在欄列邊界 hover 顯示插入線與圓形按鈕，或欄位把手選單（插入左/右、刪除、複製），互動較豐富但需要額外的 hover 判斷、插入位置計算等版面邏輯；Obsidian／Typora 這類較輕量的表格編輯器則是「表格固定角落顯示一顆『+』」（右側加欄、下方加列），刪除則是每欄/列旁一顆小「×」，沒有拖曳、沒有插入到中間的功能。選擇跟進後者：結構簡單、不需要拖曳或欄位選單，也跟這個專案既有的「hover 出現一顆小按鈕」風格（樹狀節點的「⋮」、區塊的「Aa」）一致，本次評估後直接採用可實作。

**插入表格**：既有的「Aa」區塊格式選單（`FORMAT_OPTIONS`）新增一個「表格」選項；點擊後把目前區塊轉成一個 2×2 的表格（若原本有文字，保留到第一格 `rows[0][0]`，不會被無聲丟棄），焦點移到第一格。只在格式選單這一個既有入口新增選項，沒有另外做斜線指令或獨立的「插入區塊」按鈕。

**新增/刪除列欄**：`renderTableBlock` 重新設計表格結構——每一列前面多一個「角落欄」（表頭列該格空白，資料列該格放「刪除這一列」的「×」按鈕，rowIndex 0 的表頭本身不能被刪）；表頭列最後多一格「+」新增欄按鈕；`tbody` 最後多一列（`colspan` 撐滿所有欄）放「+ 新增列」按鈕。對應四個新函式：`addTableRow`／`removeTableRow`（`rowIndex <= 0` 時拒絕刪除表頭）／`addTableColumn`／`removeTableColumn`（只剩 1 欄時拒絕刪除，避免表格變成 0 欄）；四個都是修改 `block.rows`/`block.align` 後呼叫 `render()` + `commitChange(true)`，跟其他會改變區塊結構（非單純打字）的操作一致，會產生一筆可 `Ctrl+Z` 復原的歷史紀錄。

**鍵盤 Tab 導覽**：儲存格改成「外層 `<th>`/`<td>` 不可編輯、內層包一個 `<span class="block-table-cell-text" contenteditable>`」的結構，而不是讓 `<th>`/`<td>` 本身直接可編輯——原因是刪欄按鈕（「×」）需要放在同一個表頭儲存格裡，如果儲存格本身就是 contenteditable，這顆按鈕會被當成儲存格文字內容的一部分（`textContent` 會混進 `×`，使用者打字時也可能不小心選取/刪到它），拆成內層 span 之後按鈕跟可編輯文字互不影響。Tab／Shift+Tab 的 keydown 監聽器掛在這個內層 span 上：同一列往右/左移動；到達列尾/列首時跨到下/上一列；在最後一列最後一格按 Tab 會直接呼叫 `addTableRow` 新增一列並移入（比照試算表/多數表格編輯器的慣例）。新增 `focusTableCell(blockId, rowIndex, colIndex)` 依 `data-col` 屬性定位到指定儲存格的內層 span 並設定游標到文字結尾。

已用隔離測試伺服器驗證：一開始誤把刪欄按鈕直接放進 contenteditable 的 `<th>` 裡，實測發現儲存格文字被「第一項×」這種混入按鈕文字的方式污染——改成內層 span 結構後重測確認乾淨（`textContent` 不含按鈕文字，輸入事件只更新到 `block.rows` 對應位置）。功能驗證：從格式選單插入表格且保留原文字、新增列/新增欄、刪除列/刪除欄（含刪到剩 1 欄時的拒絕保護）、Tab 在同列/跨列前進、Shift+Tab 後退（含跨列到上一列最後一格）、在最後一格按 Tab 自動新增列並移入焦點——每一步都直接讀 `window.NotesEditor.getBlocks()` 核對記憶體中的資料結構，並確認背景自動存檔後 `.md` 檔案內容正確。

Ctrl+Z／Tab 這兩個鍵盤快捷鍵在這次測試環境裡透過自動化工具送出的真實按鍵一度沒有被頁面收到（懷疑是瀏覽器分頁焦點/合成鍵盤事件在該工具當下的限制，並非程式邏輯問題）；改用 `element.dispatchEvent(new KeyboardEvent(...))` 直接對已聚焦的儲存格觸發 `keydown` 驗證 Tab 導覽邏輯本身（這類測試屬於驗證「自己註冊的事件處理常式」，不像拖放事件那樣依賴瀏覽器原生的座標命中判定，用合成事件驗證是合理的）。Ctrl+Z 復原沒有另外針對表格重新測試，但新增/刪除列欄呼叫的是既有的 `commitChange(true)`，跟其他一般文字區塊的結構性操作（例如縮排、格式轉換）用的是同一支函式、同一套歷史紀錄機制，先前已在其他情境驗證過可正常復原。

已知限制：只能在表格「最後」新增列/欄，不能插入到中間；沒有拖曳調整欄寬；沒有整個表格區塊的刪除按鈕（要移除整個表格仍要切到「檢視原始碼」）。

### 表格儲存格內的 Ctrl+Z 改用 App 自己的復原機制（含二次修正：改成全域監聽）
上一階段刻意把 `Ctrl+Z`/`Ctrl+Shift+Z` 留給表格儲存格所在的 `contenteditable` 元素自己處理（沒有攔截），原因是當時只想先把新增/刪除列欄的功能做出來。使用者實測後回報：在表格儲存格內按 `Ctrl+Z` 感覺像是「只能復原一次」。

原因排查：因為沒有攔截，瀏覽器會用它自己對該 `contenteditable` 元素內建的復原堆疊處理——這跟 App 自己的 `history`/`historyIndex`（100 步、以整個區塊樹為單位）完全是兩套獨立機制。瀏覽器原生堆疊本身不一定只能復原一次，但任何一次結構性操作（新增/刪除列、新增/刪除欄）都會呼叫 `render()` 整個重新產生表格 DOM，把舊的 `contenteditable` 節點連同它自己的原生復原歷史一起丟棄、換成全新節點——所以只要使用者曾經新增/刪除過列欄，該儲存格的瀏覽器原生復原歷史就會被清空重來，體感上就像「常常只能復原一次」。

**第一版修正（後來發現不夠）**：直接讓表格儲存格的 `keydown` 監聽器在偵測到 `Ctrl+Z`／`Ctrl+Shift+Z`／`Ctrl+Y` 時呼叫既有的 `undo()`/`redo()`，跳過瀏覽器原生的 contenteditable 復原（比照一般區塊 `handleKeydown` 的判斷式）。

使用者實測後給出更完整的重現步驟（新增列輸入 456、再新增列輸入 789，然後連續按 `Ctrl+Z`）：第一次 `Ctrl+Z` 正確讓「789」文字消失，但**第二次 `Ctrl+Z` 完全沒反應**，跟預期的「789 那一列整個消失」不符。

根因排查：`undo()` 內部呼叫 `restoreSnapshot()`，會用 `container.innerHTML = ''` 整個重繪編輯區、換上全新的 DOM 節點，但重繪後沒有任何程式碼把焦點移回任何一個儲存格或區塊——這其實是這個專案在更早之前（Backspace 合併相鄰區塊那個功能）就已經記錄過、但當時判斷「範圍外」而沒有修的同一個根因：**復原一次之後畫面焦點會消失，若監聽器是掛在個別區塊/儲存格上，第二次按 `Ctrl+Z` 時已經沒有任何元素擁有焦點，事件自然發不到任何一個監聽器手上**，也就是「什麼事都沒發生」。第一版修正只是把這個既有根因原封不動地帶進了表格儲存格，並沒有解決它。

**第二版修正（實際採用）**：與其在每個可能取得焦點的元素上各自掛一份 `Ctrl+Z` 處理、且每次都要祈禱焦點還在，不如把 `Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y` 改成**只註冊一次的全域 `document` 監聽器**（在 `init()` 裡），不依賴目前焦點落在哪個特定元素上：
- 用 `container.hidden` 判斷目前是否在區塊模式（區塊模式才攔截；原始碼模式維持使用 `<textarea>` 原生復原，兩者本來就是分開的機制，README 已有說明）。
- 額外用 `document.activeElement` 判斷：只有在焦點是 `document.body`（代表沒有東西聚焦，例如剛復原完畫面重繪後）或焦點落在 `container` 內部時才攔截；若焦點落在別的地方（例如樹狀節點的重新命名/搬移彈出視窗的文字輸入框），就不攔截、讓那個輸入框自己的原生復原正常運作——這個排除是因為第一次接上全域監聽器時，範圍沒收斂好會連彈出視窗裡打字的 `Ctrl+Z` 都攔截掉，等於使用者在改筆記名稱時按 `Ctrl+Z` 想改掉打錯的字，卻被誤判成要復原筆記內容，因此額外測試補上了這個排除。
- 同時把一般區塊 `handleKeydown` 裡原本自己處理 `Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y` 的那段判斷式整段移除，以及表格儲存格第一版修正加的那段也整段移除——兩邊都不再各自處理，只保留這一個全域監聽器，避免同一次按鍵被兩個監聽器各自呼叫一次 `undo()`，變成一次按鍵復原兩步的重複觸發問題。

已用隔離測試伺服器完整重現使用者回報的操作序列（新增列輸入 456、等待超過 600ms 的合併視窗、再新增列輸入 789）並連續按 4 次 `Ctrl+Z`，確認結果與使用者原本預期的順序完全一致：「789」文字消失 → 789 那一列整個消失 → 「456」文字消失 → 456 那一列整個消失，回到操作前的原始狀態；再按 `Ctrl+Shift+Z` 確認可以正確往前一步。另外驗證：在重新命名彈出視窗的文字輸入框內按 `Ctrl+Z` 不會被攔截（`defaultPrevented` 為 `false`，走原生復原）；切到「檢視原始碼」模式時 `Ctrl+Z` 也不會被攔截（同樣走 textarea 原生復原）；一般區塊（標題）連續按兩次 `Ctrl+Z`（中途不重新點擊聚焦）也能正確連續復原兩步——確認這次修正同時把先前記錄過的「復原後焦點消失、下一次要先點回去才能再復原」這個既有已知限制一併解決掉了，不只是表格專屬的修正。瀏覽器主控台全程無錯誤，Python 測試 36 個維持全過。

### 編輯區內直接重新命名筆記＋顯示相對更新時間

### 插入圖片
使用者請我先研究「以現有介面來說要怎麼擴充插入圖片」，並問圖片該存在共用目錄還是各自目錄。研究後提出三個插入手勢（貼上、拖放、格式選單）與三種儲存位置（共用資料夾、每篇筆記各自附屬資料夾、跟 md 同目錄）的取捨；使用者確認：插入手勢與圖片獨立成一個區塊型態都照建議做，但儲存位置最後選「跟 md 檔同目錄，不建立額外資料夾」（比我原本建議的「每篇筆記各自 `.assets/` 資料夾」更簡單）；檔名衝突「後蓋前，使用者自行負責」；限制副檔名與 10MB 大小上限；後端 API 怎麼設計交給我決定。確認方向後，使用者接著想到兩個因「同目錄、不建立資料夾」才會發生的新問題：搬移筆記到別的資料夾時圖片不會跟著搬（參考會失效）、刪除筆記不會一併刪除同目錄圖片（可能被其他筆記共用，無法確定），並提出「未來要做：搬移/刪除有圖片時跳出確認提示（沒得選、只能繼續或取消）」，但明確表示**這次不用實作**，先記錄下來。

**資料模型**：`Block` 新增 `src` 欄位（Python／JS 兩邊比照 `rows`/`align` 的模式）。Parser 新增 `_IMAGE_RE`（`^!\[([^\]]*)\]\(([^)\s]+)\)$`），一整行**只有**一個 `![alt](檔名)`、沒有其他文字時才視為圖片區塊（避免段落文字中間夾雜的圖片語法被誤判，那種情況維持當作一般段落文字，這部分暫不支援行內圖片）；serializer 對應輸出 `![alt](src)`。

**儲存路徑設計**：關鍵決定是「.md 檔案裡存的內容」跟「瀏覽器顯示圖片用的網址」要分開處理，兩邊各自簡單：
- **持久化格式**：`block.src` 就是不含路徑的純檔名（例如 `photo.png`），Python／JS 的 parser／serializer 完全不用處理任何路徑運算，跟其他欄位（`text`、`rows`）對稱處理——這樣 `.md` 檔案本身維持可攜性，複製整個資料夾到別的地方，圖片連結依然有效，不會因為換了機器/路徑而失效。
- **顯示網址**：由前端負責組出可以載入的網址。`app.js` 在 `selectNode()` 呼叫 `NotesEditor.load(data.blocks, parentDirOf(node.path))` 多帶一個「目前筆記所在資料夾」的參數，`editor.js` 存成模組層級的 `imageBaseDir`；渲染圖片區塊時用 `window.NotesApi.fileUrl(imageBaseDir + '/' + block.src)` 組出 `/api/files/<路徑>` 這種可以直接 fetch 的網址。這個關聯只在瀏覽器執行期間存在，不會寫回 `.md` 檔案。

**後端**：新增 `POST /api/notes/<note_path>/images`（multipart 上傳）與 `GET /api/files/<path:rel_path>`（讀取任意檔案，沿用既有的 `resolve_safe_path` 做路徑安全檢查，用 Flask `send_file` 回傳）。上傳檔名處理**沒有**用 werkzeug 的 `secure_filename`——那個函式會把非 ASCII 字元（中文檔名）整個過濾掉或轉成底線，對這個中文為主的 App 不合適；改寫一個簡單的 `_safe_upload_filename`：只取 `os.path.basename()`（防止檔名帶路徑分隔符逃逸）、拒絕空字串/`.`/`..`/含 null byte，中文檔名可以完整保留。副檔名白名單 `{'.png','.jpg','.jpeg','.gif','.webp'}`、大小上限 `10 * 1024 * 1024`（讀取 `file.stream` 的 seek/tell 取得實際大小，不信任 `Content-Length` 表頭）。檔名衝突比照使用者要求，直接覆蓋、不做任何自動重新命名。

**前端插入流程**：三種手勢共用同一個 `onImageUpload(file)` callback（`init()` 時由 `app.js` 傳入，內部呼叫 `NotesApi.uploadImage(currentNode.path, file)`），editor.js 本身不知道目前是哪一篇筆記、也不直接碰 API，維持原本「泛用區塊樹編輯器」的角色分離：
- **貼上**：`container` 上掛一個 `paste` 監聽器（而非每個區塊各自掛），檢查 `clipboardData.items` 有沒有 `image/*` 類型；找到就用 `document.activeElement` 反查目前是哪個區塊（`findBlockTextAncestor`），上傳成功後呼叫 `insertImageBlockAfter(block, filename)`，在該區塊**之後**插入新的圖片區塊、原區塊文字不受影響（不是把目前區塊直接轉成圖片，因為貼上圖片時使用者通常還在打字，不是想把已經打的內容整個換掉）。
- **拖放**：同樣掛在 `container` 上，檢查 `dataTransfer.files`（外部檔案拖放用這個，跟樹狀索引內部搬移節點用的 `dataTransfer.setData('text/plain', path)` 是不同的資料管道，兩者不會互相干擾）；找到圖片檔案就上傳，成功後呼叫 `appendImageBlock(filename)`，固定加在筆記最後（沒有做「依放開座標找最近的區塊插入」這種精準定位，先求簡單）。
- **格式選單插入圖片**：`FORMAT_OPTIONS` 加一個「插入圖片」選項，但**不能**沿用其他選項「點了就直接把 `block.type` 設成目標型態」的既有邏輯——因為使用者可能在檔案選擇視窗按取消，這時不該已經把區塊型態改掉。改成點擊後呼叫 `promptInsertImage(block)`，動態建立一個 `<input type="file" accept="image/png,image/jpeg,image/gif,image/webp">` 並觸發 `.click()`，只有在 `change` 事件真的選到檔案、上傳也成功之後，才把 `block.type` 設為 `'image'`、`block.src` 設為回傳的檔名；並比照「轉成表格保留原文字到第一格」的既有慣例，把區塊原本的文字保留成圖片的 `alt`（`block.text`），不會被無聲丟棄。

**渲染與刪除**：圖片區塊跟表格區塊一樣，不透過一般區塊共用的 `renderBlock` 流程（沒有調整格式鈕、摺疊箭頭、清單標記），整個渲染成一個 `<img>`，hover 顯示右上角一顆「×」刪除按鈕，點擊呼叫既有的 `removeBlock(block._id)` + `commitChange(true)`——只移除筆記內容裡的這個區塊，不會連帶刪除磁碟上的圖片檔案（保留孤兒圖片，對應使用者提到但先不實作的「刪除時警告」需求）。

### 程式碼區塊
使用者在確認我有能力實作圍欄程式碼區塊（```` ``` ````）之後直接請我實作，沿用跟表格/圖片同一套模式（新增區塊型態、parser 辨識、serializer 輸出、格式選單插入）。

**資料模型**：`Block` 新增 `lang` 欄位（Python／JS 對稱處理，比照 `src`）。Parser 新增 `_FENCE_RE`（`^```(\w*)\s*$`，只比對去除頭尾空白後的整行），命中後**不逐行套用其他 Markdown 規則**、直接把後續每一行原封不動蒐集起來（不 `strip()`，保留縮排），直到遇到一行內容恰好是 ` ``` ` 為止（或碰到檔案結尾，視為未閉合圍欄，內容涵蓋到檔案結尾）；蒐集到的行以 `\n` join 存成 `text`，開頭圍欄後面的文字存成 `lang`。Serializer 輸出時利用一個小技巧：`` '```' + lang + '\n' + text + '\n```' `` 當成**單一一個字串**塞進要輸出的 `lines` 陣列（而非把 `text` 內部的每一行拆開個別 append），因為最終組字串是用 `'\n'.join(lines)`，一個陣列元素內部本來就可以包含自己的 `\n` 換行符，一樣能正確跟前後的其他行接起來，不需要額外處理。

**編輯器渲染**：跟表格/圖片一樣不走一般區塊共用的 `renderBlock` 流程（沒有調整格式鈕/摺疊箭頭/清單標記）。上方一個純文字 `<input>` 記錄語言標記（純粹存文字，不做語法高亮、不驗證是否為合法語言名稱），下方一個 `<textarea>` 放程式碼內容——**選用 `<textarea>` 而不是跟其他文字區塊一樣的 `contenteditable`**，原因是程式碼需要原樣保留縮排/換行，`contenteditable` 對 Enter 鍵在不同瀏覽器有不一致的 `<div>`/`<br>` 插入行為，反而更難保證空白字元被精準保留；`<textarea>` 原生就是為了多行純文字設計，這個 App 既有的「檢視原始碼」模式也是用同一個元件、已經驗證過可靠。`input` 事件即時同步 `block.text`／`block.lang`，並呼叫一個簡單的 `autoGrowTextarea`（`style.height='auto'` 再設回 `scrollHeight`）讓高度隨內容自動增高，不需要手動拖曳調整（仍保留 CSS `resize: vertical` 讓使用者可以自行覆寫高度）。

**刪除**：兩種方式——內容清空後按 `Backspace`（比照一般文字區塊清空後刪除的既有慣例）、或 hover 出現右上角「×」按鈕（不論內容是否清空都可以直接刪，比照表格/圖片區塊的做法），兩者都呼叫既有的 `removeBlock` + `commitChange(true)`，包含「不能刪掉筆記裡最後一個頂層區塊」這個既有的安全防呆也自動套用（沒有另外寫特殊邏輯，`removeBlock` 本來就是型態無關的）。

**復原機制／格式選單插入**：完全重用既有基礎設施，沒有新寫任何專屬邏輯——`Ctrl+Z` 全域監聽器只檢查焦點是否在 `container` 內，`<textarea>` 本來就是 `#block-editor`的子元素，直接就適用；格式選單新增「程式碼」選項，因為只需要 `text`（已存在，會自動帶過去）加一個 `lang: ''` 初始值，不像表格/圖片需要在轉換當下額外準備複雜的初始資料結構或先跳出檔案選擇視窗，所以不需要像 `image`/`table` 那樣特別攔截點擊事件，只需要多一個 `else if (opt.type === 'code_block')` 分支設定 `block.lang = block.lang || ''`、呼叫新增的 `focusCodeBlock()`把焦點移到 `<textarea>`（沿用 `focusTableCell`/`focusBlock` 的既有寫法風格）。

**刻意不做的**：`Tab` 鍵在程式碼區塊內沒有攔截（原生瀏覽器行為是把焦點移出，不會插入縮排字元或空白），沒有語法高亮，沒有把「輸入 ` ``` ` 自動轉換」這種打字捷徑（跟標題的 `# ` 自動轉換不同，程式碼區塊只能透過格式選單建立）——這些都是為了先求正確可用、範圍不擴大，之後有需要再加。

### 修正：插入圖片／程式碼區塊後沒有機制可以在下面繼續打字
使用者實測回報：插入圖片、或在程式碼區塊裡按 `Enter`，都沒辦法在下面新增一行——按 Enter 沒有反應。

排查發現這其實是兩個各自獨立、原因不同的問題：

**圖片**：`insertImageBlockAfter`／`appendImageBlock`／`promptInsertImage`（格式選單轉換）這三個插入路徑，原本上傳成功後只呼叫 `render(); commitChange(true);`，**完全沒有呼叫任何 focus 函式**。因為圖片區塊本身沒有 `.block-text`（不像其他區塊有可編輯的文字介面），畫面重繪後編輯焦點就直接消失、落在 `document.body` 上——不是「按 Enter 沒反應」，而是這時候根本沒有任何元素持有焦點，鍵盤事件無處可去，所以不管按什麼鍵都沒有用。

**程式碼區塊**：`<textarea>` 原生的 `Enter` 行為本來就只是「在文字內容裡插入一個換行字元」，這對於「正在寫多行程式碼」是正確、需要的行為（不應該一按 Enter 就跳出整個程式碼區塊，那樣反而沒辦法輸入真正的多行程式碼），所以並不是 bug，但也確實沒有提供「我打完程式碼了，想跳出去繼續寫筆記」的退出手段。

**修正**：兩者用同一個共用概念解決——新增 `NON_TEXT_TYPES = ['image', 'table', 'code_block']` 與共用函式 `ensureFollowingParagraph(list, afterIdx)`：檢查 `afterIdx` 後面那個區塊是否存在、且型態不在 `NON_TEXT_TYPES` 內（也就是有 `.block-text` 可編輯），有的話就直接回傳它的 id 重複利用（不憑空多插入一個空段落）；沒有的話（不存在，或緊接著的也是圖片/表格/程式碼這類不可輸入文字的區塊）就新插入一個空白 `paragraph` 並回傳它的 id。三個圖片插入路徑上傳成功後都呼叫這個函式取得要聚焦的區塊 id，再呼叫既有的 `focusBlock(id, false)`。

程式碼區塊則是在既有的 `Enter` 判斷式裡，比照這個專案已經用過的「連續兩次都是空的才觸發」規則（跟先前「清單項目清空後再按 Enter 才跳出清單」是同一種設計語言）：判斷游標是否在內容最後（`selectionStart === value.length`）且目前內容是空字串或已經以 `\n` 結尾（代表使用者剛按過一次 Enter、還沒在那個新行打任何字）——符合才觸發跳出：`preventDefault()`、把那個多餘的尾端空行去掉（`.replace(/\n$/, '')`）、呼叫同一個 `ensureFollowingParagraph` 移動焦點。不符合（例如最後一行還有內容）就放行，讓瀏覽器原生行為正常插入換行，維持多行程式碼的正常輸入體驗。

已用隔離測試伺服器驗證：貼上圖片後（前面/後面都已有其他文字區塊時）正確重用既有的下一個區塊、不多插入空段落，也能直接接著打字；貼上圖片在筆記最尾端時正確新增並聚焦一個空白段落；程式碼區塊第一次按 Enter（模擬「瀏覽器沒攔截時才手動補插入換行」，因為合成的 `KeyboardEvent` 本來就不會觸發瀏覽器原生的文字插入，這點測試時要留意，不能真的送出瀏覽器原生按鍵）正確不觸發跳出、只留在區塊內新增空行；同一位置再按一次才正確跳出、清掉多餘空行、聚焦到下一個區塊；同時意外測到一個更刁鑽的情境：如果跳出時緊接著的下一個區塊剛好也是另一個程式碼區塊（同樣不可輸入文字），系統正確在兩者之間插入一個新段落，而不是誤判或出錯。瀏覽器主控台全程無錯誤，Python 測試 53 個維持通過（此次為純前端修正，未變動 parser/serializer）。
### 修正上一項修正：實際操作中仍然無法接續打字，改用渲染時的固定不變量

上一項修正（`ensureFollowingParagraph` + 三個圖片插入路徑的 `focusBlock` + 程式碼區塊雙按 `Enter` 跳出）在自動化測試裡完整跑過所有路徑都正確通過，但使用者實測回報依然沒辦法接著打字。沒有再花時間往鍵盤事件時機或 `focus()` 呼叫時機的方向繼續除錯（合成事件測試通過不代表真實瀏覽器裡的 focus/事件時機一定正確，兩者已知會有落差），改採使用者提出的方向：與其依賴「插入當下」的一次性程式化動作（可能因為某個時間點的 DOM 還沒繪製完成、或瀏覽器對 `focus()` 呼叫時機的處理跟預期不同而默默失敗），不如讓「使用者看到什麼、能不能點下去打字」直接由渲染結果保證，不牽涉任何時間點或事件觸發順序。

**做法**：`render()`（統一的重繪入口，不論是載入筆記、插入區塊、還是 undo/redo 復原，最終都會呼叫到它）開頭新增 `ensureTrailingParagraph()`：只看 `blocks` 陣列（僅頂層，不含巢狀清單）的最後一個區塊，型態若屬於 `NON_TEXT_TYPES`（圖片／表格／程式碼），就直接 `push` 一個空白 `paragraph`。這個檢查每次重繪都會重新做一次，所以不管什麼操作路徑導致「文件最底下變成非文字區塊」這個狀態成立，下一次重繪畫面上就一定會多一行空白、可點擊、可直接打字的段落——不需要精準呼叫某個 focus 函式、不需要使用者剛好在某個時間點按下某個鍵。

**存檔不能把這個輔助用的空白段落也存進去**：新增 `stripAutoTrailingParagraph(list)`，只有在「最後一個區塊是空白 `paragraph`（無文字、無子項目）**且**倒數第二個區塊型態屬於 `NON_TEXT_TYPES`」這個精確條件下才濾掉最後一個區塊——這個條件刻意設計成剛好是 `ensureTrailingParagraph` 會觸發新增動作的反向條件，所以只會濾掉「自動補上、使用者還沒碰過」的那一個，不會誤刪使用者自己特意留白的段落（例如使用者自己在兩個文字段落之間按 Enter 留一行空白，那種情況倒數第二個區塊不是非文字型態，不會被濾掉）。`snapshotBlocks()`（undo/redo 快照）與 `getBlocks()`／`getMarkdownSource()`（存檔/複製原始碼路徑共用的同一個函式）都先套用這層過濾，所以這個輔助段落完全不會出現在復原歷史或 `.md` 檔案裡；一旦使用者真的在裡面輸入了任何內容，這個過濾條件就不再成立，它就自然變成一個「正式」的段落，一併存檔。

跟任務 38 的關係：38 的機制（插入圖片時自動聚焦、程式碼區塊雙按 Enter 跳出）維持保留，兩者不衝突且處理的情境不同——38 處理的是「插入當下，緊接在該區塊後面補一個可編輯段落」，就算該區塊不在文件最底下（例如插在文件中間）也適用；這次新增的不變量則是不論任何操作路徑、任何時間點，只要「文件最底下是非文字區塊」這個狀態成立就一定成立的保底機制，兩者疊加使用。

已用隔離測試伺服器驗證（皆為真實滑鼠點擊/鍵盤輸入，非合成事件）：於一則筆記中把段落轉成程式碼區塊（此時它是文件裡唯一/最底下的區塊），畫面確實多渲染出一行空白段落，直接點擊該處輸入文字即可正常接續編輯；用 `getBlocks()`／`getMarkdownSource()` 確認未輸入內容時該輔助段落不存在於回傳結果，存檔後的 `.md` 檔案（以十六進位檢視確認結尾位元組）確實乾淨、無多餘換行或空白行；輸入內容後重新檢查，確認該段落正確以真正段落的身份保留並存檔。另外用 `loadFromMarkdownSource` 載入以 `![alt](test.png)` 結尾的 Markdown（模擬圖片為文件最底下區塊的情境），同樣確認多渲染出可點擊空白段落且存檔時正確濾掉。Python 測試 53 個維持通過（純前端修正，未變動 parser/serializer/後端）。

## Risks / Trade-offs

- [Python 3.8 已停止官方安全更新] → 僅作為本機離線工具使用，不對外部網路開放服務，降低此風險的實際影響；於文件中註明此限制。
- [第三方套件版本可能於後續釋出中放棄 Win7/舊版 wheel 支援] → 將相依套件數量降到最低（僅 Flask 及其核心相依），並於專案文件中明確釘選（pin）已驗證可在 Win7 上運作的版本號。
- [自訂大綱 ⇄ Markdown 序列化規則覆蓋語法有限] → 明確定義並文件化支援的區塊型態（標題/清單/段落），非支援語法以純文字段落保留，避免使用者資料遺失。
- [路徑安全檢查若實作不慎可能被跳脫] → 統一透過單一共用的路徑正規化與範圍檢查函式處理所有檔案系統 API，不允許個別端點自行組合路徑。
- [中文檔名/內容在 Win7 舊版檔案系統下的編碼疑慮] → 一律以 Python 3 的 Unicode 路徑 API 與 UTF-8 讀寫檔案內容，不依賴系統 ANSI 預設編碼。
- [樹狀拖曳搬移使用 HTML5 原生拖放 API，觸控裝置（無滑鼠）不支援拖放手勢] → 右鍵選單的「搬移」（手動輸入目標路徑）維持保留作為替代操作方式，觸控裝置使用者仍可完成搬移。
- [前端（JS）與後端（Python）各自維護一份 Markdown 解析/序列化邏輯，可能因修改不同步而產生行為落差] → 兩者的規則刻意保持極簡（僅標題/清單/段落三種型態），並在測試中涵蓋相同案例；未來若擴充語法支援，需同時更新 `noteapp/markdown_blocks.py` 與 `static/js/markdown.js`。
- [行內字級以內嵌 HTML `<span>` 存檔，不是標準 Markdown 語法] → 大多數 Markdown 檢視器都支援內嵌 HTML 直接渲染，相容性風險低；但若使用者拿去不支援內嵌 HTML 的檢視器開啟，會直接看到原始的 `<span>` 標籤文字，已於 README 的已知限制中註明。

## Migration Plan

全新專案，無既有系統或資料需要遷移。初次部署步驟：
1. 在目標機器安裝 Python 3.8（Win7 相容版本）。
2. 安裝已釘選版本的相依套件（`pip install -r requirements.txt`）。
3. 設定筆記根目錄（環境變數或設定檔），或使用預設的 `notes/` 資料夾。
4. 啟動本機伺服器，於瀏覽器開啟 `http://127.0.0.1:<port>` 使用。

無需回滾（rollback）機制：本工具不修改既有系統，移除即完成復原。

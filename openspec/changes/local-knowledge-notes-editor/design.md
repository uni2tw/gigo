## Context

這是一個全新、獨立的 Python 專案（與本 repo 內既有的 `PXB2E.*` .NET 專案無關），目標是在使用者本機（可能是 Win7）啟動一個網站，透過瀏覽器操作。核心限制：
- 必須相容 Win7 可執行的 Python 版本。
- 不依賴雲端服務、資料庫或需要編譯的第三方套件。
- 樹狀結構與筆記內容都直接對應本機檔案系統（見 `markdown-file-storage` spec）。

詳見 proposal.md 的 Why / What Changes。

## Goals / Non-Goals

**Goals:**
- 提供一個可在 Win7 上以雙擊或簡單指令啟動的本機 Web 應用。
- 前後端皆使用最少、風險最低的相依套件，降低在舊系統上安裝失敗的機率。
- 樹狀索引與大綱編輯器的資料一律即時反映為本機檔案系統上的實體檔案/資料夾。

**Non-Goals:**
- 不實作全文搜尋（proposal 已明確排除）。
- 不支援多使用者同時編輯或任何形式的權限/帳號系統（單機單使用者情境）。
- 不實作留言/註解功能（使用者已確認不需要）：需要獨立的留言資料模型、歸屬（誰留言）、顯示與後端儲存，超出單機單人筆記工具的範圍。
- 不將編輯器的摺疊/展開等純 UI 狀態持久化為檔案的一部分。

## Decisions

### Python 版本：3.8
Python 3.8 是官方最後一個提供 Windows 7 安裝版的版本（Python 3.9 起官方安裝程式不再支援 Win7）。所有相依套件版本須確認其對應的 wheel 有支援到可在 Win7 上執行的 CPython 3.8。

### 後端框架：Flask（搭配 Werkzeug 內建開發伺服器）
選擇 Flask 而非自行以 `wsgiref`/`http.server`手刻路由，理由：
- Flask 與其相依套件（Werkzeug、Jinja2、MarkupSafe、click、itsdangerous）皆為純 Python 實作，不需要編譯 C 擴充套件，Win7 上的相容風險與零相依方案相近。
- 相較於自行手刻 WSGI 路由，Flask 可大幅減少樣板程式碼與出錯機會，且文件與生態成熟，利於長期維護。
- 相較 Bottle（單檔零相依），Flask 生態更成熟；由於两者在 Win7 上的相依風險相近，優先選擇維護性更好的 Flask。

伺服器僅綁定 `127.0.0.1`（不對外開放網路），因為此工具設計為本機單人使用，不需要對外提供服務。

### 前端：純 Vanilla HTML/CSS/JavaScript，無建置流程
不使用需要 Node.js/npm 建置的前端框架（React/Vue 等），理由：
- 目標環境（Win7）不一定有 Node.js 可用於建置，且執行期也不需要任何前端建置產物之外的東西。
- 樹狀索引與大綱編輯器的互動邏輯規模有限，純 JavaScript 即可勝任，避免引入外部 CDN 相依（本工具需可離線本機執行）。

大綱編輯器（區塊、縮排層級、摺疊狀態、排序）以自訂的最小化 JavaScript 元件實作，不引入第三方富文本編輯器函式庫，以降低相依風險與授權/版本相容疑慮。

### 資料模型：檔案系統即單一事實來源
不另外建立資料庫或中介的 metadata 儲存。樹狀結構節點 = 本機資料夾／`.md` 檔案，讀取樹狀索引時即時掃描筆記根目錄。摺疊/展開狀態純粹是前端執行期的 UI 狀態，不寫回檔案，以維持 `.md` 檔案的純文字可攜性（對應 `markdown-file-storage` 的「Markdown 純文字格式相容性」需求）。

### 大綱區塊 ⇄ Markdown 序列化規則
編輯器內部以區塊樹（block tree，含層級與順序）表示筆記內容；儲存時序列化為標準 Markdown 語法：
- 具有子項目的區塊層級 → 巢狀項目符號清單（依縮排層級對應清單縮排）。
- 標題型態區塊 → `#`～`######` 標題語法。
- 一般文字區塊 → 純段落文字。

載入既有 `.md` 檔案時，以同一套規則的反向解析，將 Markdown 文字還原為區塊樹。此規則只涵蓋標題、清單（含巢狀）、段落三種區塊型態，不支援其餘 Markdown 語法（如表格、程式碼區塊）的專屬區塊化編輯；若檔案含有這類語法，載入時以純文字段落區塊呈現，儲存時原樣保留純文字內容，不做語意轉換。

### 路徑安全性
所有涉及檔案系統的 API（讀取、寫入、建立、重新命名、刪除、搬移）一律：
1. 將請求路徑與設定的筆記根目錄組合後，取其正規化絕對路徑（resolve symlink、`..` 等）。
2. 檢查該絕對路徑是否仍位於筆記根目錄之內，否則直接拒絕並回傳錯誤，不執行任何檔案系統操作。

### 筆記根目錄設定
筆記根目錄透過環境變數（例如 `NOTES_ROOT`）或同層設定檔指定；未設定時預設為執行檔所在目錄下的 `notes/` 資料夾，若該資料夾不存在則於啟動時自動建立。

### UI 視覺風格：類 Outline 的簡潔版面
前端版面與視覺風格參考 Outline 筆記軟體的呈現方式（僅取版面配置與視覺風格，不採用其功能或內容）：
- 左側側欄：可摺疊的樹狀結構，資料夾／筆記節點以簡潔的清單呈現，選中節點有明顯的高亮背景。
- 右側編輯區：頁面頂部為大字級的筆記標題，內文以清爽的無襯線字體、充足留白呈現；區塊化內容（標題、清單、段落）之間有清楚的視覺層級。
- 整體配色簡單、乾淨，避免多餘的裝飾線條或圖示，聚焦於內容本身的可讀性。

此為前端 CSS/版面設計的依據，不影響 API 或資料模型的行為（不新增 spec 需求）。

### 區塊格式選單（Hover Toolbar）
考量單靠輸入 `#` 前綴切換標題層級的方式不易被使用者發現，於每個區塊列滑鼠移入時顯示一個小型「Aa」格式按鈕，點擊展開下拉選單（標題 1／標題 2／標題 3／一般文字），可直接切換該區塊的型態與層級，等效於輸入對應的 Markdown 前綴語法，兩者可互換使用、不衝突。

### 原始 Markdown 原始碼檢視/編輯模式
為支援使用者直接貼上既有 Markdown 內容，或編輯區塊編輯器尚未支援的語法（如表格、程式碼區塊），於編輯區加入「檢視原始碼」切換鈕：
- 切換至原始碼模式：將目前區塊樹序列化為 Markdown 文字，顯示於一個可編輯的 `<textarea>`。
- 切換回區塊模式：將 textarea 內容重新解析為區塊樹並渲染。
- 自動儲存機制在兩種模式下皆生效（原始碼模式下先將 textarea 內容解析為區塊樹，再走既有的儲存流程）。

為避免每次切換都往返後端，解析/序列化邏輯以 JavaScript 複寫一份（`static/js/markdown.js`），邏輯與後端 `noteapp/markdown_blocks.py` 保持一致（相同的標題/清單/段落規則與縮排寬度）。兩份實作各自獨立維運，若未來修改解析規則需同步更新兩處。

### 區塊型態擴充：引用／編號清單／待辦清單
在既有的標題／清單／段落三種區塊型態之外，新增：
- `quote`：對應 Markdown `> text`，不參與縮排巢狀（每行各自成一個獨立的引用區塊）。
- `ordered_item`：對應 Markdown `N. text`，與 `list_item` 共用同一套縮排巢狀機制；序號於序列化時依「同層級中連續的 `ordered_item` 」重新計算，因此使用者調整順序或刪除項目後，編號會自動重新排列，不需手動維護。
- `checklist_item`：對應 Markdown `- [ ] text` / `- [x] text`，新增 `checked` 布林欄位；使用者可直接點擊區塊前的核取方塊切換勾選狀態，勾選後套用刪除線樣式。

這三種型態皆可透過既有的區塊格式選單（Aa）切換，也可比照標題的做法，之後視需要加入輸入時的即時偵測（例如打 `1. ` 或 `- [ ] ` 自動轉換），目前僅支援透過格式選單手動切換。

按 `Enter` 新增區塊時，若目前區塊型態為 `list_item`／`ordered_item`／`checklist_item`，新區塊會延續相同型態（避免每輸入一個編號/待辦項目都要重新選一次格式）；其餘型態（標題、引用）之後預設回到一般清單項目。

### 行內文字格式（Bold／Italic／Strikethrough／Code／Link）
新增選取文字時浮現的懸浮工具列，提供 5 個行內格式操作，對齊常見富文本編輯器（如 Notion）的體驗：
- 粗體／斜體／刪除線：透過瀏覽器原生 `document.execCommand('bold'|'italic'|'strikeThrough')` 實作，具備原生的「切換」語意（已格式化的選取範圍再次點擊會取消格式），相容性與穩定度高於自行實作。
- 行內程式碼：`execCommand` 沒有對應指令，改為手動操作 Selection Range：若選取範圍已在 `<code>` 內則解開，否則以 `range.surroundContents` 包裹一個 `<code>` 元素。
- 連結：跳出既有的 `NotesModal.prompt` 詢問網址，輸入後以 `execCommand('createLink', ...)` 套用；若選取範圍已在連結內，則改為 `execCommand('unlink', ...)` 解除連結。點擊工具列按鈕時，會在 `mousedown` 階段呼叫 `preventDefault()`，避免點擊瞬間造成 contenteditable 失焦、清空選取範圍。

**資料模型與儲存的關鍵設計**：區塊的 `text` 欄位在磁碟／API 層級「一律」是純文字並直接內嵌 Markdown 行內語法（例如 `**粗體** 一般文字`），與既有的區塊層級序列化模型完全相容——**後端完全不需要修改**：`noteapp/markdown_blocks.py` 本來就只是把整行文字（含標題/清單前綴後的部分）視為不透明字串照抄，不理解也不需要理解行內語法。所有「HTML（contenteditable 編輯中所見）⇄ 行內 Markdown 文字（儲存格式）」的轉換，都只發生在前端 `static/js/markdown.js` 新增的 `inlineMarkdownToHtml` / `htmlToInlineMarkdown` 兩個函式：
- 渲染區塊供編辑時：`block.text`（純文字，含行內 Markdown 語法）→ `inlineMarkdownToHtml()` → 設為 contenteditable 的 `innerHTML`。
- 使用者編輯或套用行內格式後：讀取 contenteditable 目前的 DOM（`innerHTML`）→ `htmlToInlineMarkdown()` 遞迴走訪節點 → 寫回 `block.text`（純文字）。

`htmlToInlineMarkdown` 對巢狀標籤採遞迴組合（例如 `<b><i>x</i></b>` 會先得到 `*x*` 再包成 `**\*x\***` = `***x***`，恰好符合標準 Markdown 粗斜體語法），`inlineMarkdownToHtml` 則以正規表示式依序處理（先保護行內程式碼片段、再處理連結、粗斜體組合、粗體、斜體、刪除線），只涵蓋這 5 種語法，不支援其餘 Markdown 行內語法（如圖片、跳脫字元的完整規則）。

### Undo / Redo（復原／取消復原）
編輯器內建一個純前端的復原歷史堆疊（不經過後端），純粹針對區塊編輯器（`static/js/editor.js`）的 `blocks` 狀態：
- 每次有意義的變更（輸入文字、Enter/Tab/Backspace/上移下移、切換區塊型態、勾選待辦清單、套用行內格式）都會對目前 `blocks` 的深層快照（JSON 字串）做一次記錄。
- 連續輸入文字時，若與上一次記錄的時間間隔在 600ms 內，直接覆蓋合併為同一個復原步驟（避免每個字都各自成一步，貼近使用者對「復原一步＝復原一個有意義的動作」的預期）；其餘結構性操作（Enter、縮排、刪除、排序、格式切換、行內格式、待辦勾選）一律視為獨立步驟，不與其他操作合併。
- 歷史堆疊上限 100 筆，超過時捨棄最舊的紀錄。
- 歷史紀錄的範圍是「單一筆記」：每次從樹狀索引開啟一篇筆記時，歷史會重設為只包含剛載入的狀態（無法復原到開啟這篇筆記之前）；切換到原始碼模式編輯後切回區塊模式，會將該次原始碼變更視為一個獨立的復原步驟，但不會重設整個歷史。
- 快捷鍵：`Ctrl+Z` 復原、`Ctrl+Shift+Z` 或 `Ctrl+Y` 取消復原，僅在區塊編輯器（`.block-text`）取得焦點時生效；原始碼模式的 `<textarea>` 使用瀏覽器原生的復原機制，兩者互不影響、也不共用歷史。
- 復原/取消復原後會照常觸發自動儲存，讓磁碟上的檔案內容與復原後的畫面狀態一致。

### 鍵盤快捷鍵
除了既有的 `Tab`/`Shift+Tab`（縮排）、`Enter`（新增區塊）、`Backspace`（刪除空區塊）、`Ctrl+↑`/`Ctrl+↓`（排序）之外，新增：
- `Ctrl+Alt+1`／`Ctrl+Alt+2`／`Ctrl+Alt+3`：將目前區塊設為標題 1/2/3。
- `Ctrl+Alt+0`：將目前區塊還原為一般文字（`list_item`）。
- `Ctrl+B`／`Ctrl+I`／`Ctrl+Shift+X`：套用粗體／斜體／刪除線，內部直接呼叫與浮動工具列相同的 `applyInlineCommand`，確保行為一致、不重複實作。

這些快捷鍵的判斷邏輯內嵌在既有的 `handleKeydown`（每個區塊各自綁定）中，不需要額外的全域鍵盤監聽器，天然限定只在區塊編輯器內生效，不會與其他頁面元件（如 Modal 輸入框、原始碼模式的 textarea）的鍵盤行為衝突。

### API 形式
後端提供簡單的 JSON API 供前端呼叫：
- `GET /api/tree`：取得目前樹狀結構
- `POST /api/nodes`：新增節點（筆記或資料夾）
- `PATCH /api/nodes/<path>`：重新命名或搬移節點
- `DELETE /api/nodes/<path>`：刪除節點
- `GET /api/notes/<path>`：讀取筆記內容（回傳區塊樹或原始 Markdown）
- `PUT /api/notes/<path>`：儲存筆記內容

前端頁面（HTML/CSS/JS）由同一個 Flask 應用以靜態檔案方式提供。

### 選取文字調整大小（行內字級）
延續行內格式（粗體/斜體/刪除線/程式碼/連結）的作法：使用者於浮動工具列選擇「小／一般／大／特大」其中之一，僅套用於目前選取的那段文字（而非整個區塊，這點與標題 H1/H2/H3 是「整個區塊變大」不同，用來滿足「選取局部文字調整大小」的需求）。

標準 Markdown 沒有原生的行內字級語法，因此比照既有的行內格式作法，直接以內嵌 HTML `<span style="font-size:Npx">text</span>` 儲存在 `block.text` 裡（同樣是「後端完全不需要修改」——`markdown_blocks.py` 只把整行文字當不透明字串照抄）。`static/js/markdown.js` 的 `inlineMarkdownToHtml`/`htmlToInlineMarkdown` 新增對這個特定 `<span>` 樣式的辨識與還原，且會遞迴處理 span 內部的其餘行內格式（例如字級內還有粗體），與既有的程式碼片段保護機制（先抽出、處理完再放回）採同一套手法。

字級只提供 4 個離散選項（12px/一般/20px/26px），不提供任意像素數值輸入，理由：
- 對齊既有格式選單（標題/引用/清單）的「選單挑選」互動模式，操作一致。
- 避免使用者存出大量不同的隨機字級值，讓筆記的視覺風格失控。

### 區塊間游標導航（ArrowUp / ArrowDown）
每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設不會在按上下鍵時把游標從一個區塊的 `<div>` 移到另一個區塊的 `<div>`（這與單一大文字框的編輯器不同）。因此明確攔截未搭配 Ctrl/Shift/Alt 的 `ArrowUp`/`ArrowDown`：先把目前的樹狀結構依「展開順序」（摺疊的子項目不計入）攤平成一個陣列，找出目前區塊的位置，將游標移至前一個／後一個區塊。

簡化決策：不論區塊內容是否換行（過長文字被瀏覽器自動包行），一律視為「上一個/下一個區塊」而非「上一個/下一個視覺行」，即使區塊內容跨多行也一樣直接跳到相鄰區塊。這對應大多數大綱編輯器（如 Workflowy）的慣例，換取實作簡單、行為可預期，避免另外量測游標在換行文字中的視覺列位置。`Ctrl+↑`/`Ctrl+↓`（調整區塊順序）維持原本行為不變，兩者可並存不衝突。

### Enter 依游標位置切開文字（而非永遠新增空白區塊）
使用者實測回報：在一個有子項目的區塊（如 `123`，子項為 `456`）最前面按 Enter，新的空白區塊出現在 `456` 之後、`789` 之前，而不是緊接在 `123` 下面，覺得不符合預期。這是因為原始實作不論游標在文字哪個位置，一律「在目前區塊後面插入一個新空白區塊」，從不真正依游標位置切開文字；而子項目在畫面上永遠緊接在父區塊自己那一行之後，導致新區塊被子項目擋在後面。

在採取修正前，先研究了 Workflowy、Notion、Logseq、Outline 等大綱/筆記工具與其使用者討論（見下方 Sources），確認業界慣例的 Enter 行為：
- 游標在文字**結尾**：新增一個空白區塊在**後面**，原區塊文字與子項目不變（多數工具的最常見情境）。
- 游標在文字**最前面**：新增一個空白區塊在**前面**，原文字與子項目維持不變、只是位置往後挪一格；游標留在原文字上（Logseq 使用者論壇的功能請求明確描述了這個行為：<https://discuss.logseq.com/t/arrow-movements-left-to-previous-point-and-new-point-when-pressing-enter-at-first-character/120>）。
- 游標在文字**中間**：把游標後面的文字移到新插入（在後面）的區塊，原區塊保留游標前面的文字，兩者都是同一層級的區塊（Logseq issue 對這個情境有明確描述：<https://github.com/logseq/logseq/issues/8945>）。

依此設計 `splitAtCaret(textEl)`：以游標所在的 Range 為界，取得「游標前」與「游標後」兩段 DOM 內容（若目前有選取範圍而非單純游標，先呼叫 `range.deleteContents()` 清空選取範圍再切開，比照一般文字編輯器「輸入會取代選取範圍」的行為）。子項目一律留在**原本的區塊物件**上不移動——這代表若游標剛好在「有子項目的區塊」文字中間切開，兩半都會是同層級的區塊，但子項目仍跟著原區塊（現在文字變成游標前半段），可能造成子項目看起來夾在兩個新切出的區塊之間；這是為了保留最常見情境（游標在結尾/開頭）正確行為所做的取捨，中間切開且該區塊有子項目是相對少見的組合。

### 修正：只有一個子項目時 Backspace 沒反應
使用者回報：一個區塊如果是其父區塊「唯一的子項目」，把內容清空後按 Backspace 完全沒有反應，不會被刪除。

原因：`removeBlock` 原本有一個保護機制——「如果目前區塊所在的清單只剩 1 個項目，就不執行刪除」，目的是避免使用者把整份筆記的最後一個區塊也刪掉，導致畫面上沒有任何區塊可以繼續編輯（沒有游標可停靠的地方）。但這個保護被套用到**任何**清單，包括某個區塊的子項目清單——只要一個父區塊只有一個子項目，這個保護就會誤判成「不能刪」，即使刪掉之後父區塊仍然存在、游標可以正常移回父區塊。

修正：保護只保留給**頂層清單**（`list === blocks`），子項目清單允許刪到剩 0 個（父區塊就變成沒有子項目，這是正常狀態）。刪除後若子項目清單變空，游標移回其父區塊（原本的邏輯是移到前一個同層兄弟節點，清單變空時沒有兄弟節點可移，需另外處理）。

### 樹狀索引排序：資料夾優先於檔案
使用者詢問左側樹狀索引是否支援拖拉調整順序。討論後確認實際需求並非拖拉（拖拉排序需要引入一套「自訂順序」的儲存機制，與「檔案系統即單一事實來源、不額外存 metadata」的既有設計原則衝突，詳見上方設計決策），而是單純希望資料夾一律排在檔案前面。

修正方式：`noteapp/tree.py` 的 `build_tree` 掃描每一層目錄時，將資料夾與 `.md` 檔案分開累積成兩個清單，各自依名稱排序後，回傳「資料夾清單 + 檔案清單」，取代原本「不分型態、單純依檔名字母排序」的做法。前端 `tree.js` 沒有另外排序，單純依後端回傳的順序渲染，因此只需修改後端。

### 樹狀索引視覺調整：展開箭頭放大、資料夾筆記數徽章
- 展開/摺疊箭頭字級從 11px 放大 1.5 倍至 16.5px（連同容器寬度從 12px 調整為 18px，避免放大後被裁切）。
- 資料夾節點右側新增一個筆記數徽章：遞迴計算該資料夾（含所有子資料夾）底下的筆記總數，count 為 0 時不顯示徽章。此計算完全在前端 `tree.js` 進行（`countNotes(node)` 走訪 `node.children`），因為 `GET /api/tree` 回傳的樹本身已含完整的巢狀子節點資料，不需要後端額外計算或新增欄位。

### 樹狀索引拖曳搬移
使用 HTML5 原生拖放 API（`draggable`、`dragstart`/`dragover`/`drop` 事件），不引入額外的拖放函式庫：
- 每個節點（資料夾與筆記皆可）皆可拖曳，`dragstart` 時把該節點的路徑存進 `event.dataTransfer`。
- 只有資料夾節點接受放置（`dragover`/`drop`），放置時計算目標路徑（目標資料夾路徑 + 拖曳節點的檔名），呼叫既有的 `PATCH /api/nodes/<path>`（與右鍵選單「搬移」共用同一個 `performMove` 函式，兩者合併去重）。
- 拖到目前所在的父資料夾（等同原地不動）時，前端直接短路不送出請求，避免後端把它當成「目標已存在」的衝突錯誤。
- 拖曳中的節點套用半透明樣式，拖到有效的資料夾上方時該資料夾列會顯示高亮外框，提供視覺回饋。

新增後端防呆（`noteapp/tree.py` 的 `move_or_rename_node`）：若搬移目標路徑是來源資料夾自己的子路徑（把資料夾拖進自己的子資料夾），明確拋出 `NodeConflictError` 並給出清楚訊息，取代原本會讓 `shutil.move` 拋出未經處理例外的行為。這個防呆不只保護拖放操作，也同時保護既有的「搬移」文字輸入路徑。

### 拖曳搬回最外層（拖到樹狀索引空白處）
初版拖放只支援「拖到某個資料夾上」，沒有對應「拖到空白處＝搬回根目錄」的放置區，這是右鍵選單「搬移」（手動輸入路徑）原本就能做到、拖放做不到的落差之一。修正：在 `NotesTree.init()` 對整個樹狀容器（`#tree-root`）額外註冊 `dragover`/`drop`，接住所有「沒有落在特定資料夾列上」的放置，一律視為「搬回筆記根目錄」；同時讓資料夾列自己的 `dragover`/`drop` 呼叫 `event.stopPropagation()`，避免事件往上冒泡到容器層，導致同一次放置被兩層邏輯各處理一次。

**與「搬移」選單的比較（結論：拖放無法完全取代手動搬移）**：補上這個缺口後，拖放已能覆蓋「搬到某資料夾」「搬回根目錄」兩種最常見情境，但仍有兩項手動輸入路徑才能做到、拖放做不到的能力，因此兩者並存，不移除既有的「搬移」選單：
- **搬移時順便改名**：拖放固定保留原檔名（只換路徑），手動輸入路徑可以在同一步驟內把檔名也改掉（例如搬到 `archive/2024/新名字.md`）。
- **不需滑鼠也能操作**：HTML5 原生拖放需要滑鼠手勢，觸控裝置或鍵盤操作使用者無法拖放，仍需仰賴選單輸入路徑完成搬移。

### 複製原始碼按鈕
編輯區右上角新增「複製原始碼」按鈕，與「檢視原始碼」並排，不需先切換到原始碼模式即可一鍵複製整篇筆記目前的 Markdown 原始碼到剪貼簿。內容來源依目前檢視模式決定：區塊模式下呼叫 `NotesEditor.getMarkdownSource()`（從目前的區塊樹序列化），原始碼模式下直接讀取 `<textarea>` 目前的即時內容（可能包含尚未切回區塊模式、尚未存檔的編輯），確保複製到的一定是「畫面上看到的」內容。

複製優先使用 `navigator.clipboard.writeText`（需安全情境，`http://127.0.0.1` 被視為安全來源，可正常使用）；若瀏覽器不支援 Clipboard API（考量 Win7 上可能安裝較舊的瀏覽器），退回建立暫時的 `<textarea>` + `document.execCommand('copy')` 的傳統作法。複製成功後按鈕文字短暫變成「已複製！」，1.5 秒後恢復。

### 樹狀節點操作選單：移除右鍵，改為 hover 顯示「⋮」按鈕 + 浮動選單
原本樹狀節點的重新命名／搬移／刪除是透過右鍵（`contextmenu`）叫出一個置中的 Modal 選單。使用者參考聊天室列表常見的互動模式（滑鼠移到項目上時，右側浮現一個「⋮」按鈕，點擊後貼著該項目彈出一個小的浮動選單），要求改成同樣的模式，且明確表示右鍵這個入口不需要保留。

調整內容：
- 移除 `tree-node-row` 的 `contextmenu` 監聽；右鍵一個節點現在會顯示瀏覽器原生的右鍵選單（不再被攔截）。
- 每個節點列右側新增一個「⋮」按鈕，預設透明（`opacity: 0`），滑鼠移到該列上才顯示，與既有的區塊格式選單、字級選單使用同一種「hover 才顯示的觸發按鈕」設計語言保持一致。
- 點擊「⋮」會在該按鈕正下方彈出一個小的浮動選單（不是螢幕置中的 Modal），內容仍是重新命名／搬移／刪除三項，各自附一個小圖示；選單的顯示/關閉邏輯（同時只能開一個、點擊外部關閉）與區塊格式選單共用相同的實作模式，分別在 `tree.js` 與 `editor.js` 各自維護一份（兩者是不同模組，暫不合併抽象，避免過度提前設計）。
- 圖示為手繪的極簡線條 SVG（`stroke="currentColor"`，無填色），不引入外部圖示庫或 CDN 字型——符合本專案「不依賴外部資源」的既有原則，也避免任何圖示授權疑慮。
- `NotesModal.menu()`（原本用來顯示「重新命名／搬移／刪除」置中選單的通用函式）已無其他呼叫者，隨之移除，避免死程式碼。

新增「⋮」按鈕後，資料夾節點右側同時存在「筆記數徽章」與「⋮」按鈕兩個元素，原本各自佔用自己的版面空間，滑鼠移到列上時兩者會並排擠在一起。修正：把兩者包進同一個固定 22×22px 大小的容器（`.tree-node-trailing`），內部皆以 `position: absolute; top: 0; right: 0;` 錨定在同一個右上角座標，兩者互斥顯示（預設顯示筆記數，`.tree-node-row:hover` 時筆記數 `display: none`、「⋮」按鈕 `opacity` 變為 1），視覺上共用同一個插槽、不會同時出現、也不會有版面跳動。

### 修正：拖到樹狀索引下方空白處實際上沒有反應（游標顯示禁止圖示）
使用者實測回報：把節點拖到左側樹狀索引下方視覺上看起來空白的區域，游標顯示禁止（no-drop）圖示，放開後什麼事也沒發生——雖然先前已針對「拖曳搬回最外層」功能驗證過，但先前的驗證方式是直接對 `#tree-root` 這個 DOM 元素本身派發合成事件，沒有測試「使用者實際看到的空白區域，是否真的屬於 `#tree-root` 的可視範圍」。

實際排查發現：`#tree-root` 本身沒有任何高度相關的 CSS，只會撐到樹狀節點內容本身的高度，並不會延伸填滿 `#sidebar` 剩餘的垂直空間。畫面上看起來的「空白處」其實是 `#sidebar`（`#tree-root` 的父層）自己的背景，`#tree-root` 的 `dragover`/`drop` 監聽器根本接不到那個區域的事件——瀏覽器對「沒有註冊 drop 監聽、且沒有呼叫 `preventDefault()`」的區域，預設就是顯示禁止圖示、drop 不會觸發任何行為，恰好對應使用者描述的現象。

修正：讓 `#sidebar` 改為 `display: flex; flex-direction: column;`，並讓 `#tree-root` 設為 `flex: 1`，使其確實撐滿 `#sidebar` 扣除頂部 `#sidebar-header` 之後的剩餘空間（`#sidebar-header` 另外補上 `flex-shrink: 0` 避免筆記很多、内容擠壓時被壓縮）。修正後以 `document.elementFromPoint()` 在畫面下方視覺空白處取樣，確認該座標確實回傳 `#tree-root`（或其內部），並用該座標為基準派發 `dragover`/`drop` 合成事件（而非直接對 DOM 參照派發），驗證搬回最外層確實成功——這種「以視覺座標定位再派發事件」的驗證方式比先前「直接對元素參照派發」更貼近真實使用者操作，之後測試拖放相關功能應優先採用此方式。

### Backspace 於區塊文字最前面時併入上一個區塊
先前 `Backspace` 只處理「區塊文字已清空」這一種情況（`removeBlock`）；游標在非空文字最前面按 `Backspace` 時，因為每個區塊各自是獨立的 `contenteditable` 元素，瀏覽器預設行為在該元素起始位置無事可刪，實際上什麼也不會發生，不符合一般大綱編輯器（Workflowy/Notion/Logseq）「併入上一個區塊」的直覺。

新增 `isCaretAtStart(textEl)`：以 `Range` 量測游標所在位置到區塊起點之間是否有任何文字內容，取代單純比對 `range.startOffset === 0`（避免游標落在巢狀行內格式標籤內時誤判）。命中後呼叫 `mergeIntoPreviousBlock(block, textEl)`：取得依展開順序排列的上一個可視區塊（`adjacentVisibleBlockId(..., -1)`），將目前區塊的 Markdown 文字接在該區塊文字之後、移除目前區塊（原有子項目升級補位，作法與 `removeBlock` 一致），並將編輯焦點移至合併後文字中「原上一個區塊文字結尾」的交接處。若已是依展開順序排列的第一個區塊（找不到上一個可視區塊），則不做任何事，避免拋錯。

游標落點的計算：因為區塊內文字可能包含巢狀行內格式標籤（`<b>`、`<code>` 等），無法直接用單一文字節點的 offset 定位，因此另外實作 `focusBlockAtTextOffset(id, offset)`，以 `TreeWalker` 走訪目標區塊內所有文字節點、依純文字字數（不含標籤）累加找到對應的節點與位移，再設定 `Range`／`Selection`。已透過隔離測試伺服器以真實鍵盤事件（而非直接呼叫內部函式）驗證：合併結果、`Ctrl+Z` 復原、以及「已是第一個區塊」時的 no-op 均符合預期。

### 修正：在已清空的清單項目上不斷按 Enter 會無限新增空 bullet
使用者實測回報：對著一個內容已清空的清單項目（一般清單／編號清單／待辦清單）持續按 `Enter`，畫面會不斷往下新增空的清單項目，並附上與參考編輯器（Notion／Outline 等區塊編輯器）的對照截圖——那些工具在文字結尾按下 Enter 會先延續清單型態新增一個空項目（與本專案現有行為一致），但若使用者在那個仍是空的項目上「再按一次」Enter，工具會把該項目轉成不帶標記的一般段落並跳出清單，而不是繼續往下疊加空的清單項目。

原因：`splitAtCaret` 對「整個區塊文字本來就是空的」這種情況，`atStart` 與 `atEnd` 會同時為 `true`，原本的判斷式 `if (split.atStart && !split.atEnd)` 因此不成立、一律落到 `insertSiblingAfter(block, '')`，對清單型態區塊（`CONTINUABLE_TYPES` 內的型態）而言會延續同型態，等於每按一次 Enter 就多一個空 bullet，沒有終止條件。

修正：在 Enter 的處理最前面加入一個攔截分支——若目前區塊文字已清空（`textEl.textContent === ''`）且型態屬於 `CONTINUABLE_TYPES`，就直接把該區塊的 `type` 改成 `paragraph`（Python/JS 兩端序列化早已支援、原本用於一般純文字行的型態，畫面上不帶任何標記），焦點留在原區塊，不建立新區塊、也不呼叫 `splitAtCaret`。同時把 `insertSiblingAfter` 在「非延續」情境下新建區塊的預設型態，由原本寫死的 `list_item`（會生成新 bullet）改為 `paragraph`——否則使用者在轉換後的空段落上再按一次 Enter，又會因為這個預設值重新生出一個 bullet，形成「清單→段落→清單→段落…」的另一種無限增生。修正後，一般段落本身仍可無限按 Enter 新增空白段落（這是所有文件編輯器的常見、可接受行為，不會有視覺上的清單符號堆積），符合使用者提供的參考截圖行為。

已透過隔離測試伺服器以真實鍵盤事件驗證：非空清單項目按 Enter 延續清單型態（行為不變）→ 空清單項目再按 Enter 轉為無標記段落、不新增區塊 → 空段落再按 Enter 才新增新的空段落（無標記）。

### 修正：標題／段落區塊看起來像被多插入一個 tab
使用者比對真實筆記檔案（無任何前導空白的 `# 千萬`）與畫面渲染結果，發現標題文字比原始檔案「多縮進一段」，懷疑排版有問題。

排查發現：每一行區塊（`renderBlock`）無論型態，一律固定附加三個欄位在文字前面——調整格式鈕（20px）、摺疊箭頭（16px）、清單標記（16px，只有一般清單／編號清單／待辦清單會在裡面畫東西）。標題、引用、一般段落沒有標記內容，但 `renderMarker` 原本仍會回傳一個文字為空的 `<span class="block-bullet">`，CSS 對 `.block-bullet` 設有固定 `width:16px`，所以這個空白欄位照樣占用版面，讓沒有標記的區塊文字也被往右推了一段（約 22px，含欄位間距），視覺上就像多了一個 tab，即便原始 Markdown 完全沒有前導空白。

修正（先採取影響範圍較小的做法）：`renderMarker` 對非 `list_item`／`ordered_item` 型態直接回傳 `null`，`renderBlock` 只在 `renderMarker` 有回傳值時才把它加進 `row`，不再為空欄位保留寬度。調整格式鈕與摺疊箭頭這兩個所有型態共用的欄位維持原狀不動（不同型態之間的縮排差異只縮小到「少了清單標記欄位」的 22px，尚未做到與一般 Markdown 檢視器完全貼齊最左邊——那需要把調整格式鈕與摺疊箭頭改成絕對定位懸浮在文字外側，且子項目縮排目前只有 22px／層、不足以容納這兩顆按鈕的浮動欄位，屬於較大範圍的改動，先不做）。已用使用者的真實筆記複本＋隔離測試伺服器驗證：標題文字左邊界從 412px 減少為 390px，剛好少了原本清單標記欄位的 22px。

### 重新整理頁面後恢復先前開啟的筆記
使用者回報：點選一篇筆記後按重新整理，畫面會回到「請從左側選擇一篇筆記」的首頁狀態，之前選的筆記就不見了，希望重新整理後能留在原本開啟的筆記。

原因：`app.js` 原本完全沒有把「目前開啟哪篇筆記」這件事反映到瀏覽器可以感知的任何狀態（URL、localStorage 皆無），純粹是記憶體裡的 `currentNode` 變數，重新整理必然清空。

作法：選用 URL hash（例如 `#資料夾A/筆記.md`，每個路徑片段以 `encodeURIComponent` 編碼）而非 query string 或 localStorage，原因是 hash 完全不會送到伺服器，Flask 現有唯一的 `/` 路由不需要任何改動就能在帶著任意 hash 重新整理時正常回應同一份頁面；相較 localStorage，hash 這種作法還能讓網址本身就可以分享/加入書籤直達某篇筆記（雖然目前是純本機工具，暫時用不到分享，但不需要額外成本就能保留這個可能性）。

實作：`selectNode` 選取筆記時呼叫 `setHashForPath`，用 `history.replaceState` 而非直接指派 `location.hash`——避免每切換一篇筆記就多一筆瀏覽器歷史紀錄（否則使用者按「上一頁」會在筆記之間跳來跳去，而不是離開這個網站，不符合預期）。頁面載入時 `reloadTree()` 取得完整樹狀資料後，呼叫新增的 `restoreFromHash(tree)`：解析目前 URL hash 還原成路徑、以新增的 `findNodeByPath` 遞迴搜尋樹狀資料找出對應節點，找到且型態為筆記時，呼叫 `NotesTree.revealPath()`（新增，展開該路徑上所有祖先資料夾，否則筆記雖然選中了，但因為所在資料夾是收合的，畫面上會看不到左側樹狀索引反白在哪）再呼叫 `selectNode` 正常走一般選取流程。找不到對應節點（筆記已被刪除、或網址被手動改壞）時單純不做任何事，維持預設的空白畫面，不拋錯。另外在 `onNodeMoved`／`onNodeDeleted` 也同步更新／清除 hash，確保網址列不會殘留一個指向舊路徑或已刪除筆記的 hash。

已透過隔離測試伺服器＋真實瀏覽器導航（`navigate` 到含 hash 的網址，非單純 JS 內部呼叫）驗證：選取筆記後 hash 正確更新 → 重新整理／重新導覽到同網址後，資料夾自動展開、筆記正確重新載入且區塊內容一致 → 網址沒有 hash 時維持原本空白畫面 → hash 指向不存在的筆記時安全 no-op、不出錯。

### 表格區塊（第一階段：先求正確顯示，可編輯既有儲存格，暫不做新增/刪除列欄與插入表格）
使用者需求：筆記需要能編輯 Markdown 表格。目前完全沒有表格支援——`parse_markdown_to_blocks`／`markdown.js` 的 `parseMarkdownToBlocks` 對 `| ... |` 這種行沒有任何特殊判斷，逐行當成一般段落處理，畫面上顯示的是原始 pipe 語法文字而非真正的表格。

先研究了 Obsidian（本機 `.md` 檔案編輯器中最相近的參照對象）、Notion、以及本專案命名由來的 Outline（底層為 ProseMirror + `prosemirror-tables`）三者的表格 UX，三者收斂到同一套慣例：插入時選列數欄數 → 點擊儲存格直接編輯純文字（不支援儲存格內再放清單/標題等區塊）→ `Tab`/`Shift+Tab`、`Enter`/`↑`/`↓` 在儲存格間移動 → hover 列/欄邊界出現「+」快速新增、也可刪除整列/整欄。因為要把這整套（插入表格的列數/欄數選擇器、儲存格間鍵盤導覽、hover 新增/刪除列欄按鈕）一次做完範圍很大，與使用者討論後拆成兩階段：**第一階段只做「正確顯示既有表格＋可編輯既有儲存格文字」**，鍵盤導覽與新增/刪除列欄、插入新表格的選單留到下一階段。

資料模型：`Block`（Python）新增 `rows`（二維陣列，每列是儲存格文字字串陣列）與 `align`（每欄對齊設定：`'left'`/`'center'`/`'right'`/`None`，來自分隔列的 `:---`/`---:`/`:---:`）欄位；JS 端的 block 物件比照新增同名欄位。兩邊 `Block`/plain object 其餘型態不使用這兩個欄位時保持空陣列，不影響既有行為。

Parser（Python `parse_markdown_to_blocks` 與 JS `parseMarkdownToBlocks`）都從原本单純的逐行 `for`／`forEach` 迴圈，改成可以「向前多看一行」的索引式迴圈：只有當目前行符合 `| ... |` 格式、且**下一行**是合法的分隔列（每個儲存格都是 `:?-+:?` 的形式）時，才開始收集一個表格區塊，持續吃進後續同樣是 `| ... |` 格式的行，直到遇到空行或不符合表格格式的行為止；否則（沒有合法分隔列）該行仍照舊被當成一般段落，避免把使用者原本就想打的、剛好含有 `|` 字元的一般文字誤判成表格。

Serializer（Python `blocks_to_markdown` 與 JS `blocksToMarkdown`）新增表格分支：依 `align` 重新產生分隔列（沒有對齊設定的欄輸出 `---`），並把每一列的儲存格數補齊到該表格最長的那一列（不足的欄位補空字串），確保輸出永遠是欄數一致的合法 GFM 表格，即使儲存格被個別編輯到參差不齊也不會產生語法錯誤的表格。

編輯器渲染（`editor.js`）：新增 `renderTableBlock`，對 `type === 'table'` 的區塊整個改渲染成一個 `<table>`（表頭列用 `<th>`，其餘用 `<td>`），略過一般區塊共用的調整格式鈕／摺疊箭頭／清單標記（表格沒有子項目、也還沒有把自己納入格式選單的可轉換型態），每個儲存格都是獨立的 `contenteditable`，`input` 事件直接更新 `block.rows[r][c]` 並呼叫 `commitChange(false)`（不觸發整棵樹重新 render，跟一般文字區塊的 `handleInput` 行為一致，避免每打一個字就整個重繪、把游標位置弄丟）。儲存格文字比照一般區塊使用 `inlineMarkdownToHtml`/`htmlToInlineMarkdown` 顯示與讀回，所以粗體/斜體等行內格式在儲存格裡一樣能正確顯示與編輯。

因為表格區塊沒有走一般區塊共用的 `.block-text`/keydown 處理路徑，第一階段這些既有功能對錶格區塊是安全的無作用（no-op），不會出錯，但也還沒有支援：
- `ArrowUp`/`ArrowDown` 從相鄰區塊移動到表格：`focusBlock` 找不到表格內的 `.block-text`（表格用的是 `<td>`/`<th>`，不是 `.block-text`），會安全地什麼都不做，游標不會移進表格，也不會壞掉。
- `Backspace` 合併上一個區塊：`mergeIntoPreviousBlock` 特別加了守衛，若「上一個可視區塊」是表格，直接視為找不到上一個區塊（不合併）——否則原本合併邏輯會把目前區塊的文字寫進表格區塊的 `.text` 欄位，但表格渲染完全不使用 `.text`，會造成使用者的文字被無聲吞掉、找不到跑去哪了。
- 表格整個區塊本身目前沒有鍵盤或滑鼠刪除方式；要移除一個表格，暫時只能切到「檢視原始碼」手動刪掉對應的 Markdown 文字。

「插入新表格」在第一階段沒有專門的按鈕/選單，但因為 parser 已經認得表格語法、且原始碼模式與區塊模式雙向切換本來就會重新解析/序列化，使用者可以切到「檢視原始碼」直接貼上或手動輸入一個 Markdown 表格，切回區塊模式就會正確渲染成真正的表格——已用隔離測試伺服器實測這個路徑可行。

已用使用者提供的真實表格內容驗證：Python 端 `parse_markdown_to_blocks`/`blocks_to_markdown` 往返（round-trip）測試（新增於 `tests/test_markdown_blocks.py`，含基本解析、三種對齊標記、表格結束於空行或非表格行、沒有分隔列時退回一般段落、往返穩定性、序列化時補齊參差列數）全數通過，既有 30 個測試也維持全過（共 36 個）；並用隔離測試伺服器＋真實瀏覽器操作驗證：表格正確渲染成 `<table>`（含右/左/置中對齊、粗體儲存格）、點擊編輯儲存格文字後背景自動儲存回檔案內容正確、切到原始碼模式看到的 pipe 語法正確、在原始碼模式貼上一個全新表格切回區塊模式後正確渲染。

### 修正：標題／段落與清單項目的文字沒有對齊、窄表格右側留白
使用者用一份混合標題、清單、表格的真實內容實測後回報兩個現象：（1）標題跟旁邊清單項目的文字看起來沒對齊，「縮排不正常」；（2）內容較短的表格（如「年度支出」那個兩欄表）右側有一塊明顯的空白，跟其他內容的右邊界對不齊。

排查（1）的原因：這是先前「修正標題像多一個 tab」那次改動故意先擱置、當時就講明的取捨——當時只讓標題/表格/引用/段落不再保留清單標記（`.block-bullet`）那 22px 的欄位，但調整格式鈕（20px）與摺疊箭頭（16px）這兩個所有型態共用的欄位並沒有動，所以標題文字落在「欄位寬度 48px」的位置，清單項目文字則落在「48px + 22px 標記欄位 = 70px」的位置——兩者從「一起被推到 70px、彼此對齊」變成「一個在 48px、一個在 70px，彼此不對齊」，改完後反而更顯眼。

這次採用先前提過、當時評估為風險較高而暫緩的「方案 2」：把調整格式鈕與摺疊箭頭從 flex 版面裡的「保留欄位」改成 `position: absolute`（`.block-row` 加上 `position: relative` 作為定位基準），使其懸浮在文字欄位外側、不再佔用任何版面空間；清單標記（`.block-bullet`/`.block-checkbox`）維持原本在 flex 流程中的正常欄位。效果是：所有型態的文字現在統一從區塊自身最左邊（`left: 0`，即 row 本身的框線位置）開始，只有清單型態會因為前面多一個標記欄位而多縮進 22px——這正是一般 Markdown 檢視器的慣例（標題與段落貼齊最左邊，清單的縮排只來自標記本身），而不是先前「大家一起被往右推」的樣子。

先前評估「方案2」時，曾擔心巢狀子項目縮排只有 22px／層，不夠放調整格式鈕+摺疊箭頭合計約 48px 寬的浮動欄位，可能在深層巢狀時互相蓋到。這次改用 `position: absolute` 之後重新驗算：因為每一列的浮動控制項是相對於**該列自己**的框線定位（`left: -48px`／`-22px`），而不是相對於編輯區最外層的固定欄位，所以深度 d 的列，其浮動控制項的絕對水平位置會落在 `d × 22 - 48` px——隨著深度增加，這個值只會往「更靠右、更安全」的方向移動（不會变得更負、更容易被裁切），且不同深度的列本來就分別畫在不同的垂直位置，彼此之間本來就不會有水平方向的視覺重疊。因此不需要放寬 22px 的縮排步階，直接套用到所有深度都是安全的；先前判斷「巢狀時有風險」是評估過程中對「浮動位置是否隨深度固定」想岔了，這次搭配隔離測試伺服器對含巢狀子項目的內容實測，確認每一層的縮排、標記欄位、浮動控制項位置都符合預期。

排查（2）的原因：`.block-table` 沒有設定 `width`，`<table>` 預設依內容自動撐開寬度，內容較短的表格自然比旁邊的標題/段落窄，形成視覺上的落差。這其實是 GitHub／VSCode／Obsidian 等多數 Markdown 檢視器的共同慣例（表格預設不會被強制拉滿版面），嚴格來說不算錯，但使用者希望視覺上跟其他內容對齊，所以直接幫 `.block-table` 加上 `width: 100%`，讓表格一律撐滿到跟標題/段落文字同樣的右邊界，不論內容多短。

已用隔離測試伺服器＋真實瀏覽器（含一個有巢狀子項目、兩個表格、多種標題層級混合的測試筆記）驗證：所有標題與段落文字的左邊界統一落在區塊自身框線位置；清單/巢狀清單項目的文字統一比同一層的區塊框線多縮進 22px、且巢狀層級間的相對縮排量不變；兩個表格不論內容長短，右邊界都精準對齊到跟標題/段落文字相同的座標；調整格式鈕（含下拉選單點擊套用格式）與摺疊箭頭（點擊摺疊/展開子項目）在浮動定位後功能與可點擊性都正常，並確認瀏覽器主控台沒有任何錯誤。

### 表格區塊（第二階段：插入新表格、新增/刪除列與欄）
第一階段只做到「正確顯示既有表格＋編輯既有儲存格」，插入新表格只能靠切到「檢視原始碼」貼上/手打 pipe 語法。這次要補上「從介面新增表格、新增/刪除列與欄」，先簡短研究了幾個同類工具在「新增/刪除列欄」這個具體操作上的做法：Notion／Google Docs 是在欄列邊界 hover 顯示插入線與圓形按鈕，或欄位把手選單（插入左/右、刪除、複製），互動較豐富但需要額外的 hover 判斷、插入位置計算等版面邏輯；Obsidian／Typora 這類較輕量的表格編輯器則是「表格固定角落顯示一顆『+』」（右側加欄、下方加列），刪除則是每欄/列旁一顆小「×」，沒有拖曳、沒有插入到中間的功能。選擇跟進後者：結構簡單、不需要拖曳或欄位選單，也跟這個專案既有的「hover 出現一顆小按鈕」風格（樹狀節點的「⋮」、區塊的「Aa」）一致，本次評估後直接採用可實作。

**插入表格**：既有的「Aa」區塊格式選單（`FORMAT_OPTIONS`）新增一個「表格」選項；點擊後把目前區塊轉成一個 2×2 的表格（若原本有文字，保留到第一格 `rows[0][0]`，不會被無聲丟棄），焦點移到第一格。只在格式選單這一個既有入口新增選項，沒有另外做斜線指令或獨立的「插入區塊」按鈕。

**新增/刪除列欄**：`renderTableBlock` 重新設計表格結構——每一列前面多一個「角落欄」（表頭列該格空白，資料列該格放「刪除這一列」的「×」按鈕，rowIndex 0 的表頭本身不能被刪）；表頭列最後多一格「+」新增欄按鈕；`tbody` 最後多一列（`colspan` 撐滿所有欄）放「+ 新增列」按鈕。對應四個新函式：`addTableRow`／`removeTableRow`（`rowIndex <= 0` 時拒絕刪除表頭）／`addTableColumn`／`removeTableColumn`（只剩 1 欄時拒絕刪除，避免表格變成 0 欄）；四個都是修改 `block.rows`/`block.align` 後呼叫 `render()` + `commitChange(true)`，跟其他會改變區塊結構（非單純打字）的操作一致，會產生一筆可 `Ctrl+Z` 復原的歷史紀錄。

**鍵盤 Tab 導覽**：儲存格改成「外層 `<th>`/`<td>` 不可編輯、內層包一個 `<span class="block-table-cell-text" contenteditable>`」的結構，而不是讓 `<th>`/`<td>` 本身直接可編輯——原因是刪欄按鈕（「×」）需要放在同一個表頭儲存格裡，如果儲存格本身就是 contenteditable，這顆按鈕會被當成儲存格文字內容的一部分（`textContent` 會混進 `×`，使用者打字時也可能不小心選取/刪到它），拆成內層 span 之後按鈕跟可編輯文字互不影響。Tab／Shift+Tab 的 keydown 監聽器掛在這個內層 span 上：同一列往右/左移動；到達列尾/列首時跨到下/上一列；在最後一列最後一格按 Tab 會直接呼叫 `addTableRow` 新增一列並移入（比照試算表/多數表格編輯器的慣例）。新增 `focusTableCell(blockId, rowIndex, colIndex)` 依 `data-col` 屬性定位到指定儲存格的內層 span 並設定游標到文字結尾。

已用隔離測試伺服器驗證：一開始誤把刪欄按鈕直接放進 contenteditable 的 `<th>` 裡，實測發現儲存格文字被「第一項×」這種混入按鈕文字的方式污染——改成內層 span 結構後重測確認乾淨（`textContent` 不含按鈕文字，輸入事件只更新到 `block.rows` 對應位置）。功能驗證：從格式選單插入表格且保留原文字、新增列/新增欄、刪除列/刪除欄（含刪到剩 1 欄時的拒絕保護）、Tab 在同列/跨列前進、Shift+Tab 後退（含跨列到上一列最後一格）、在最後一格按 Tab 自動新增列並移入焦點——每一步都直接讀 `window.NotesEditor.getBlocks()` 核對記憶體中的資料結構，並確認背景自動存檔後 `.md` 檔案內容正確。

Ctrl+Z／Tab 這兩個鍵盤快捷鍵在這次測試環境裡透過自動化工具送出的真實按鍵一度沒有被頁面收到（懷疑是瀏覽器分頁焦點/合成鍵盤事件在該工具當下的限制，並非程式邏輯問題）；改用 `element.dispatchEvent(new KeyboardEvent(...))` 直接對已聚焦的儲存格觸發 `keydown` 驗證 Tab 導覽邏輯本身（這類測試屬於驗證「自己註冊的事件處理常式」，不像拖放事件那樣依賴瀏覽器原生的座標命中判定，用合成事件驗證是合理的）。Ctrl+Z 復原沒有另外針對表格重新測試，但新增/刪除列欄呼叫的是既有的 `commitChange(true)`，跟其他一般文字區塊的結構性操作（例如縮排、格式轉換）用的是同一支函式、同一套歷史紀錄機制，先前已在其他情境驗證過可正常復原。

已知限制：只能在表格「最後」新增列/欄，不能插入到中間；沒有拖曳調整欄寬；沒有整個表格區塊的刪除按鈕（要移除整個表格仍要切到「檢視原始碼」）。

### 表格儲存格內的 Ctrl+Z 改用 App 自己的復原機制（含二次修正：改成全域監聽）
上一階段刻意把 `Ctrl+Z`/`Ctrl+Shift+Z` 留給表格儲存格所在的 `contenteditable` 元素自己處理（沒有攔截），原因是當時只想先把新增/刪除列欄的功能做出來。使用者實測後回報：在表格儲存格內按 `Ctrl+Z` 感覺像是「只能復原一次」。

原因排查：因為沒有攔截，瀏覽器會用它自己對該 `contenteditable` 元素內建的復原堆疊處理——這跟 App 自己的 `history`/`historyIndex`（100 步、以整個區塊樹為單位）完全是兩套獨立機制。瀏覽器原生堆疊本身不一定只能復原一次，但任何一次結構性操作（新增/刪除列、新增/刪除欄）都會呼叫 `render()` 整個重新產生表格 DOM，把舊的 `contenteditable` 節點連同它自己的原生復原歷史一起丟棄、換成全新節點——所以只要使用者曾經新增/刪除過列欄，該儲存格的瀏覽器原生復原歷史就會被清空重來，體感上就像「常常只能復原一次」。

**第一版修正（後來發現不夠）**：直接讓表格儲存格的 `keydown` 監聽器在偵測到 `Ctrl+Z`／`Ctrl+Shift+Z`／`Ctrl+Y` 時呼叫既有的 `undo()`/`redo()`，跳過瀏覽器原生的 contenteditable 復原（比照一般區塊 `handleKeydown` 的判斷式）。

使用者實測後給出更完整的重現步驟（新增列輸入 456、再新增列輸入 789，然後連續按 `Ctrl+Z`）：第一次 `Ctrl+Z` 正確讓「789」文字消失，但**第二次 `Ctrl+Z` 完全沒反應**，跟預期的「789 那一列整個消失」不符。

根因排查：`undo()` 內部呼叫 `restoreSnapshot()`，會用 `container.innerHTML = ''` 整個重繪編輯區、換上全新的 DOM 節點，但重繪後沒有任何程式碼把焦點移回任何一個儲存格或區塊——這其實是這個專案在更早之前（Backspace 合併相鄰區塊那個功能）就已經記錄過、但當時判斷「範圍外」而沒有修的同一個根因：**復原一次之後畫面焦點會消失，若監聽器是掛在個別區塊/儲存格上，第二次按 `Ctrl+Z` 時已經沒有任何元素擁有焦點，事件自然發不到任何一個監聽器手上**，也就是「什麼事都沒發生」。第一版修正只是把這個既有根因原封不動地帶進了表格儲存格，並沒有解決它。

**第二版修正（實際採用）**：與其在每個可能取得焦點的元素上各自掛一份 `Ctrl+Z` 處理、且每次都要祈禱焦點還在，不如把 `Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y` 改成**只註冊一次的全域 `document` 監聽器**（在 `init()` 裡），不依賴目前焦點落在哪個特定元素上：
- 用 `container.hidden` 判斷目前是否在區塊模式（區塊模式才攔截；原始碼模式維持使用 `<textarea>` 原生復原，兩者本來就是分開的機制，README 已有說明）。
- 額外用 `document.activeElement` 判斷：只有在焦點是 `document.body`（代表沒有東西聚焦，例如剛復原完畫面重繪後）或焦點落在 `container` 內部時才攔截；若焦點落在別的地方（例如樹狀節點的重新命名/搬移彈出視窗的文字輸入框），就不攔截、讓那個輸入框自己的原生復原正常運作——這個排除是因為第一次接上全域監聽器時，範圍沒收斂好會連彈出視窗裡打字的 `Ctrl+Z` 都攔截掉，等於使用者在改筆記名稱時按 `Ctrl+Z` 想改掉打錯的字，卻被誤判成要復原筆記內容，因此額外測試補上了這個排除。
- 同時把一般區塊 `handleKeydown` 裡原本自己處理 `Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y` 的那段判斷式整段移除，以及表格儲存格第一版修正加的那段也整段移除——兩邊都不再各自處理，只保留這一個全域監聽器，避免同一次按鍵被兩個監聽器各自呼叫一次 `undo()`，變成一次按鍵復原兩步的重複觸發問題。

已用隔離測試伺服器完整重現使用者回報的操作序列（新增列輸入 456、等待超過 600ms 的合併視窗、再新增列輸入 789）並連續按 4 次 `Ctrl+Z`，確認結果與使用者原本預期的順序完全一致：「789」文字消失 → 789 那一列整個消失 → 「456」文字消失 → 456 那一列整個消失，回到操作前的原始狀態；再按 `Ctrl+Shift+Z` 確認可以正確往前一步。另外驗證：在重新命名彈出視窗的文字輸入框內按 `Ctrl+Z` 不會被攔截（`defaultPrevented` 為 `false`，走原生復原）；切到「檢視原始碼」模式時 `Ctrl+Z` 也不會被攔截（同樣走 textarea 原生復原）；一般區塊（標題）連續按兩次 `Ctrl+Z`（中途不重新點擊聚焦）也能正確連續復原兩步——確認這次修正同時把先前記錄過的「復原後焦點消失、下一次要先點回去才能再復原」這個既有已知限制一併解決掉了，不只是表格專屬的修正。瀏覽器主控台全程無錯誤，Python 測試 36 個維持全過。

### 編輯區內直接重新命名筆記＋顯示相對更新時間

### 插入圖片
使用者請我先研究「以現有介面來說要怎麼擴充插入圖片」，並問圖片該存在共用目錄還是各自目錄。研究後提出三個插入手勢（貼上、拖放、格式選單）與三種儲存位置（共用資料夾、每篇筆記各自附屬資料夾、跟 md 同目錄）的取捨；使用者確認：插入手勢與圖片獨立成一個區塊型態都照建議做，但儲存位置最後選「跟 md 檔同目錄，不建立額外資料夾」（比我原本建議的「每篇筆記各自 `.assets/` 資料夾」更簡單）；檔名衝突「後蓋前，使用者自行負責」；限制副檔名與 10MB 大小上限；後端 API 怎麼設計交給我決定。確認方向後，使用者接著想到兩個因「同目錄、不建立資料夾」才會發生的新問題：搬移筆記到別的資料夾時圖片不會跟著搬（參考會失效）、刪除筆記不會一併刪除同目錄圖片（可能被其他筆記共用，無法確定），並提出「未來要做：搬移/刪除有圖片時跳出確認提示（沒得選、只能繼續或取消）」，但明確表示**這次不用實作**，先記錄下來。

**資料模型**：`Block` 新增 `src` 欄位（Python／JS 兩邊比照 `rows`/`align` 的模式）。Parser 新增 `_IMAGE_RE`（`^!\[([^\]]*)\]\(([^)\s]+)\)$`），一整行**只有**一個 `![alt](檔名)`、沒有其他文字時才視為圖片區塊（避免段落文字中間夾雜的圖片語法被誤判，那種情況維持當作一般段落文字，這部分暫不支援行內圖片）；serializer 對應輸出 `![alt](src)`。

**儲存路徑設計**：關鍵決定是「.md 檔案裡存的內容」跟「瀏覽器顯示圖片用的網址」要分開處理，兩邊各自簡單：
- **持久化格式**：`block.src` 就是不含路徑的純檔名（例如 `photo.png`），Python／JS 的 parser／serializer 完全不用處理任何路徑運算，跟其他欄位（`text`、`rows`）對稱處理——這樣 `.md` 檔案本身維持可攜性，複製整個資料夾到別的地方，圖片連結依然有效，不會因為換了機器/路徑而失效。
- **顯示網址**：由前端負責組出可以載入的網址。`app.js` 在 `selectNode()` 呼叫 `NotesEditor.load(data.blocks, parentDirOf(node.path))` 多帶一個「目前筆記所在資料夾」的參數，`editor.js` 存成模組層級的 `imageBaseDir`；渲染圖片區塊時用 `window.NotesApi.fileUrl(imageBaseDir + '/' + block.src)` 組出 `/api/files/<路徑>` 這種可以直接 fetch 的網址。這個關聯只在瀏覽器執行期間存在，不會寫回 `.md` 檔案。

**後端**：新增 `POST /api/notes/<note_path>/images`（multipart 上傳）與 `GET /api/files/<path:rel_path>`（讀取任意檔案，沿用既有的 `resolve_safe_path` 做路徑安全檢查，用 Flask `send_file` 回傳）。上傳檔名處理**沒有**用 werkzeug 的 `secure_filename`——那個函式會把非 ASCII 字元（中文檔名）整個過濾掉或轉成底線，對這個中文為主的 App 不合適；改寫一個簡單的 `_safe_upload_filename`：只取 `os.path.basename()`（防止檔名帶路徑分隔符逃逸）、拒絕空字串/`.`/`..`/含 null byte，中文檔名可以完整保留。副檔名白名單 `{'.png','.jpg','.jpeg','.gif','.webp'}`、大小上限 `10 * 1024 * 1024`（讀取 `file.stream` 的 seek/tell 取得實際大小，不信任 `Content-Length` 表頭）。檔名衝突比照使用者要求，直接覆蓋、不做任何自動重新命名。

**前端插入流程**：三種手勢共用同一個 `onImageUpload(file)` callback（`init()` 時由 `app.js` 傳入，內部呼叫 `NotesApi.uploadImage(currentNode.path, file)`），editor.js 本身不知道目前是哪一篇筆記、也不直接碰 API，維持原本「泛用區塊樹編輯器」的角色分離：
- **貼上**：`container` 上掛一個 `paste` 監聽器（而非每個區塊各自掛），檢查 `clipboardData.items` 有沒有 `image/*` 類型；找到就用 `document.activeElement` 反查目前是哪個區塊（`findBlockTextAncestor`），上傳成功後呼叫 `insertImageBlockAfter(block, filename)`，在該區塊**之後**插入新的圖片區塊、原區塊文字不受影響（不是把目前區塊直接轉成圖片，因為貼上圖片時使用者通常還在打字，不是想把已經打的內容整個換掉）。
- **拖放**：同樣掛在 `container` 上，檢查 `dataTransfer.files`（外部檔案拖放用這個，跟樹狀索引內部搬移節點用的 `dataTransfer.setData('text/plain', path)` 是不同的資料管道，兩者不會互相干擾）；找到圖片檔案就上傳，成功後呼叫 `appendImageBlock(filename)`，固定加在筆記最後（沒有做「依放開座標找最近的區塊插入」這種精準定位，先求簡單）。
- **格式選單插入圖片**：`FORMAT_OPTIONS` 加一個「插入圖片」選項，但**不能**沿用其他選項「點了就直接把 `block.type` 設成目標型態」的既有邏輯——因為使用者可能在檔案選擇視窗按取消，這時不該已經把區塊型態改掉。改成點擊後呼叫 `promptInsertImage(block)`，動態建立一個 `<input type="file" accept="image/png,image/jpeg,image/gif,image/webp">` 並觸發 `.click()`，只有在 `change` 事件真的選到檔案、上傳也成功之後，才把 `block.type` 設為 `'image'`、`block.src` 設為回傳的檔名；並比照「轉成表格保留原文字到第一格」的既有慣例，把區塊原本的文字保留成圖片的 `alt`（`block.text`），不會被無聲丟棄。

**渲染與刪除**：圖片區塊跟表格區塊一樣，不透過一般區塊共用的 `renderBlock` 流程（沒有調整格式鈕、摺疊箭頭、清單標記），整個渲染成一個 `<img>`，hover 顯示右上角一顆「×」刪除按鈕，點擊呼叫既有的 `removeBlock(block._id)` + `commitChange(true)`——只移除筆記內容裡的這個區塊，不會連帶刪除磁碟上的圖片檔案（保留孤兒圖片，對應使用者提到但先不實作的「刪除時警告」需求）。

### 程式碼區塊
使用者在確認我有能力實作圍欄程式碼區塊（```` ``` ````）之後直接請我實作，沿用跟表格/圖片同一套模式（新增區塊型態、parser 辨識、serializer 輸出、格式選單插入）。

**資料模型**：`Block` 新增 `lang` 欄位（Python／JS 對稱處理，比照 `src`）。Parser 新增 `_FENCE_RE`（`^```(\w*)\s*$`，只比對去除頭尾空白後的整行），命中後**不逐行套用其他 Markdown 規則**、直接把後續每一行原封不動蒐集起來（不 `strip()`，保留縮排），直到遇到一行內容恰好是 ` ``` ` 為止（或碰到檔案結尾，視為未閉合圍欄，內容涵蓋到檔案結尾）；蒐集到的行以 `\n` join 存成 `text`，開頭圍欄後面的文字存成 `lang`。Serializer 輸出時利用一個小技巧：`` '```' + lang + '\n' + text + '\n```' `` 當成**單一一個字串**塞進要輸出的 `lines` 陣列（而非把 `text` 內部的每一行拆開個別 append），因為最終組字串是用 `'\n'.join(lines)`，一個陣列元素內部本來就可以包含自己的 `\n` 換行符，一樣能正確跟前後的其他行接起來，不需要額外處理。

**編輯器渲染**：跟表格/圖片一樣不走一般區塊共用的 `renderBlock` 流程（沒有調整格式鈕/摺疊箭頭/清單標記）。上方一個純文字 `<input>` 記錄語言標記（純粹存文字，不做語法高亮、不驗證是否為合法語言名稱），下方一個 `<textarea>` 放程式碼內容——**選用 `<textarea>` 而不是跟其他文字區塊一樣的 `contenteditable`**，原因是程式碼需要原樣保留縮排/換行，`contenteditable` 對 Enter 鍵在不同瀏覽器有不一致的 `<div>`/`<br>` 插入行為，反而更難保證空白字元被精準保留；`<textarea>` 原生就是為了多行純文字設計，這個 App 既有的「檢視原始碼」模式也是用同一個元件、已經驗證過可靠。`input` 事件即時同步 `block.text`／`block.lang`，並呼叫一個簡單的 `autoGrowTextarea`（`style.height='auto'` 再設回 `scrollHeight`）讓高度隨內容自動增高，不需要手動拖曳調整（仍保留 CSS `resize: vertical` 讓使用者可以自行覆寫高度）。

**刪除**：兩種方式——內容清空後按 `Backspace`（比照一般文字區塊清空後刪除的既有慣例）、或 hover 出現右上角「×」按鈕（不論內容是否清空都可以直接刪，比照表格/圖片區塊的做法），兩者都呼叫既有的 `removeBlock` + `commitChange(true)`，包含「不能刪掉筆記裡最後一個頂層區塊」這個既有的安全防呆也自動套用（沒有另外寫特殊邏輯，`removeBlock` 本來就是型態無關的）。

**復原機制／格式選單插入**：完全重用既有基礎設施，沒有新寫任何專屬邏輯——`Ctrl+Z` 全域監聽器只檢查焦點是否在 `container` 內，`<textarea>` 本來就是 `#block-editor`的子元素，直接就適用；格式選單新增「程式碼」選項，因為只需要 `text`（已存在，會自動帶過去）加一個 `lang: ''` 初始值，不像表格/圖片需要在轉換當下額外準備複雜的初始資料結構或先跳出檔案選擇視窗，所以不需要像 `image`/`table` 那樣特別攔截點擊事件，只需要多一個 `else if (opt.type === 'code_block')` 分支設定 `block.lang = block.lang || ''`、呼叫新增的 `focusCodeBlock()`把焦點移到 `<textarea>`（沿用 `focusTableCell`/`focusBlock` 的既有寫法風格）。

**刻意不做的**：`Tab` 鍵在程式碼區塊內沒有攔截（原生瀏覽器行為是把焦點移出，不會插入縮排字元或空白），沒有語法高亮，沒有把「輸入 ` ``` ` 自動轉換」這種打字捷徑（跟標題的 `# ` 自動轉換不同，程式碼區塊只能透過格式選單建立）——這些都是為了先求正確可用、範圍不擴大，之後有需要再加。

### 修正：插入圖片／程式碼區塊後沒有機制可以在下面繼續打字
使用者實測回報：插入圖片、或在程式碼區塊裡按 `Enter`，都沒辦法在下面新增一行——按 Enter 沒有反應。

排查發現這其實是兩個各自獨立、原因不同的問題：

**圖片**：`insertImageBlockAfter`／`appendImageBlock`／`promptInsertImage`（格式選單轉換）這三個插入路徑，原本上傳成功後只呼叫 `render(); commitChange(true);`，**完全沒有呼叫任何 focus 函式**。因為圖片區塊本身沒有 `.block-text`（不像其他區塊有可編輯的文字介面），畫面重繪後編輯焦點就直接消失、落在 `document.body` 上——不是「按 Enter 沒反應」，而是這時候根本沒有任何元素持有焦點，鍵盤事件無處可去，所以不管按什麼鍵都沒有用。

**程式碼區塊**：`<textarea>` 原生的 `Enter` 行為本來就只是「在文字內容裡插入一個換行字元」，這對於「正在寫多行程式碼」是正確、需要的行為（不應該一按 Enter 就跳出整個程式碼區塊，那樣反而沒辦法輸入真正的多行程式碼），所以並不是 bug，但也確實沒有提供「我打完程式碼了，想跳出去繼續寫筆記」的退出手段。

**修正**：兩者用同一個共用概念解決——新增 `NON_TEXT_TYPES = ['image', 'table', 'code_block']` 與共用函式 `ensureFollowingParagraph(list, afterIdx)`：檢查 `afterIdx` 後面那個區塊是否存在、且型態不在 `NON_TEXT_TYPES` 內（也就是有 `.block-text` 可編輯），有的話就直接回傳它的 id 重複利用（不憑空多插入一個空段落）；沒有的話（不存在，或緊接著的也是圖片/表格/程式碼這類不可輸入文字的區塊）就新插入一個空白 `paragraph` 並回傳它的 id。三個圖片插入路徑上傳成功後都呼叫這個函式取得要聚焦的區塊 id，再呼叫既有的 `focusBlock(id, false)`。

程式碼區塊則是在既有的 `Enter` 判斷式裡，比照這個專案已經用過的「連續兩次都是空的才觸發」規則（跟先前「清單項目清空後再按 Enter 才跳出清單」是同一種設計語言）：判斷游標是否在內容最後（`selectionStart === value.length`）且目前內容是空字串或已經以 `\n` 結尾（代表使用者剛按過一次 Enter、還沒在那個新行打任何字）——符合才觸發跳出：`preventDefault()`、把那個多餘的尾端空行去掉（`.replace(/\n$/, '')`）、呼叫同一個 `ensureFollowingParagraph` 移動焦點。不符合（例如最後一行還有內容）就放行，讓瀏覽器原生行為正常插入換行，維持多行程式碼的正常輸入體驗。

### 修正上一項修正：實際操作中仍然無法接續打字，改用渲染時的固定不變量

上一項修正（`ensureFollowingParagraph` + 三個圖片插入路徑的 `focusBlock` + 程式碼區塊雙按 `Enter` 跳出）在自動化測試裡完整跑過所有路徑都正確通過，但使用者實測回報依然沒辦法接著打字。沒有再花時間往鍵盤事件時機或 `focus()` 呼叫時機的方向繼續除錯（合成事件測試通過不代表真實瀏覽器裡的 focus/事件時機一定正確，兩者已知會有落差），改採使用者提出的方向：與其依賴「插入當下」的一次性程式化動作（可能因為某個時間點的 DOM 還沒繪製完成、或瀏覽器對 `focus()` 呼叫時機的處理跟預期不同而默默失敗），不如讓「使用者看到什麼、能不能點下去打字」直接由渲染結果保證，不牽涉任何時間點或事件觸發順序。

**做法**：`render()`（統一的重繪入口，不論是載入筆記、插入區塊、還是 undo/redo 復原，最終都會呼叫到它）開頭新增 `ensureTrailingParagraph()`：只看 `blocks` 陣列（僅頂層，不含巢狀清單）的最後一個區塊，型態若屬於 `NON_TEXT_TYPES`（圖片／表格／程式碼），就直接 `push` 一個空白 `paragraph`。這個檢查每次重繪都會重新做一次，所以不管什麼操作路徑導致「文件最底下變成非文字區塊」這個狀態成立，下一次重繪畫面上就一定會多一行空白、可點擊、可直接打字的段落——不需要精準呼叫某個 focus 函式、不需要使用者剛好在某個時間點按下某個鍵。

**存檔不能把這個輔助用的空白段落也存進去**：新增 `stripAutoTrailingParagraph(list)`，只有在「最後一個區塊是空白 `paragraph`（無文字、無子項目）**且**倒數第二個區塊型態屬於 `NON_TEXT_TYPES`」這個精確條件下才濾掉最後一個區塊——這個條件刻意設計成剛好是 `ensureTrailingParagraph` 會觸發新增動作的反向條件，所以只會濾掉「自動補上、使用者還沒碰過」的那一個，不會誤刪使用者自己特意留白的段落（例如使用者自己在兩個文字段落之間按 Enter 留一行空白，那種情況倒數第二個區塊不是非文字型態，不會被濾掉）。`snapshotBlocks()`（undo/redo 快照）與 `getBlocks()`／`getMarkdownSource()`（存檔/複製原始碼路徑共用的同一個函式）都先套用這層過濾，所以這個輔助段落完全不會出現在復原歷史或 `.md` 檔案裡；一旦使用者真的在裡面輸入了任何內容，這個過濾條件就不再成立，它就自然變成一個「正式」的段落，一併存檔。

跟任務 38 的關係：38 的機制（插入圖片時自動聚焦、程式碼區塊雙按 Enter 跳出）維持保留，兩者不衝突且處理的情境不同——38 處理的是「插入當下，緊接在該區塊後面補一個可編輯段落」，就算該區塊不在文件最底下（例如插在文件中間）也適用；這次新增的不變量則是不論任何操作路徑、任何時間點，只要「文件最底下是非文字區塊」這個狀態成立就一定成立的保底機制，兩者疊加使用。

### 表格／程式碼區塊在筆記最前面時，按上鍵插入空白段落

**做法**：新增共用函式 `insertParagraphBefore(block, list)`，在指定的清單裡、該區塊目前的位置插入一個空白 `paragraph`，重繪後**將編輯焦點移到新段落**（不是留在原區塊）——這裡刻意跟 `insertEmptySiblingBefore`（`Enter` 鍵在文字最前面觸發、焦點留在原區塊）的焦點行為不同，因為 `↑` 鍵本身的語意就是「游標往上移動」，使用者按下 `↑` 是預期游標真的往上走，而不是原地不動。

### 表格儲存格內以上下鍵在同一欄的相鄰列間移動

### 一般文字區塊按上下鍵移到相鄰的表格/程式碼區塊

診斷後發現根本原因很單純：一般文字區塊原本的 `↑`/`↓` 邏輯（`adjacentVisibleBlockId` 找出相鄰區塊 id，再呼叫 `focusBlock` 聚焦）本來就沒有排除表格/程式碼區塊——`adjacentVisibleBlockId` 是把 `blocks` 整棵樹攤平，不分型態，所以表格/程式碼區塊的 id 一樣會被當成合法的「上一個/下一個區塊」，因此 `e.preventDefault()` 確實有被呼叫（瀏覽器原生的游標移動被攔截掉了），但接下來的 `focusBlock(id, atEnd)` 只認得 `.block-text` 這個 class（一般段落/標題/清單/引用共用的可編輯元素），表格與程式碼區塊的 DOM 結構裡完全沒有這個 class，所以 `querySelector` 找不到、函式提早返回——使用者看到的就是「按了鍵，畫面完全沒反應」，但其實不是「什麼都沒發生」，而是「攔截了原生行為，但接手的動作找不到目標而失敗」。

**修正**：新增一個依區塊型態分派聚焦方式的函式 `focusBlockSmart(id, atEnd)`：`table` 型態呼叫 `focusTableCell`，固定進入第一欄，`atEnd` 決定是第一列還是最後一列（對應「往下進入」該進表頭列、「往上進入」該進最後一列的直覺）；`code_block` 型態呼叫 `focusCodeBlock`（順便把這個既有函式也加上 `atEnd` 參數，讓它除了原本唯一呼叫端固定用的「聚焦到結尾」，也能依需要聚焦到開頭）；其餘型態維持原本的 `focusBlock`。所有原本呼叫 `focusBlock` 但目標可能是任意型態區塊的地方（一般文字區塊的 `↑`/`↓`，以及前一項修正裡表格/程式碼區塊在邊界時「移到相鄰區塊」的三處呼叫）都換成 `focusBlockSmart`，後者額外涵蓋了「相鄰區塊本身又是表格或程式碼區塊」（例如兩個表格緊鄰）這種先前遺漏的情況。圖片區塊沒有可聚焦的文字介面，`focusBlockSmart` 對圖片會落到最後的 `focusBlock` 分支，維持既有的靜默不作為，跟先前對圖片區塊鍵盤操作的限制一致，不特別處理。

### 貼上多行內容自動拆解為區塊

使用者從外部複製一段含 `#` 標題、`-` 清單的多行內容貼到編輯區，結果整段黏在同一個區塊裡，跟其他區塊編輯器「貼上會自動格式化」的體驗不一致。

根本原因：既有的 `paste` 監聽器只處理剪貼簿裡的圖片檔案，純文字貼上完全沒有攔截，直接交給瀏覽器原生的 `contenteditable` 貼上行為接手。但這個編輯器的區塊模型是「每個區塊的 `.block-text` 對應單一行內容」，`Enter` 鍵換行是靠 JS 手動拆成新區塊物件（`splitAtCaret`/`insertBlockAfter` 之類的既有邏輯），並不是讓一個區塊的 DOM 節點裡自然存在多行文字。瀏覽器原生貼上多行文字時，只會在同一個 `.block-text` 節點裡插入換行字元或多個子元素，這些內容序列化回資料模型（`htmlToInlineMarkdown`）時沒有對應的「多區塊」概念可以承接，於是使用者看到的就是「所有東西擠在同一區塊裡」。

**做法**：與其重新設計一套貼上內容的解析規則，直接重用專案裡已經存在、且已被 `loadFromMarkdownSource`（切到「檢視原始碼」再切回、或整篇筆記載入時）驗證過的 `window.NotesMarkdown.parseMarkdownToBlocks`——這正是同一個編輯器信任的「Markdown 文字 → 區塊陣列」轉換規則，貼上的內容只要包含換行，就交給它解析，不另外維護第二套規則。`paste` 監聽器改成：先統一取出目前游標所在的區塊，圖片分支邏輯不變；文字分支則讀取 `clipboardData.getData('text/plain')`，只有內容包含換行字元時才攔截並解析（沒有換行就是最常見的「貼一個詞/一句話」情境，維持瀏覽器原生行為，不要沒事找事去攔截）。

解析出的區塊陣列插入位置比照專案裡其他「插入新區塊」的既有慣例（`insertParagraphBefore`、圖片/程式碼區塊插入後的行為）：如果目前游標所在區塊是空白的一般文字區塊（使用者剛新增筆記、還沒打字就先貼上這種最常見情境），直接整個取代掉這個空白佔位區塊，避免貼完後前面多一行沒用的空段落；如果目前區塊已經有內容，就插在它後面，不動原內容。貼完後編輯焦點移到解析出的最後一個區塊，沿用先前修正跨區塊上下鍵導航時新增的 `focusBlockSmart`（依目標區塊型態決定聚焦到文字結尾、表格最後一列、還是程式碼區塊結尾），維持整個編輯器一致的「插入後自動聚焦到可以繼續打字的地方」設計語言。

**刻意不做的**：只讀取 `clipboardData` 的 `text/plain`，不讀取 `text/html`——也就是說，來源如果是網頁或 Word 那種透過瀏覽器原生格式化（粗體、顏色、字級）呈現的內容，這些格式不會被保留，只有貼上的純文字內容本身剛好符合本專案支援的 Markdown 語法（`**粗體**`、`# 標題`、`- 清單` 等）才會被正確辨識成對應區塊。這個取捨符合專案一貫「範圍不擴大、先求正確可用」的原則——解析 `text/html` 需要另外處理任意來源網頁的雜亂標籤與樣式，複雜度遠高於重用既有的純文字 Markdown 解析器，且使用者這次回報的實際情境（複製的內容本身就是以 Markdown 慣例書寫的純文字）用純文字路徑就能完整解決。

已用隔離測試伺服器驗證（改用合成 `ClipboardEvent` 測試，因為這個自動化瀏覽器環境沒有剪貼簿讀寫權限）：用使用者提供的實際內容貼在新筆記的空白區塊上，正確解析出 18 個區塊（標題/清單/段落），空白佔位區塊被取代不殘留；貼在已有內容的區塊上正確保留原內容、新區塊接在後面；貼上後編輯焦點正確落在最後一個區塊；存檔後 `.md` 內容正確；單行純文字貼上確認放行原生行為；圖片貼上分支確認重構後沒有回歸。Python 測試 53 個維持通過（純前端修正，未變動 parser/serializer/後端）。

改用 `<img>` 標籤取代 `<svg>` 之後，唯一需要小心的地方是 `static/js/tree.js` 裡的 `ICON_NEW_FILE`——這個檔案是純 JS、沒有 Jinja 模板引擎可以用 `url_for` 產生正確的靜態檔案網址，所以圖片路徑用寫死的 `/static/img/new-note.png`，這剛好符合 Flask app 建立時沒有另外指定 `static_url_path`（預設就是 `/static`），跟 `templates/index.html` 用 `url_for` 產生的網址會是同一個結果，兩處寫法不同但指向同一份檔案，維持一致。

已用隔離測試伺服器驗證：兩個 PNG 皆可正常存取；圖示放大檢視確認畫質清晰、跟原圖一致；工具列與資料夾選單「新文件」的圖示皆正確顯示；建立資料夾/筆記等既有功能不受影響；主控台無錯誤。Python 測試 53 個維持通過（純前端修改）。

### 樹狀索引圖示改用同風格全彩圖示（無「+」）；「+」圖示去背；產生方式的技術取捨

**去背處理（新增資料夾/新增筆記這兩個含「+」的圖示）**：使用者接著要求把先前直接使用使用者原圖裁切縮放而來的 `new-folder.png`／`new-note.png`（背景是原圖攤平後的不透明白色）也去背。因為這兩張圖是使用者提供的既有素材、不是我自己畫的 SVG，沒辦法回頭用「畫的時候本來就不上背景色」的方式取巧，需要事後去背。採用 `PIL.ImageDraw.floodfill` 從圖片四個角落開始、以顏色相似度容許值（`thresh=25`）填成透明——這個做法只會清除跟邊界相連的白色背景區域，不會誤觸圖示內部本身偏淺色但沒有跟外部背景相連通的區塊（例如筆記圖示的淡藍白色紙張本體）。實際抽樣量測筆記圖示紙張本體的像素值（約 `(196,214,241)`）跟純白背景（`(254,254,254)`）的色差夠大（min 色版相差約 58），確認這個方法不會把紙張本體誤判成背景一併挖空——如果當初直接套用「離純白多遠就給多少透明度」這種簡單反推算式，紙張本體這麼淺的顏色會被算出接近全透明，等於把紙張圖案整個抹掉，所以改用「以邊界連通性為準」的 flood fill 而不是逐像素反推。

**尺寸**：樹狀索引圖示的顯示尺寸幾經調整（16px 起始 → 32px → 最終定案 24px），來源 PNG 統一輸出為 64×64，24px 顯示尺寸仍在原始解析度內、不會模糊，不需要因為尺寸調整重新產圖。

### 浮動工具列擴充：醒目提示、標題/引用轉換、清除格式；格式選單目前狀態提示

使用者提供一張 Outline（另一款成熟的區塊編輯器）的浮動工具列截圖，詢問 gigo 有哪些可優化的方向。比對後歸納出四項跟 gigo 現況有落差、且符合「單人、本機、克難」定位的優化：醒目提示、選取文字直接轉標題/引用、清除格式、目前狀態的視覺回饋；同時明確排除截圖裡的留言（comment）協作功能——那是多人協作場景的東西，跟 gigo「單人使用、不需要伺服器同步」的定位直接衝突，牽涉留言串資料模型、作者身份等，會大幅擴大範圍，不建議做，也沒有做。

**醒目提示重用既有基礎設施，幾乎零成本**：`toggleInlineWrap(tagName)` 這個函式本來就是「給定任意標籤名稱、包住或取消包住選取範圍」的通用實作（`code` 標籤已經在用），直接傳入 `'mark'` 就能用，不需要新寫包/拆邏輯。序列化同樣重用既有的 `INLINE_WRAP_TAGS`（`B`/`I`/`S` 都是「同一個字串包住頭尾」的通用處理）機制，只要加一行 `MARK: '=='` 就完成 HTML→Markdown 方向；反向的 Markdown→HTML 也只需要新增一行正規表示式取代。採用 `==文字==` 這個語法而非比照字級調整那樣內嵌原始 `<span>` HTML，是因為 `==...==` 是多數 Markdown 擴充方言（如 Obsidian）已經在用的慣例語法，比內嵌 HTML 更接近「看起來像 Markdown」，日後如果需要真的支援真標準 Markdown 檢視器，這個語法至少在語意上比較容易被讀者理解成「這是強調」，即使該檢視器不認得也不會顯示出突兀的原始標籤文字。Python 端完全不用改——`Block.text` 本來就是不解析行內語法的原始字串（既有的粗體、斜體、字級調整都是同樣道理），行內格式從頭到尾都是純前端的顯示/序列化細節。

**選取文字直接轉標題/引用**：新增 `convertBlockType(block, textEl, type, level)`，邏輯上跟既有 Aa 選單的區塊型態切換完全一樣（設定 `block.type`/`block.level`、重繪、聚焦、存檔），只是把觸發點從「區塊層級、需要先開啟下拉選單」搬到「文字選取層級、浮動工具列直接點擊」，讓使用者不需要中斷選取狀態去點開另一個選單。刻意保留區塊原有的行內格式化文字（`window.NotesMarkdown.htmlToInlineMarkdown(textEl)`）再套用新型態，避免轉換時遺失已經套用的粗體/醒目提示等格式。

**清除格式**：`clearInlineFormatting` 用瀏覽器原生的 `range.deleteContents()` + 插入純文字節點取代，而不是手動走訪 DOM 拆解每一種標籤——這樣即使選取範圍只覆蓋某個格式標籤的一部分（例如只選了一段粗體文字的後半段），瀏覽器原生的 range 操作本來就會正確處理「部分刪除、剩餘部分保留原標籤」這種情況，不需要自己重新實作這套邏輯。

**目前狀態的視覺回饋（浮動工具列 + Aa 選單）**：浮動工具列這邊，粗體/斜體/刪除線可以直接用瀏覽器原生的 `document.queryCommandState()` 查詢（這個 API 雖然老舊但仍受各主流瀏覽器支援，本來就是設計來回答「目前選取範圍是否已套用某個格式」這個問題），程式碼/醒目提示/連結則用既有的 `findAncestorTag` 往上找對應標籤——兩種手法都是重用既有能力，沒有另外維護一份「目前套用了哪些格式」的狀態。Aa 選單那邊更單純，`renderFormatMenu` 本來就拿得到 `block` 物件，直接比對 `opt.type`/`opt.level` 是否等於 `block.type`/`block.level` 即可，不需要額外查詢。

### 字級調整與標題轉換的視覺衝突；進一步移除字級調整功能

使用者對照剛新增的浮動工具列 H1/H2/H3 按鈕，追問「原來的 A 字級跟新的標題按鈕是否重疊」。實測驗證後確認這不是程式邏輯層面互相干擾（兩者是完全獨立、互不知道對方存在的機制），而是**視覺呈現上的衝突**：字級調整用行內 `<span style="font-size:Npx">` 包住選取文字，標題大小則是用 CSS 屬性選擇器 `[data-heading-level] { font-size }` 套在整個區塊的容器上——inline style 的優先權天生高於任何 CSS 選擇器，這是 CSS 規範本身的行為，不是這個專案的實作缺陷。所以「先對一段文字套用『小』(12px)，之後把整個區塊轉成 H1 (26px)」這個操作順序，會讓那段文字停留在 12px、明顯小於標題其餘文字，變成一個內部大小不一致的標題。這個組合方式透過既有的 Aa 選單其實本來就存在（Aa 選單一直都能把任何區塊轉成標題），只是這次新增的浮動工具列 H1/H2/H3 快速按鈕讓使用者更容易連續做出「選字套字級 → 選整段轉標題」這個順序，因而更容易踩到。

**第一階段修正**：轉換為標題時自動清除區塊內殘留的字級調整。實作上重用既有的 `SIZE_SPAN_RE` 正規表示式（`markdown.js` 裡原本就有，用來把字級調整的 HTML 轉回 Markdown 儲存格式），新增並匯出 `stripFontSizeMarkup(text)`，把 `<span style="font-size:...">內容</span>` 取代成單純的「內容」——只拆包裝、不動裡面的文字。`editor.js` 的兩個轉換路徑（新的浮動工具列 `convertBlockType`、既有 Aa 選單的區塊型態切換）都在目標型態是 `heading` 時呼叫這個函式；轉換成引用、清單等其他型態則不受影響，因為那些型態沒有固定的區塊層級字型大小、不會產生衝突。

**第二階段：使用者反思是否乾脆整個拿掉字級調整功能**。使用者接著提出一個更根本的疑問：「是否給了過多的設定字型大小的選擇，反而容易讓使用者困擾」，並主動提議「A 整個拿掉，剩下一般文字/H1/H2/H3 四種大小應該也夠用」。評估後同意這個方向：
- 標題已經完整涵蓋「讓文字變大」這個需求，而且是語意化的（真正的 Markdown 標題層級），不會像字級調整那樣只是視覺上的像素覆蓋、容易跟其他機制打架。
- 這次同一批加入的「醒目提示」功能，某種程度上補上了字級調整原本承擔的「段落內強調」需求（用顏色而非大小做強調）。
- 拿掉之後唯一會失去的能力，是「讓一小段文字縮小」——標題完全做不到這件事（標題只會讓文字更大更粗）。但這是相對少見的情境（附註、小字說明之類），跟這個專案一貫「先求正確可用、不擴大範圍」的克難精神一致，值得用「拿掉一個容易誤用/衝突的功能」換取整體介面更簡單。

**移除範圍與相容性**：只移除「建立新字級調整」的 UI 入口（`FONT_SIZE_OPTIONS`、`renderFontSizePicker`、`applyFontSize`、`findAncestorFontSizeSpan` 與浮動工具列裡的呼叫，以及對應的 `.inline-size-picker`／`.inline-size-dropdown` CSS）。`markdown.js` 對 `<span style="font-size:...">` 的解析／序列化，以及第一階段新增的 `stripFontSizeMarkup`，完全保留不動——這確保了任何在這次修改「之前」就已經存在、含有字級調整的舊筆記，仍然可以正常讀取、正常顯示，只是使用者往後無法再透過介面建立新的字級調整；而「轉換為標題時清除舊字級調整」這個修正邏輯依然有效，涵蓋的正是「舊資料 + 新的標題快速轉換」這個最容易出現衝突的組合。

已用隔離測試伺服器驗證：重現原始衝突（`getComputedStyle` 確認區塊 26px、內部 span 仍是 12px）、套用修正後確認字級標記已從資料清除；浮動工具列與 Aa 選單兩條轉標題路徑分別驗證；轉換為引用確認字級標記不受影響；移除「A」按鈕後確認浮動工具列不再顯示該按鈕、既有字級調整資料仍正常顯示、轉標題仍正確清除；主控台無錯誤。Python 測試 53 個維持通過（純前端修改，未變動後端與 parser/serializer）。

### 筆記內搜尋與取代（Ctrl+F）— 實作與修正

實作過程中對原規劃做了兩個修正：

**醒目提示標籤從 `<mark>` 改成 `<span>`**：原規劃打算用 `<mark class="search-match">` 做暫時性的搜尋醒目提示，實作時發現這會跟同一個 session 稍早新增的「醒目提示」行內格式功能直接衝突——`htmlToInlineMarkdown` 的序列化邏輯把任何 `<mark>` 標籤都當成使用者套用的醒目提示格式，會轉成 `==...==` 存檔。如果暫時性的搜尋標記在某個時間點被意外反推存檔（例如使用者在搜尋醒目提示還沒清除時就直接在區塊裡打字），會把「搜尋當下的視覺提示」誤存成「真正的醒目提示格式」，是不小的資料正確性風險。改用普通的 `<span class="search-match">`／`search-match-current`：一般 `<span>` 不在 `INLINE_WRAP_TAGS` 對應表裡，`htmlToInlineMarkdown` 對它完全透明（原樣返回內部文字，不加任何包裝符號），從根本排除這個風險，不需要額外寫「小心清除時機」這類防禦性程式碼。

**搜尋列的復原快捷鍵被既有判斷式擋住**：測試「全部取代」時發現，如果操作完成後焦點還停留在搜尋列自己的取代輸入框（搜尋列是附加在 `document.body` 下的獨立元素，不在 `container` 範圍內），按 `Ctrl+Z` 完全沒有反應——不是取代的邏輯寫錯，是既有「鍵盤事件只在 `container` 範圍內才處理」這個判斷式，把搜尋列的輸入框也擋在外面了（這個判斷式原本是設計來避免 `Ctrl+Z` 誤觸發在筆記重新命名輸入框之類的地方）。修正方式是幫這個判斷式加一個例外：焦點如果落在目前顯示中的搜尋列裡，也視為有效範圍。這個修正很小，但對「全部取代是單一復原步驟」這個原本就設計好的能力來說是必要的——沒有這個修正，使用者實際操作時會覺得「全部取代後復原不了」，即使底層的單步驟復原邏輯其實是對的。

### 筆記內搜尋與取代（Ctrl+F）— 規劃

使用者展示 Outline 的 `Ctrl+F` 搜尋列截圖，一起釐清這個功能的本質：搜尋（find）本身瀏覽器原生就有（在一般 DOM 網頁上按 `Ctrl+F` 就能找字、醒目提示），Outline 自己刻一套搜尋 UI 的真正目的是要做「取代」（replace／replace all）——這件事只有應用程式自己知道底層資料、能夠真的把畫面上的文字改掉，瀏覽器原生搜尋做不到。確認方向：往「取代」規劃，不只是「找」。

**範圍**：這是「在目前這篇筆記內」搜尋/取代，不是跨所有筆記的全文搜尋——後者本來就是這個專案明確排除的功能（需要建立索引、掃描整個筆記根目錄），範疇完全不同。「筆記內搜尋」只操作目前已經載入在編輯器裡的區塊資料，不需要索引。

**技術核心問題：畫面文字位置 ≠ 原始儲存字串位置**。這個編輯器的區塊文字是存成「夾雜 `**`、`` ` ``、`==` 等標記語法的 Markdown 字串」（`block.text`），但使用者搜尋/看到的是**畫面上已經轉換過的顯示文字**（例如 `**粗體**` 顯示成「粗體」）。如果直接在 `block.text` 這個原始字串上做字元位置的搜尋/取代，位置會跟畫面對不上。解法是比照這個編輯器裡粗體/斜體/清除格式等既有功能的做法——一律在**已經渲染出來的 DOM**（`.block-text` 的 `textContent`）上做搜尋與比對位置，取代時透過 DOM Range 做 `deleteContents()`／`insertNode()` 精確編輯，編輯完再用既有的 `htmlToInlineMarkdown(textEl)` 反推回 `block.text` 存檔——完全重用既有的「DOM 是即時真相、事後才反推存檔字串」這套模式，不需要另外處理位置對應問題。

**收合（collapsed）子項目仍要能被搜尋到**：確認 `.block-children.collapsed` 只是 `display:none`，DOM 節點本身仍然存在、`textContent` 仍讀得到，所以搜尋範圍可以直接透過 `container.querySelectorAll('.block-text')`（依 DOM 順序，天然涵蓋巢狀子項目）取得所有可搜尋的文字區塊，不需要另外走訪 `blocks` 資料結構；跳轉到一個位於收合區塊內的符合結果時，需要沿著父層鏈把 `_collapsed` 展開再捲動過去。

**v1 範圍刻意排除**：表格儲存格、程式碼區塊、圖片替代文字——這三種目前不計入搜尋範圍，作為已知限制文件化，之後有需要再擴充，避免這次範圍一次拉太大。

**取代全部（Replace All）的做法**：不能直接用 `textEl.textContent = 新文字` 整段覆蓋（那樣會把區塊裡其他既有的行內格式，例如中間穿插的粗體字，一併清空成純文字，是資料遺失的風險）。改成逐一比對到的符合結果，在同一個區塊內從**最後一個符合結果往前**依序用 DOM Range 編輯（因為從後往前處理時，還沒處理到的較前面符合結果的字元位置不會被後面的編輯影響，不需要重新計算位移），每個區塊處理完後只反推一次 `block.text`，全部區塊處理完才呼叫一次 `commitChange(true)`，讓「全部取代」在復原歷史裡是單一一步、一次 `Ctrl+Z` 就能整個復原。

**搜尋列的鍵盤事件**：搜尋列自己的輸入框（查詢、取代文字）附加在 `document.body` 下（比照既有的浮動工具列 `floatingToolbar` 做法），不在 `container` 範圍內，所以既有的「僅在 `container` 內才處理鍵盤事件」判斷不適用；`Enter`／`Esc` 改成直接掛在搜尋列自己的輸入框／容器上處理（`Enter` 跳下一個、`Shift+Enter` 跳上一個、`Esc` 關閉），`Ctrl+F` 則獨立於既有的「聚焦範圍」判斷之外——只要目前有筆記開啟（`!container.hidden`）就會攔截，不管當下游標實際在哪裡。

### 提示框／標註框（callout / notice）區塊

使用者展示 Outline 的「Info notice」區塊（帶圖示與淡色背景的提示框），詢問是否為 Markdown 原生語法——確認不是，這是編輯器自訂的擴充功能，比較常見的慣例是 GitHub Flavored Markdown 的 Alerts（`> [!NOTE]` 等）或 Obsidian 的 Callout（`> [!info]` 等），皆建立在引用語法之上加特殊標記。使用者當下要求先記下，之後透過 `AskUserQuestion` 確認兩個決策後正式實作（詳見任務 57）：語法採用 GFM Alerts（`> [!NOTE]`／`> [!TIP]`／`> [!IMPORTANT]`／`> [!WARNING]`／`> [!CAUTION]`）；建立後可透過區塊上的下拉選單隨時切換種類。

**解析設計：比照引用語法，多行內文比照程式碼區塊**。`> [!KIND]` 標記行本身也符合既有的引用行正規表示式（`^>\s?(.*)$`），所以解析順序上必須先比對「是否為提示框標記行」，比對成功才繼續往下吃連續的 `> ` 前綴行當作內文（直到空白行或下一個標記行為止），比對不到（例如 `> [!FOO]` 這種無法辨識的種類）才落回既有的引用解析——不需要額外寫 fallback 分支，純粹是解析順序的安排就能讓「無法辨識」自然退化成一般引用。多行內文使用跟程式碼區塊完全相同的「單一字串內嵌 `\n`」手法（`block.text` 直接存多行文字，序列化時逐行補上 `> ` 前綴），比起「每個引用行各自獨立成一個區塊」（既有引用語法的行為）更適合提示框這種通常需要完整一段說明文字的使用情境。

**渲染設計：重用 `.block-text`，不重新發明行內格式/搜尋支援**。提示框內文的 `contenteditable` 元素刻意保留既有的 `.block-text` class，讓既有的浮動工具列（粗體/斜體/醒目提示/連結等）、`htmlToInlineMarkdown`／`inlineMarkdownToHtml` 序列化、以及 `Ctrl+F` 搜尋/取代（`runSearch()` 本來就是抓 `.block-text` 做搜尋範圍）都不需要新增任何程式碼就自動適用在提示框內文上——同一個 class 命名换來大量功能免費重用，是這次實作沿用既有慣例（`renderBlock` 對 `code_block`/`image`/`table` 的提早分派模式）之外，另一個「盡量重用既有機制」的重點。唯一需要新增的是 `inlineMarkdownToHtml` 補上 `\n` → `<br>` 的轉換（`htmlToInlineMarkdown` 反方向的 `<br>` → `\n` 早就存在，只是先前沒有任何區塊會產生內嵌換行的文字，這次是第一個需要用到的案例）。

**Enter／Backspace 改用專屬邏輯，不套用一般區塊的 `handleKeydown`**：一般區塊的 `handleKeydown` 在按 `Enter` 時預設會把區塊「分割」成兩個區塊，這對提示框不適用（提示框的多行內文應該留在同一個區塊內）；因此提示框內文改綁一個獨立的 `keydown` 監聽器，`Enter` 一律呼叫 `document.execCommand('insertLineBreak')` 插入換行，`Backspace`（內容清空時）才刪除整個區塊——這與程式碼區塊的 `<textarea>` 各自有專屬鍵盤處理邏輯（不共用一般區塊的 `handleKeydown`）是同一個既有慣例。

**方向鍵跳出區塊刻意不做（v1 已知限制）**：表格與程式碼區塊先前有專門處理「游標在邊界時按方向鍵跳到相鄰區塊」（`focusBlockSmart`），提示框這次刻意不比照——內文通常較短、跳出需求較低，且已有「清空後 Backspace 刪除區塊」與「`NON_TEXT_TYPES` 讓提示框自動在筆記結尾補一個空段落」兩種既有的逃生路徑，足以應付大多數情境，避免這次範圍拉太大；日後若有實際需求再補。

### 修正：游標在連結（或其他行內格式）結尾按 Enter 會留下空殼標記

使用者回報：游標在一個連結的最後面時按 `Enter`，下一行會出現「沒有連結但相同的內容」。實際重現後發現使用者的描述跟真正的成因略有落差——不是「內容被複製」，而是「行內格式標記留下一個空殼」：下一行實際出現的是 `[](網址)`（空白籤文字、保留原網址），因為 `[^\]]+` 的渲染規則不吃空字串，畫面上會直接顯示原始的 `[](網址...)` 字樣，視覺上容易被誤認為「內容重複但沒有變成連結」。

**根本原因**：現有的「游標在文字中間按 Enter 分割區塊」機制（`splitAtCaret`）透過 `Range.cloneContents()` 分別複製游標前後兩段內容。當游標精確落在某個行內格式元素（`<a>`／`<b>`／`<code>` 等）文字節點的最後一個字元之後、且該元素是區塊裡最後的內容時：依 DOM Range 規格，「游標之後」這段範圍的起點容器是該文字節點本身，跟範圍終點所在的容器不同，因此不算是「已收合」的範圍——即使實際上兩點之間沒有任何字元。`cloneContents()` 對這種「起點卡在行內元素內部」的情形，會依規格複製一份該行內元素的祖先鏈結構（內含空字串）而非完全空的內容。這是瀏覽器 Range API 標準行為，本身沒有錯；真正的問題出在 `htmlToInlineMarkdown`（`static/js/markdown.js`）序列化這段「內文字為空的行內格式元素」時，沒有做防呆，直接照原本邏輯輸出 `[](網址)`、`****`、空的 `` `` ``、`====`、`~~~~` 等空殼標記。

**修正**：`htmlToInlineMarkdown` 對 `A`、`CODE`、`INLINE_WRAP_TAGS`（粗體/斜體/刪除線/醒目提示）與字級調整 `SPAN` 的包裝邏輯，統一改成「內文字為空時直接回傳空字串，不輸出任何包裝符號」。這是通用修正，不只修連結——同一套 `splitAtCaret` 機制被所有一般文字區塊共用，只要游標剛好落在任何行內格式的結尾邊界，都可能觸發同一種空殼標記問題，一次修正涵蓋所有情況，不需要在每個呼叫端（`splitAtCaret`、未來其他透過 Range 分割內容的功能）各自加防呆。

已用隔離測試伺服器驗證：以真實的 DOM Range 精確重現使用者回報的邊界情境（連結、粗體、行內程式碼、醒目提示、刪除線皆測試），確認修正後下一行是真正的空白區塊，不含任何殘留標記；額外驗證「游標在行內格式文字中間按 Enter」的既有正常情境不受影響（粗體文字中間切開，兩段仍分別正確保留粗體標記）；瀏覽器主控台無錯誤。Python 測試 62 個維持通過（純前端修正，未變動後端 parser/serializer）。

### 連結的開啟／編輯／移除（懸浮小卡片）

使用者回報連結目前沒有友善的開啟方式，提出的第一個想法是：剛開啟筆記、尚未開始編輯時，點連結直接開啟新分頁；一旦開始編輯，連結才改成目前的行為。

**先評估「依編輯狀態切換點擊行為」的可行性，結論是不建議**：技術上真正的困難點在於時機——瀏覽器在 `mousedown` 階段就會把游標移入 contenteditable，早於 `click` 事件觸發，所以「點連結時去檢查現在算不算開始編輯」這件事，必須在 `mousedown`（而非最直覺的 `click`）就做判斷並視情況 `preventDefault()`，否則判斷的當下瀏覽器其實已經把焦點移過去了；除了時機點的工程複雜度之外，「開始編輯」本身的定義也沒有明確答案（單純點擊任一區塊算不算開始編輯？如果你開了一個連結、回來筆記又點了另一個連結，第二個連結算不算「已經開始編輯」而不該再自動開啟？），這些屬於需要事先定義清楚的產品行為決策，不是單純的技術修正。評估後如實回報給使用者，使用者決定改採業界（Google Docs、多數 ProseMirror 系編輯器）常見的另一種模式，不採用「依編輯狀態切換」的方向。

**採用的設計：懸浮小卡片＋修飾鍵點擊**：純點擊連結永遠只定位游標（不會跳頁），維持「點哪裡都是安全地在編輯」這個貫穿整個編輯器的核心假設，不需要為連結另外開特例；改用兩種明確、不會跟一般編輯操作衝突的方式做開啟/編輯/移除：

- 滑鼠懸浮在連結上，或游標（收合的選取範圍）移進連結內，會浮出一張小卡片，顯示完整網址，並提供「開啟」「編輯」「移除」三個按鈕；卡片本身也能被滑鼠懸浮（移到卡片上不會被關閉），這樣使用者才有時間把滑鼠從連結移到卡片上點按鈕。定位與顯示/隱藏機制刻意比照既有的浮動工具列（`inline-toolbar`）與搜尋列（`search-bar`）——同樣 `position: fixed` 掛在 `document.body`、同樣用 `hidden` 屬性切換、同樣用 `getBoundingClientRect()` 計算位置——降低新概念的數量，維護起來跟既有的浮動 UI 是同一套心智模型。
- `Ctrl/Cmd+點擊` 直接開啟連結，不需要先叫出小卡片，這是大部分編輯器都有的標準捷徑，跟「一般點擊安全」完全不衝突（多一個修飾鍵才會觸發，不會誤觸）。

**編輯網址重用既有的輸入框元件**：「編輯」按鈕沒有另外設計一個內嵌可編輯輸入框，而是直接呼叫既有的 `window.NotesModal.prompt(message, defaultValue)`（跟建立連結、筆記改名共用同一個元件），只是這次把 `defaultValue` 帶入目前的網址，讓使用者能夠「修改」而非「從空白重新輸入」；確定後直接對現有的 `<a>` 元素 `setAttribute('href', url)`，不需要重新選取範圍或呼叫 `execCommand('createLink')`。這個決定省下了設計、實作、測試一個全新內嵌編輯 UI 的成本，且沿用的元件已經有既有的 Enter 確認／Esc 取消／自動選取全文（方便直接輸入新網址覆蓋）等既有行為，不需要重新做一遍。

**移除重用既有的 `unwrapElement`**：跟「清除格式」拆解 `<mark>`／`<code>` 等標籤是同一個輔助函式，把 `<a>` 標籤拆掉、保留內部文字，再 `normalize()` 合併文字節點——不需要另外寫一套移除連結的邏輯。

**顯示/隱藏的時機協調**：小卡片有三種可能觸發顯示的來源（滑鼠懸浮連結、滑鼠懸浮卡片本身、游標收合於連結內），也有多種可能觸發隱藏的來源（滑鼠移出連結且沒移到卡片上、游標移出連結、切換筆記、`Esc`、選取一段文字改由浮動工具列接手）。為了避免「滑鼠正要從連結移到卡片上的路途中卡片被關掉」，隱藏一律透過 250ms 的防抖計時器（`scheduleHideLinkCard`／`cancelHideLinkCard`）處理，而不是任何一個「離開」事件就立即隱藏；同時擴充既有的 `handleSelectionChange`（原本「選取範圍收合就隱藏浮動工具列」的分支），讓收合的游標多一個「是否落在連結內」的判斷，這條路徑原本就已經在追蹤選取狀態，直接擴充比另外新增一個平行的選取監聽器更省事，也不會有兩邊狀態互相打架的風險。

**修正：按住修飾鍵時缺乏視覺回饋、且小卡片仍會搶戲**：使用者實測 `Ctrl+點擊開啟` 後回報，操作本身有效，但過程會讓人混淆——按住 `Ctrl` 把游標移到連結上準備點擊時，編輯用的小卡片仍然照常浮現（跟使用者「準備跳頁」的意圖矛盾，卡片上的「編輯」「移除」在這個當下並不相關），滑鼠游標也還是文字輸入游標，沒有給使用者「這裡準備要開啟」的訊號。修正方式是追蹤 `Control`/`Meta` 鍵的按下/放開狀態（`linkOpenModifierActive` 旗標），按下時：(1) 在 `document.body` 加上一個 class，透過 CSS 讓連結顯示一般連結常見的指標游標（`cursor: pointer`），(2) 立即隱藏正在顯示的小卡片、且按住期間 SHALL NOT 再顯示小卡片。額外處理了一個容易被忽略的邊界：如果使用者按住 `Ctrl` 時切換到其他應用程式（例如 Alt+Tab），瀏覽器可能收不到對應的 `keyup` 事件，旗標會卡在「啟用」狀態回不去；用 `window` 的 `blur` 事件補上這個重置，確保視窗重新取得焦點後，連結的游標樣式與小卡片行為都能正確恢復正常。

**滑鼠路過型懸浮加上顯示延遲**：使用者評估後決定，滑鼠「路過型」懸浮連結（單純掃過文字、沒有要停留的意圖）要停留超過約 500 毫秒才觸發顯示小卡片，避免滑鼠移動路徑剛好經過連結時卡片一直閃現、造成干擾；而透過編輯游標（打字、方向鍵移動）進入連結，屬於使用者主動的編輯動作而非路過，維持立即顯示、不套用這個延遲。實作上新增一組跟既有「隱藏防抖」（`scheduleHideLinkCard`／`cancelHideLinkCard`，250ms）對稱的「顯示延遲」機制（`scheduleShowLinkCard`／`cancelShowLinkCard`，500ms），`mouseover` 改成排入延遲、`mouseout` 在延遲到期前移出就直接取消，不會事後才突然冒出來。

實作過程中發現並修正一個真實的邊界 bug：一開始圖方便，在既有的 `hideLinkCard()` 裡也一併呼叫了新的 `cancelShowLinkCard()`，用意是「隱藏卡片的同時，順便清掉任何還在等待中的顯示計時器」，覺得是個無害的防禦性清理。但實際測試「快速從連結 A 移到連結 B」時發現：使用者在 B 上停留超過 500 毫秒，卡片理應要顯示，結果卻完全沒出現。追查後發現：離開 A 時排入的「250ms 後隱藏」計時器，會在 B 的「500ms 後顯示」計時器到期之前先觸發——而這個較早觸發的 `hideLinkCard()` 呼叫，順手把 B 那個都還沒完成倒數的顯示計時器也取消掉了。兩個計時器（A 的隱藏、B 的顯示）本來互不相干，卻因為共用同一個「隱藏時清空顯示」的邏輯而互相干擾。修正方式是把 `cancelShowLinkCard()` 從 `hideLinkCard()` 移除：`showLinkCardForLink` 本身已經有「連結是否還在畫面上」（`container.contains`）與「是否按住開啟修飾鍵」兩層檢查，即使筆記切換或按住修飾鍵之後，有一個「過期」的顯示計時器之後才觸發，也會被這兩層既有檢查安全擋下，不需要在 `hideLinkCard()` 裡額外主動取消——移除這行既不影響原本想防禦的情境，也徹底解決了「不相干連結的計時器互相取消」這個問題。這是這次修改真正的難點：兩個獨立、看似互不相干的計時器（一個管隱藏、一個管顯示），因為共用了同一個「清理」函式而產生了非預期的耦合，且只有在「快速移動經過多個連結」這種特定操作順序下才會顯現，一般的「單一連結懸浮/移出」測試不會發現。

已用隔離測試伺服器驗證：滑鼠快速掠過連結（<500ms 移出）全程不顯示卡片；持續停留超過 500ms 正確顯示；快速從連結 A（停留 350ms 未到期）移到連結 B（停留超過 500ms）正確顯示 B 的卡片與網址；文字游標進入連結維持立即顯示、不受延遲影響；按住修飾鍵、`Esc`、切換筆記等既有情境重新測試皆不受影響；瀏覽器主控台無錯誤。Python 測試 62 個維持通過（純前端功能）。

**隱藏延遲統一改成 500ms**：小卡片的隱藏延遲（滑鼠移出連結或移出小卡片本身後、隔多久才真正隱藏）原本是 250ms，「移出後延遲、期間移回就取消」這個機制本身在任務 59.2 就已經實作完成；使用者實測後回報感覺不出這個延遲的存在，也不確定該怎麼測試這麼短的間隔，索性直接統一成跟顯示延遲一樣的 500ms（新增具名常數 `LINK_CARD_HIDE_DELAY_MS`），數值好記、好驗證，兩種延遲的長度是否需要不同本來就沒有特別的理由，統一後也更容易解釋給使用者理解（「滑鼠停留互動一律抓 0.5 秒」這個單一心智模型）。

### 非文字區塊上方的「插入空白段落」按鈕

使用者遇到的情境：貼上或建立兩個表格後，介面上找不到辦法在兩個表格之間插入一行空白——Markdown 表格語法的解析規則是「連續的 `|` 開頭行都算同一個表格的延續」，兩個表格中間如果沒有空白行分隔，儲存後重新載入時會被解析成同一個表格，資料結構被破壞（多一欄或多一列，不是使用者原本想要的兩個獨立表格）。要求先研究其他類似軟體怎麼處理「兩個非文字區塊相鄰、中間沒有游標可以按 Enter 加空行」這個情境。

**研究結論**：Notion／Outline／Google Docs 採用跟區塊型態完全無關的通用做法——滑鼠移到任兩個區塊的交界處，浮現一個「+」按鈕，點擊就在那個確切位置插入一個新的空白區塊，不管交界兩側是什麼型態。Obsidian 則因為底層本來就是原始 Markdown 文字，直接在原始碼裡該位置加空行即可；gigo 剛好也已經有「檢視原始碼」模式可以這樣手動處理，這是這個問題現有的替代方案（雖然不直覺，但確實存在）。

**決定縮小範圍，只做 4 種非文字區塊**：完整比照 Notion 的做法，會是在所有區塊型態（包含一般文字、標題、清單）上都加這個「+」按鈕；評估後決定縮小範圍，只加在表格／圖片／程式碼區塊／提示框這 4 種「非文字」區塊上——理由是一般文字類型的區塊本來就能直接把游標移到該處按 `Enter` 插入空白行，這個「+」按鈕對它們來說是重複的能力，不縮小範圍也不會多做什麼事，純粹是多餘的介面元素；只有這 4 種型態才是「真的沒有其他方式可以在它前面加空行」的情況，縮小範圍後改動的檔案/渲染函式數量也比全域版本少。

**核心邏輯早就存在，只補一個入口**：實作前檢查發現，`insertParagraphBefore(block, list)`——「在指定區塊前插入一個空白段落並將編輯焦點移過去」——這個函式已經存在，只是目前只有一個呼叫入口：「表格/程式碼區塊位於文件最前面時按上鍵」。新增的「+」按鈕純粹是幫這個既有函式多開一個入口，不需要重新設計或重寫任何插入邏輯，把原本評估時預期的工作量（比照連結懸浮小卡片的規模）大幅降低。

**用純 CSS `:hover` 取代 JS 追蹤滑鼠位置**：比照既有的 `.block-format-trigger`／`.block-collapse-toggle`「預設透明、`:hover` 才顯示」的慣例，「+」按鈕直接是該區塊 `.block-row` 的子元素、絕對定位在區塊上方，用 CSS `:hover` 控制顯示/隱藏，不需要像連結懸浮小卡片那樣額外追蹤滑鼠位置、計算交界處座標——因為插入點永遠固定在「這個區塊的正上方」，不是一個會隨滑鼠位置浮動的位置，天生就適合用最簡單的 CSS 方案處理。

**測試方法上的教訓**：驗證這個功能時，合成的 `dispatchEvent(new MouseEvent('mouseover', ...))` 沒辦法讓 CSS 的 `:hover` 偽類實際生效（`:hover` 完全由瀏覽器根據真實滑鼠位置決定，跟 JS 事件監聽器是否被觸發是兩件事）；連結懸浮小卡片能用合成事件測試成功，是因為那個功能的顯示/隱藏完全由 JS 事件監聽器邏輯控制（監聽 `mouseover`/`mouseout` 後手動切換 `hidden`），而這次的「+」按鈕是單純交給 CSS `:hover` 處理，兩者測試方式不能混用；改用 `computer` 工具的真實滑鼠移動（`hover` 動作）才能正確觸發 `:hover` 狀態驗證。

**驗證時發現的既有限制（非本次引入，但直接影響）**：測試「點擊+按鈕後兩個表格中間真的有空白行、且這段 Markdown 重新解析後確實是兩個獨立表格」時，順藤摸瓜發現 `parse_markdown_to_blocks` 遇到空白行只會重置清單巢狀狀態並跳過，SHALL NOT 把空白行還原成一個空白段落區塊。也就是說「+」按鈕插入的空白段落，存檔那一刻確實會在檔案裡留下一行真正的空白行（成功阻止兩個表格被解析成一個），但只要之後切換筆記再切回來（觸發重新載入），這個空白段落區塊本身就會消失（因為空白行不會變回區塊）——兩個表格畫面上會變回直接相鄰、沒有間距，雖然本質上仍是兩個獨立的表格區塊、不會馬上重新合併。真正的風險在於：如果重新載入後又做了其他編輯觸發自動存檔，這次存檔會用「已經沒有空白段落」的記憶體狀態覆寫檔案，這時空白行才會真正從檔案消失，下次再重新載入就會讓兩個表格重新合併回一個。這是既有 parser 對空白行處理方式所致的深層限制，修正它需要改動空白行的解析邏輯（`list_stack = []` 那一段），影響範圍涵蓋所有既有的「用空白行結束清單巢狀」情境，需要另外評估，本次先不修，只記錄下來讓使用者知道這個功能在特定操作順序下仍可能復發。

已用隔離測試伺服器驗證：4 種區塊型態的「+」按鈕皆能正確懸浮顯示（用真實滑鼠移動觸發）並插入空白段落、聚焦正確；針對「兩個表格相鄰」的原始情境，直接建構兩個獨立表格區塊（略過 Markdown 解析，因為兩個表格中間沒空白行本來就會被解析成一個——這正是問題本身）並點擊插入，確認序列化結果真的有空白行、且用 Python 驗證這段 Markdown 重新解析後仍是兩個獨立表格；`Ctrl+Z` 確認可完整復原；既有的「表格/程式碼區塊在文件最前面按上鍵插入空白段落」路徑重新測試不受影響；瀏覽器主控台無錯誤。Python 測試 62 個維持通過（純前端功能，未變動後端 parser/serializer）。

### 修正：兩個表格之間即使有空白行，切到原始碼再切回來仍會合併

使用者實測後回報一個比任務 60.6 記錄的還嚴重的問題：即使原始檔案裡兩個表格之間確實有一行空白，只要點「檢視原始碼」再切回「區塊編輯」，兩個表格還是會被合併成一個，且第一個表格的欄位數會被自動補齊到跟第二個一樣多（資料結構被破壞，不是單純外觀問題）。

**根本原因，跟 60.6 是同一個病灶但更嚴重**：追查後發現，問題不在「空白行不會還原成區塊」這件事本身（那個確實只影響外觀），而是在序列化這一步就已經先出錯了——`blocks_to_markdown`（Python）與 `blocksToMarkdown`（JS）在把兩個緊鄰的表格區塊轉回 Markdown 文字時，兩個表格中間完全沒有插入任何分隔行。這代表：只要記憶體裡兩個表格區塊是彼此緊鄰的（不管中間有沒有一個空白段落物件撐著），只要呼叫這個序列化函式（存檔時、或「檢視原始碼」要顯示文字時呼叫的正是同一個 `getMarkdownSource()`），空白分隔就會直接消失在輸出的文字裡。「檢視原始碼」模式看到的文字，本身就已經是這個有問題的序列化結果；切回區塊編輯時，重新解析的正是這段已經沒有空白行的文字，兩個表格自然就被解析成同一個——不需要「額外做一次編輯再存檔」這種多一步的觸發條件，單純「切到原始碼看一下、再切回來」就能重現，比 60.6 原本估計的還更容易踩到。

**修正**：讓序列化邏輯自己負責維護這個不變量，不依賴中間是否存在一個空白段落物件——`emit` 迴圈裡，每輸出完一個區塊之後，檢查「目前區塊是表格、且下一個相鄰的區塊也是表格」，是的話主動補一行空白。這樣不管記憶體裡兩個表格中間有沒有一個空白段落區塊撐著，序列化出來的 Markdown 一定會有分隔，徹底消除了「表格與表格之間的分隔會不會存活」這個不確定性。只針對表格→表格這一種組合處理：這是唯一真正有解析歧義的組合（連續的 `|` 開頭行本來就會被表格解析邏輯貪婪地當作同一個表格的後續資料列）；圖片（單行獨立解析）、程式碼區塊（圍欄起訖明確）、引用/提示框（各自有獨立於空白行之外的中斷條件，提示框甚至在任務 57 就已經特別處理「遇到下一個標記行就停止」）等其他組合本身不會被誤合併，不需要也不應該加上同樣的處理，避免產生不必要的多餘空白行。

**這個修正讓任務 60.6 記錄的風險大幅縮小**：60.6 原本描述的風險是「空白段落區塊在重新載入後消失，如果之後又觸發一次存檔，可能讓表格重新合併」——這個修正後，序列化本身已經無條件保證表格與表格之間一定有分隔，不再需要仰賴那個空白段落物件是否還存在，所以「表格被誤合併」這個資料完整性風險已經解決；唯一還留著的是外觀層面的影響——如果那個空白段落區塊沒有存活下來，畫面上兩個表格看起來會直接相鄰、沒有視覺間距，但這只是外觀，不會導致資料被破壞。

已用隔離測試伺服器驗證：重現使用者回報的確切情境（載入兩個獨立表格 → 呼叫 `getMarkdownSource()` 確認有空白行 → 呼叫 `loadFromMarkdownSource()` 確認仍是兩個獨立表格、欄位數正確），並額外透過真實的「檢視原始碼」/「切換為區塊編輯」按鈕完整走一次相同流程確認結果一致；後端 API 直接寫入兩個相鄰表格，確認存檔後檔案內容真的有空白行、`GET` 重新讀取確認仍是兩個獨立表格；瀏覽器主控台無錯誤。Python 測試 65 個（62 個既有＋3 個新增）全數通過。

### 修正：兩個非文字區塊直接相鄰時，插入按鈕跟前一個區塊的操作按鈕重疊

任務 61 解決了「兩個表格會不會被誤合併」這個資料完整性問題之後，使用者接著回報：修正後還是不知道怎麼在兩個表格之間插入新內容。檢查後發現任務 60 做的「+」按鈕本身邏輯完全正常（`showLinkCardForLink`... 不，是 `createInsertBeforeButton` 的點擊處理邏輯、CSS `:hover` 規則都對），問題出在**版面位置**：`.block-insert-before-btn` 用 `top: -11px` 把自己往上偏移到區塊上方，這個假設隱含了「區塊上方一定有一些留白空間」——但表格/圖片/程式碼區塊/提示框各自的 CSS `padding` 只是區塊自己方框「內部」的留白，兩個相鄰區塊的方框之間可以是完全零間距地相接（前一個方框的下緣正好等於後一個方框的上緣，這正是這個功能原本最主要的使用情境：兩個表格直接相鄰）；這時候按鈕的負向偏移量，實際落點還是在**前一個區塊自己的方框範圍內**，跟前一個表格「新增列」這類既有的操作按鈕重疊、被埋沒，使用者自然找不到也點不到。

**修正**：把 `padding`（方框內部留白）換成 `margin-top`（方框外部留白）——`margin` 才會在兩個相鄰方框之間真正創造間距，這是兩者的關鍵差異。幫這 4 種區塊各加上 `margin-top: 14px`，按鈕原本的 `top: -11px` 不需要調整，因為現在這個負偏移量會落在新增的外部留白區域裡，不再誤闖前一個區塊的地盤。

**這次的教訓**：驗證一個「懸浮才出現的按鈕」，只確認「點擊處理邏輯正確」跟「CSS 有 `:hover` 規則」是不夠的——這兩者都對，功能本身也「能用」，但實際上完全不可用，因為在最該用到它的那個情境（零間距相鄰）下，按鈕被埋沒到根本看不到、點不到。這種版面佈局層面的問題，純粹的邏輯測試/程式碼閱讀不會發現，必須實際量測元素的渲染座標（`getBoundingClientRect()`）並跟周邊既有元素的座標比對，才抓得到。

已用隔離測試伺服器驗證：重現「兩個表格零間距相鄰」情境，量測修正後兩表格方框間有 14px 真實間距、插入按鈕不再跟前一個表格的「新增列」按鈕重疊；用 `computer` 工具的真實滑鼠移動＋點擊（非合成事件）完整走一次「懸浮顯示→點擊→插入並聚焦」流程確認可正常操作；檢查「一般文字接表格」「文件最前面是表格」等既有情境的間距沒有變得不合理；瀏覽器主控台無錯誤。Python 測試 65 個維持通過（純前端樣式調整）。

**改成條件式間距**：使用者接著回饋，62.3 無條件幫這 4 種區塊都加上 `margin-top: 14px` 的做法，在最常見的情境（一般文字接表格、文件最前面就是表格）下也會多出這段間距——這些常見情境原本的 `padding` 就已經有足夠空間讓插入按鈕安身，額外的 `margin` 純粹是多餘的視覺空白。真正需要這段緩衝空間的，只有「前一個區塊也是表格/圖片/程式碼區塊/提示框」這種特定組合（真的會零間距相鄰的情況）。改成條件式：新增 `blockFollowsNonTextSibling(block)`，透過 `findParentList` 找到區塊所在的清單，檢查緊鄰的前一個區塊是否也屬於 `NON_TEXT_TYPES`；把無條件的 `margin-top` 從 4 個區塊的基礎樣式移除，改成一個獨立的 `.block-row-gap-above` class，只有在 `blockFollowsNonTextSibling` 回傳真時才加上這個 class。這樣一般情境完全不受影響（間距跟這次改動之前一樣），只有兩個非文字區塊真的緊鄰時才會多出緩衝間距——把「解決按鈕被埋沒」跟「不要影響其他情境的版面」這兩個各自獨立的需求，用同一個判斷式同時滿足。

### 修正：插入按鈕的懸浮觸發範圍不包含它自己所在的視覺空隙

使用者拿實際畫面截圖回報：兩個表格之間確實已經有間距了，但依然找不到插入內容的方式。用截圖重建同樣的版面後，定位到真正的問題，跟任務 62 修的是同一類「版面幾何」問題，但這次更微妙：`.block-insert-before-btn` 的顯示規則是「懸浮在區塊本體（`.block-row`）上才顯示」，可是按鈕本身視覺上被放在 `margin-top` 撐出來的那段空隙裡——而這段空隙本身，在 CSS 裡不屬於任何區塊自己的方框（`margin` 是方框外部，不算在 hit-test 範圍內）。也就是說，使用者最直覺的操作「把滑鼠移到兩個表格中間、看起來空白的地方」，其實沒有命中任何會觸發顯示的元素；要看到按鈕，必須先移到某一個表格「本體」上（例如表格的儲存格），這個操作路徑完全不直覺，跟使用者的直覺（滑鼠移到那段空白處）正好相反。

**雙重修正**：
1. **讓視覺空隙本身變成可以觸發的範圍**：`createInsertBeforeButton` 不再直接回傳一個小圓形按鈕，改為回傳一個橫跨區塊整個寬度、高度覆蓋那段視覺空隙的 `.block-insert-zone`（本身是一個 `<button>`），小圓形的「+」變成裡面純裝飾用的 `<span>`；`.block-insert-zone` 用 `position:absolute; top:-14px; left:0; width:100%; height:20px;` 精確覆蓋那段空隙，讓「懸浮在視覺空隙的任何位置」都能命中這個全寬的觸發區域，不需要使用者精準對到那個 20px 寬的小圓形。
2. **不依賴懸浮的保底措施**：把按鈕的預設 `opacity` 從 `0`（純懸浮才顯示）改成 `0.35`（淡化但常駐可見，懸浮時提升到 `1`）。即使懸浮觸發本身在某些情境（例如觸控裝置、或使用者操作習慣不同）下不夠可靠，使用者仍然能直接「看到」這個按鈕的存在，不需要先猜到要去懸浮才能發現它——這是從根本解決「不知道有這個功能存在」的問題，比只修觸發範圍更保險。

**測試工具本身的限制**：驗證這次修正時發現，這次任務所用的瀏覽器自動化工具的 `hover`/`click` 動作，在跨工具呼叫之間無法穩定重現真實使用者的 `:hover` 狀態——即使用 `elementFromPoint()` 確認滑鼠座標確實對準了目標元素，隔一個工具呼叫再查詢 `element.matches(':hover')` 卻經常回報 `false`。這是這個自動化環境本身的已知限制，不是產品程式碼的問題；改用直接呼叫 `.click()` 觸發原生點擊邏輯（不依賴 `:hover` 狀態，`opacity` 高低也不影響 `pointer-events`）搭配 `getBoundingClientRect()`／`elementFromPoint()` 驗證版面幾何，兩者都通過即可合理確信在真實瀏覽器裡懸浮也會正常運作。

已用隔離測試伺服器驗證：全寬插入區域的座標正確橫跨區塊整個寬度；`elementFromPoint()` 在該區域內任一點都命中正確的元素；直接呼叫 `.click()` 確認各種相鄰組合下都能正確插入空白段落並聚焦；按鈕預設 `opacity` 確認為 `0.35`（常駐可見）；瀏覽器主控台無錯誤。Python 測試 65 個維持通過（純前端調整）。

**縮小緩衝間距**：使用者確認功能可用後，接著問任務 62 引入的 `margin-top: 14px` 是否為必要值——這段留白比預期多。實際量測「兩個表格零間距相鄰」這個最極端情境的真實需求：表格自己的「新增列」按鈕距離區塊方框底部邊界約有 9px 的既有緩衝（來自表格本身的 8px `padding`），插入按鈕的觸發區域向上延伸固定 14px，兩者相減，真正需要的最小 `margin-top` 只要 5px——原本設的 14px 比實際需要的多出將近 9px。改成 8px：比理論最小值多留 3px 當安全緩衝（不貼著極限值，避免字型渲染或瀏覽器縮放比例的微小差異造成邊界情況下的重疊），同時把視覺留白縮減超過四成。

### 移除額外緩衝間距，讓相鄰的非文字區塊可以真正零間距相鄰

使用者想讓兩個表格「再接近一些」，同時維持插入功能，並提出一個具體方向：把 `.block-table-row` 的 `padding` 從 `8px 0` 改成 `0`。實際測試後發現這個方向會直接跟既有機制衝突——這段 `padding` 同時扮演「表格跟自己方框邊界的內距」跟「插入按鈕安全緩衝的一部分」兩個角色，拿掉後插入按鈕的觸發區域會跟前一個表格的「新增列」按鈕重疊 5px、也跟目前這個表格自己的表頭重疊約 5.5px，等於重新製造出任務 62 修的那個問題。評估後如實回報使用者，沒有套用這個方向。

**關鍵發現：既有的區塊內部 `padding` 本身就足夠當緩衝，根本不需要額外的 `margin`**。回頭重新檢視任務 62／64 一路以來的假設——一直預設「需要額外引入 `margin-top` 才能生出緩衝空間」，但其實表格/圖片/程式碼區塊/提示框各自本來就有的內部 `padding` 已經提供了緩衝：表格與圖片是區塊自身的 8px；程式碼區塊與提示框則是區塊自身的 4px 再加上內層 wrap 元素（`.block-code-wrap`／`.block-callout`）自己額外的 `padding`，實測下來反而有 9～18px 不等的既有緩衝，比表格/圖片還寬裕。真正的問題不是「緩衝不夠、需要額外加 `margin`」，而是插入按鈕的觸發區域（`.block-insert-zone`）原本設計得太大（20px 高、大部分往上延伸），超出了既有 `padding` 能提供的範圍。只要把觸發區域縮小並置中對齊在兩個區塊的邊界上（改成 12px 高、上下各 6px），就能完全落在既有 `padding` 的範圍內，不需要任何額外的 `margin`。以隔離測試伺服器實測「兩個表格」「圖片接表格」「程式碼區塊接提示框」「提示框接圖片」四種組合，在 `margin-top: 0` 的條件下，全部組合的緩衝都是正值（2～12px 不等，無一重疊）。

**移除整個條件式間距機制**：既然不需要額外的 `margin`，任務 62 引入的「依前一個區塊型態決定要不要加緩衝間距」（`blockFollowsNonTextSibling` 輔助函式＋ `.block-row-gap-above` class）整個機制就不再需要，直接移除——這是一次淨簡化，移除的程式碼比新增的還多。這也是這次修正過程中一個值得記住的教訓：一開始選擇的解法（額外引入 `margin`）雖然「有效」，但不是「必要」的最簡方案；多留一步回頭檢視「這個問題真的沒有更省成本的解法嗎」，才發現原本的假設（緩衝不足）其實不成立，問題根源始終是觸發區域本身的尺寸與位置設計，不是緩衝空間不足。

已用隔離測試伺服器驗證：兩個表格現在完全零間距相鄰，跟一般文字接表格等情境視覺上一致，不再有任何特別的額外間距；表格/圖片/程式碼區塊/提示框兩兩相鄰的各種組合，插入按鈕的觸發區域皆確認不重疊任何既有的可互動元素或實際內容；點擊插入按鈕確認各種組合下都能正確插入空白段落並聚焦；瀏覽器主控台無錯誤。Python 測試 65 個維持通過（純前端調整）。

**縮小懸浮觸發範圍為按鈕本身**：使用者接著回饋，懸浮在整個區塊（表格本體）上就會讓插入按鈕轉為明顯，希望改成只有懸浮在按鈕自己的範圍（`.block-insert-zone`）才觸發。原本的 `opacity: 1` 規則同時掛在 `.block-row:hover` 跟 `.block-insert-zone:hover`／`:focus` 三個選擇器上——前者是任務 60 最初的設計殘留（當時按鈕本身沒有獨立的全寬觸發區域，只能靠懸浮整個區塊來顯示），後兩者是任務 63 加入全寬觸發區域後補上的。三者並存造成「懸浮區塊本體」跟「懸浮按鈕本身」都能觸發，範圍比使用者想要的大。移除 `.block-row:hover` 這條規則，只留 `.block-insert-zone:hover`／`:focus`，按鈕預設的淡化常駐顯示（`opacity: 0.35`）不受影響，純粹縮小「轉為完全不透明」的觸發範圍。

### 切換「檢視原始碼」時延續游標位置

使用者以「UX 背景、極度為使用者著想」的角度，請我腦力激盪如何改善「檢視原始碼」功能。提出的方向包括：切換前先給變化摘要（避免像這次表格合併/插入按鈕一路踩到的「切換當下發生非預期變化」）、原始碼加語法高亮、游標位置延續、跳到區塊對應原始碼位置、甚至用分割畫面取代「切換」這個概念本身。使用者選定先做「游標位置延續」：目前不論編輯焦點在哪，切換到原始碼模式一律回到文件最上面，切回區塊模式也一樣，每次切換都要重新找剛剛在哪。

**設計取捨：只求對到「同一個區塊」，不追求字元級精準**。這個決定是這個功能可行性的關鍵——如果要求游標精準對應到原始碼裡的確切字元（例如某個粗體字中間），會牽涉到跟搜尋/取代功能同樣的難題（畫面顯示文字的位置 ≠ 底層 Markdown 原始字串的位置），複雜度高出很多。退一步只求「切換後落在同一個區塊」，體感上已經解決「每次都要重新找位置」的核心困擾，複雜度卻低得多——這是那種「多想一步、看看真正需要解決的是什麼」就能大幅降低成本的情境，跟任務 65 移除不必要的 `margin` 是同一種思考方式。

**雙向映射的做法：讓既有的序列化/解析函式「順便」記一筆帳，而非另外設計一套對照機制**：
- **區塊 → 原始碼**：切換當下已經知道游標在哪個區塊（透過 `data-id` 查得到）。把 `blocksToMarkdown` 重構成 `blocksToMarkdownWithLineMap`，序列化的過程中，每個帶 `_id` 的區塊被寫出時，順手記下「這個區塊從輸出文字的第幾行開始」，最後就有一份「區塊 ID → 起始行號」的對照表；換算成字元位移後，直接把游標移過去。
- **原始碼 → 區塊**：反過來，把 `parseMarkdownToBlocks` 重構成 `parseMarkdownToBlocksWithLineMap`，解析的過程中，每個區塊被建立時，順手記下「這個區塊消耗了原始碼的第幾行到第幾行」；游標的字元位移換算成行號後，查這份對照表就知道該落在哪個區塊——找到後直接重用既有的 `focusBlockSmart`（表格/程式碼區塊/一般文字各自對應的既有聚焦邏輯），不用另外設計「怎麼把焦點移到某個區塊」這件事。

兩個方向都刻意選擇「重構既有函式、讓它們順便多回傳一份對照資訊」，而不是另外寫一套獨立的位置追蹤機制——原本的 `parseMarkdownToBlocks`／`blocksToMarkdown` 對外行為完全不變（改成呼叫新函式後只取需要的欄位），既有呼叫端不用修改，新增的能力是「附加」而非「取代」。

**實作中發現並修正的邊界 bug**：一開始把「記錄行號範圍」的程式碼放在標題／引用／圖片／段落這幾種「單行區塊」分支裡 `i += 1`（游標前進到下一行）**之前**，導致記錄下來的結束行號跟起始行號相同，變成一個零長度的範圍（例如標題被記錄成 `[0, 0)` 而不是正確的 `[0, 1)`）；用實際測試資料把每個區塊的範圍印出來比對才發現這個問題。表格/程式碼區塊/提示框這幾種「多行區塊」原本的寫法（`i` 已經在各自的多行迴圈裡完整前進後才記錄）本來就是對的，只有「單行區塊」這幾個分支需要把記錄動作挪到 `i += 1` 之後。這是一個很典型的「複製既有模式時，順序細節沒對齊」的錯誤——多行區塊跟單行區塊的程式碼結構看起來相似，但「`i` 什麼時候完成前進」這個時機點不一樣，照抄前者的順序放到後者裡就會出錯。

已用隔離測試伺服器驗證：焦點在表格/程式碼區塊/一般段落等不同型態時切到原始碼模式，游標精確落在該區塊 Markdown 的起始位置；反向操作（原始碼游標移到某個區塊對應範圍內）切回區塊模式，編輯焦點正確移到同一個區塊，透過真實的「檢視原始碼」/「切換為區塊編輯」按鈕完整走過流程；邊界情況：完全沒有聚焦時切到原始碼模式不強制定位（`offset` 為 `null`）；游標落在兩個區塊之間的空白行時切回區塊模式，正確退回前一個區塊；既有的「原始碼模式編輯後自動存檔」呼叫路徑（不傳游標位移）不受影響；瀏覽器主控台無錯誤。Python 測試 65 個維持通過（純前端功能，未變動後端）。

### 修正：真實點擊「檢視原始碼」按鈕時游標延續完全沒有作用

使用者實測後回報完全感受不到游標有跟著切換位置——這跟任務 67 驗證時看到的結果完全相反。追查後發現，問題不在游標位置的計算邏輯本身（那部分是對的），而在**讀取「目前聚焦在哪個區塊」的時機點**：

**根本原因**：真實點擊一個 `<button>` 時，瀏覽器會在 `mousedown` 階段就把焦點移到這顆按鈕本身，這件事發生在 `click` 事件（我們的切換邏輯掛在這個事件上）觸發**之前**。等到我們的程式碼執行、呼叫 `document.activeElement` 想知道「使用者剛剛在編輯哪個區塊」時，讀到的其實已經是「這顆按鈕自己」——使用者原本聚焦的區塊資訊，在我們的程式碼有機會讀取它之前，就已經被瀏覽器的原生行為覆蓋掉了。`getFocusedBlockId()` 因此永遠回傳 `null`，整個游標延續功能形同沒作用；使用者體感上就是「游標永遠跳到原始碼最後面」（因為 `textarea.value` 被重新賦值時，瀏覽器原生行為是把游標移到文字結尾，這正好可以解釋「感受不到延續」的具體樣貌）。

**這個 bug 為什麼任務 67 的測試沒抓到**：驗證時是呼叫 `document.getElementById('btn-toggle-source').click()`（程式化觸發 click 事件），這確實會執行到跟真實點擊一樣的 `toggleViewMode`／`setViewMode` 程式碼路徑，但**不會**複製瀏覽器對真實滑鼠事件才有的「`mousedown` 自動把焦點移到按鈕」這個原生副作用——所以程式化測試當下，`document.activeElement` 還停留在使用者原本聚焦的區塊，看起來一切正常，實際上到了真人使用者點滑鼠時就會失效。這是「合成事件能驗證自己註冊的處理邏輯，但不會複製瀏覽器對真實輸入才有的原生副作用」這個原則的一次具體案例——這個專案先前已經在別的地方踩過類似的坑（`:hover` 偽類無法被合成事件觸發），這次是同一類問題的不同變形（這次是「焦點」而非「懸浮」），提醒自己這一類「瀏覽器原生副作用」的驗證，最終都得靠真實輸入事件才能徹底放心。

**修正：從「即時查詢」改成「持續追蹤」**。既然讀取的時機點本身就是問題所在（讀的時候已經太晚），解法就不能是「換個時間點再讀一次」，而是從一開始就不要依賴「點擊當下查詢」這個模式——改成在焦點變化的當下就記錄下來。新增模組變數 `lastFocusedBlockId`，在初始化時註冊一個全域 `focusin` 監聽器，只要焦點移入編輯區內某個區塊，就即時更新這個變數；`getFocusedBlockId()` 不再即時查詢 `document.activeElement`，直接回傳這個持續追蹤的值。這樣即使使用者點擊按鈕的當下焦點已經被瀏覽器搶走，我們仍然記得「搶走之前，游標在哪個區塊」——這個模式（用一個持續更新的變數取代「事後查詢瞬時狀態」）比找出「精確的讀取時機點」更穩固，不會因為未來又冒出另一個「某個操作也會搶走焦點」的情境而重蹈覆轍。

已用隔離測試伺服器驗證：改用 `computer` 工具的真實滑鼠點擊（而非 `.click()`）重現原始 bug（確認修正前游標確實落在文件最後面）；套用修正後用同樣的真實點擊路徑重新驗證兩個方向皆正確；透過監聽 `focusin` 事件並記錄時間戳，確認整個真實點擊流程中的焦點轉移順序符合預期；瀏覽器主控台無錯誤。Python 測試 65 個維持通過（純前端修正，未變動後端）。

### 捲動筆記內容時，「檢視原始碼」/「複製原始碼」按鈕維持可見與可操作

使用者提出：這兩顆按鈕原本跟標題放在同一個列，只在文件最上方才看得到，筆記內容一長、往下捲動就會被捲出畫面外，需要捲回頂端才能操作。目標是讓這兩顆按鈕在捲動時維持可見、可點擊。

**第一次嘗試與診斷**：直接在既有的按鈕容器（`#editor-toolbar-actions`，當時是 `#editor-toolbar` 內、跟標題並排的一個行內元素）加上 `position: sticky`，結果只在最前面約 98px 的捲動範圍內有效，捲過這個範圍後按鈕整個隨內容一起消失。

**根本原因**：`position: sticky` 元素能維持「黏住」的範圍，受限於它自己最近的 containing block（通常是直接父層）在畫面上還剩多少可視高度——一旦這個父層整個捲出畫面，裡面的 `sticky` 子元素就沒有母層範圍可以繼續黏著了。原本的父層 `#editor-toolbar` 只是一個跟標題一樣高的淺列（約 98px 高），撐不起整篇筆記的捲動範圍。用三個隔離探測元素（分別插入 `#editor-pane`／`#editor-toolbar`／`#editor-content` 三種不同深度的直接子層）交叉驗證後確認：只有父層本身夠高（涵蓋整個想維持黏住的捲動範圍）才會一路有效，跟 `sticky` 屬性本身無關。

**修正**：把 `#editor-toolbar-actions` 從 `#editor-toolbar` 內部搬出來，改成跟 `#editor-toolbar` 同層、都是 `#editor-content`（涵蓋整篇筆記高度）的直接子元素。但這樣一來，若單純用 `sticky` 定位，會佔用自己的版面高度、把下面的內容往下推開一段空白——改用「零高度覆蓋層」手法：容器本身設定 `height: 0; overflow: visible; pointer-events: none;`（不佔版面高度、不吃滑鼠事件），內部按鈕各自設定 `pointer-events: auto;`（讓按鈕仍可正常點擊），達成「按鈕視覺上浮動在標題右上角，但不影響版面排版、也不擋住底下內容操作」的效果。

**副作用與後續修正**：這個浮動覆蓋層手法讓標題所在的那一行不再有任何機制預留空間給右上角的按鈕——如果標題文字夠長，會直接延伸到按鈕浮動區域下面、被按鈕的白色背景視覺上蓋住一部分。量測按鈕列實際佔用寬度（含到容器右邊界的距離）為 238px，幫 `#note-title` 加上 `padding-right: 256px`（238px + 緩衝），讓標題文字的可用寬度提前收窄、在碰到按鈕保留區之前就換行。

已用隔離測試伺服器驗證：60 段落長筆記，捲動前後（`scrollTop: 0` 與 `3000`）按鈕 `top` 值不變，證實整篇筆記範圍內都維持黏住；捲動狀態下按鈕仍可正常點擊；標題改為刻意很長的文字後換行、不再跟按鈕重疊；改回一般長度標題後沒有因 `padding-right` 產生不合理的視覺空白（標題本身無背景色，`padding-right` 只限制文字可用寬度，不會露出留白）。瀏覽器主控台無錯誤，Python 測試 65 個維持通過（純前端 HTML 結構調整＋CSS，未變動任何 JS 邏輯或後端）。

### 修正：復原／取消復原後切換至原始碼模式，游標延續完全失效

使用者拿一篇真實筆記回報：編輯焦點明明在「1. 折現率通」這個標題，切換到原始碼模式後，游標卻落到文件接近結尾的位置，並懷疑是不是新加的浮動按鈕排版太擠、點擊時不小心點到別的地方。

**排除的假說**：先複製這篇真實筆記到隔離測試環境重建情境，直接用真實滑鼠點擊標題、再點擊「檢視原始碼」——這條最單純的路徑本身運作正常，游標正確落在標題對應位置；比對按鈕排版與間距，視覺上也沒有明顯擁擠。這說明問題不在按鈕排版，而在使用者回報前實際做過的「其他操作」。

**根本原因**：任務 67 設計的游標延續機制，依賴一個持續追蹤「目前編輯焦點在哪個區塊」的模組變數 `lastFocusedBlockId`（由 `focusin` 事件更新），並在切換到原始碼模式時，用這個區塊的識別碼去查詢序列化時建立的 `lineMap`。但區塊的內部識別碼（`_id`）並非永久不變——`assignIds()` 每次被呼叫都會幫**全部**區塊重新配發一組全新的識別碼（配發來源是模組層級持續遞增的 `idCounter`，不會重複使用舊值）。`load()`（開新筆記）跟 `loadFromMarkdownSource()`（原始碼切回區塊模式）這兩個會呼叫 `assignIds` 的地方，各自都有妥善處理：前者會重置 `lastFocusedBlockId`，後者之後一定會呼叫 `focusBlockSmart` 重新對焦——但 `restoreSnapshot()`（`Ctrl+Z` 復原／`Ctrl+Shift+Z`／`Ctrl+Y` 取消復原共用的還原函式）呼叫 `assignIds` 重新配發識別碼、呼叫 `render()` 整個重建 DOM 節點，卻完全沒有在還原後把焦點移回任何地方。實測重現：點擊某區塊、輸入一個字元、按 `Ctrl+Z`——復原後 `document.activeElement` 變成 `<body>`（舊的 DOM 節點已被整個換掉，原生焦點因此遺失），而 `lastFocusedBlockId` 仍停留在復原前的識別碼；由於 `assignIds` 已經讓所有區塊（即使內容和位置都沒變）換發新識別碼，這個舊識別碼在新的 `lineMap` 裡已經不存在，判定為「沒有可用的定位資訊」。此時 `app.js` 原本的實作在 `offset` 為 `null` 時完全不設定游標位置，任由瀏覽器「重新賦值 `.value` 後游標跑到結尾」的原生行為接手（這個瀏覽器行為在任務 68 已經驗證過一次）——兩者疊加，正是使用者體感到的「復原之後切原始碼，游標跳到最後面」。

**修正**：
1. `editor.js` 新增 `findBlockIndexPath`／`getBlockAtIndexPath`，用「區塊在清單中的位置路徑」（而非識別碼）作為復原前後的對應依據——因為復原/取消復原兩個相鄰的歷史快照之間，區塊的內容與位置通常維持不變，只有識別碼本身會变。`restoreSnapshot` 在呼叫 `assignIds` 之前，先用舊的 `lastFocusedBlockId` 在舊的 `blocks` 找出位置路徑；重新配發識別碼之後，再用同一條路徑到新的 `blocks` 取出對應區塊，把它目前的識別碼寫回 `lastFocusedBlockId`。這樣即使原生焦點已經遺失，內部追蹤的「目前對應哪個區塊」仍然正確，也不需要讓復原動作額外搶回畫面上的游標焦點（避免引入使用者沒有要求的新行為）。
2. `app.js` 的 `setViewMode('source')`：不再只在 `offset` 有值時才設定選取範圍，一律呼叫 `setSelectionRange`，`offset` 為 `null` 時明確帶入 `0`（原始碼開頭），不再依賴瀏覽器未明確定義、對使用者來說是意外行為的預設值（跳到結尾）。

已用隔離測試伺服器驗證：重現「點擊標題→輸入字元→`Ctrl+Z`→切換至原始碼模式」，確認游標正確對應回原本聚焦的標題；驗證「完全沒有點擊過任何區塊就切換至原始碼模式」，確認游標明確落在開頭（`selectionStart === 0`）；瀏覽器主控台無錯誤，Python 測試 65 個維持通過（純前端修正，未變動後端）。

### 修正：切換至原始碼模式時，游標數值正確但畫面沒有捲動過去

**根本原因**：`editor.js` 有兩個「在旁邊插入空區塊」的函式，判斷新區塊型態的邏輯不一致：
- `insertSiblingAfter`（Enter 在區塊尾端時用）：正確地依 `CONTINUABLE_TYPES`（`list_item`／`ordered_item`／`checklist_item`）判斷——目前區塊是清單類型就延續同型態，否則預設 `paragraph`。
- `insertEmptySiblingBefore`（Enter 在區塊開頭時用）：新區塊型態寫死成 `'list_item'`，完全不看目前區塊實際型態。

游標在清單項目開頭按 Enter 時，因為寫死的值剛好也是 `list_item`，長期掩蓋了這個問題；只要目前區塊是段落、標題等任何其他型態，就會被誤植入清單項目。

**修正**：`insertEmptySiblingBefore` 改用跟 `insertSiblingAfter` 一致的判斷邏輯（`continued ? block.type : 'paragraph'`）。

已驗證：`123.md` 的 `67890` 開頭按 Enter，新區塊正確為 `paragraph`，不再冒出孤立的「•」，存檔後只有一般空白行；游標在清單項目開頭按 Enter 仍正確延續同型態；標題、待辦清單開頭按 Enter 分別正確插入空白段落、延續待辦清單型態。Python 測試 65 個維持通過（純前端修正，未變動後端）。

### 新增分隔線（`---`）區塊型態

使用者詢問 Markdown 的 `---` 是否有特殊意義。標準 Markdown 裡 `---` 有兩種語意：獨立成行時是「分隔線（thematic break）」，緊接在一行文字下面（中間沒有空行）則是「Setext 標題底線」（會把上面那行變成 H2）。這個專案目前把 `---` 當成一般文字段落處理，兩種語意都沒有實作。使用者請我先評估調整範圍，再照建議實作。

**評估基準**：以既有的 `image` 區塊作為參考——同樣是「無文字內容、只有視覺呈現」的區塊型態，插入按鈕、刪除按鈕、`NON_TEXT_TYPES` 參與規則都可以直接沿用同一套模式，不需要另外設計。

**兩個設計決定**（實作前先跟使用者確認）：
1. **不實作 Setext 標題底線語意**——`---` 不論前面是否緊接文字，一律當分隔線處理。理由：這個專案的標題本來就只支援 `#` 這種 ATX 寫法，如果 `---` 有時候變分隔線、有時候把上一行吃掉變成標題，行為會很難預測；代價是極少數用 Setext 語法寫的舊內容，`---` 會被誤判成分隔線而非標題，評估這種寫法很少見，可以接受。
2. **hr 的解析必須是單行、不貪心**（比照 `image`／`quote`，而非 `table` 的多行迴圈式吃法）——避免重蹈先前「相鄰表格合併」那個 bug 的覆轍（如果 hr 解析時也用 while 迴圈貪心吃掉後續所有 `---` 行，兩個獨立的分隔線就會被誤合併成一個）。

**實作**：前後端各自新增 `_HR_RE`／`HR_RE`（`^ {0,3}(-{3,}|\*{3,}|_{3,})\s*$`，允許 `-`／`*`／`_` 三種字元、3 個以上）；解析與序列化邏輯的位置、寫法都直接比照 `image` 分支；`editor.js` 新增 `renderHrBlock`（結構比照 `renderImageBlock`）、`NON_TEXT_TYPES` 加入 `'hr'`、`FORMAT_OPTIONS` 加入「分隔線」選項（沿用格式選單既有的 generic 轉換分支）；CSS 沿用 `.block-image-*` 的間距與懸浮顯示刪除按鈕手法。

**刻意不處理的項目**：`focusBlockSmart` 沒有為 `hr` 加特殊處理，維持跟 `image`／`callout` 現況一致的「方向鍵移動過去但不會真的聚焦任何東西」小落差——hr 完全沒有文字內容，沒有明顯「正確」的聚焦目標，貿然加特殊邏輯只是不對稱地解決其中一種區塊型態，不是真正修正這個既有、範圍更廣的小落差，留待未來有需要時再一併處理。

已驗證：獨立一行的 `---` 正確解析並渲染成分隔線；切到原始碼再切回來（完整往返）不會消失、不會被誤判回段落；連續兩個 `---` 正確解析成兩個獨立區塊、不合併；表格分隔列（`| --- | --- |`）不受影響；插入按鈕、刪除按鈕、格式選單轉換三個互動都正確運作；`hr` 是最後一個區塊時仍會自動提供可編輯的空白段落銜接。新增 6 個 Python 測試，測試總數從 65 增加到 71 個，全數通過（純前端＋Python 後端功能，屬全新區塊型態，對既有筆記的相容性影響：既有筆記裡的 `---` 原本被當純文字段落，改完後會變成分隔線，是預期中的行為升級）。

### 標題（H1/H2/H3）上方加間距，取代嘗試保留空白段落

承接前面「空白段落無法在切原始碼往返後保留」的討論（見上方任務 76 相關記錄），使用者提出另一個方向：不試圖保留人為插入的空白段落當作留白手段，改成針對標題本身，只要上面還有其他內容，就加一點 `margin-top`，用渲染層級的視覺留白取代「插入一個空白段落」這個內容層級的手段。這個方向比較乾淨：純粹是呈現層面的事，不用跟 Markdown 的空白行語意搏鬥，也完全不受切原始碼往返影響（不寫入任何額外字元，`.md` 檔案內容不變）。

**技術限制與因應**：每個區塊外面都包了一層沒有 class 的 wrapper div（`renderList` 把 `renderBlock` 的回傳值直接 append 進共用的 `wrapper`），CSS 相鄰選擇器不容易直接命中同層的另一個 `.block-row`。因此「這個標題上面是否還有其他內容」這個判斷改在 JS 端做——`renderList` 的 `forEach` 本來就知道目前是第幾個項目，直接判斷 `index > 0` 即可，不需要用 CSS 選擇器去猜測 DOM 結構。

**實作**：`renderList` 呼叫 `renderBlock` 時多傳一個 `hasPrecedingSibling` 參數；`renderBlock` 在 `block.type === 'heading' && hasPrecedingSibling && block.level <= 3` 時才幫 `row` 加上 `block-row-heading-spaced` class 並記錄 `data-heading-level`——文件裡第一個區塊（上面沒有東西可以區隔）跟 H4 以上的標題（範圍之外）都不加，避免文件開頭多出不必要的留白、也避免無意義的 class 出現在不受影響的層級上。`style.css` 用 `.block-row-heading-spaced[data-heading-level="N"]` 三條規則分別設定各層級的 `margin-top`。

**數值調整過程**：第一版依字級大小比例抓 32px／26px／20px（H1/H2/H3）；使用者實測後嫌 H2 太大，先改成 12px（此時 H2 反而比 H3 的 20px 還小，層級關係顛倒，已跟使用者提醒）、再調整為 16px；H3 也從 20px 改成 8px。最終定案：**H1 32px／H2 16px／H3 8px**，層級遞減，符合「標題層級越大、跟前文的區隔越明顯」的直覺。

已驗證：文件第一個區塊是標題時沒有多餘留白；H1/H2/H3 在有前文的情況下正確套用對應間距；H4 標題不受影響（不加 class、無視覺變化）；一般段落與其他區塊型態不受影響。Python 測試 71 個維持通過（純前端 CSS／JS 呈現調整，未變動任何解析或序列化邏輯，`.md` 檔案內容不受影響）。

### 補上分隔線的即時輸入轉換

使用者實測分隔線功能後回報：直接在區塊裡打 `---`，畫面不會就地變成分隔線。排查後發現這是一個真正的落差，不是刻意的設計範圍——這個編輯器本來就有一個既有機制：`handleInput` 裡偵測到使用者打出 `# `（到 `###### `）會立刻把目前區塊即時轉成標題，不需要按 Enter 或用格式選單。任務 77 實作分隔線時，只處理了「解析既有 Markdown 內容」這條路徑（開啟筆記、切原始碼再切回來），沒有比照標題既有的即時輸入轉換慣例，屬於遺漏。

**修正**：`handleInput` 在既有的標題判斷之後，新增 `/^(-{3,}|\*{3,}|_{3,})$/.test(raw.trim())` 判斷，只要目前區塊的純文字內容剛好等於 3 個以上同一種字元，就立刻轉成 `hr`；轉換後呼叫既有的 `ensureFollowingParagraph(list, idx)`（跟「格式選單轉換為圖片」共用的既有工具函式）確保分隔線後面一定有可編輯的段落並把焦點移過去——分隔線本身沒有文字內容，直接留在原地會讓游標憑空消失，這樣使用者打完 `---` 可以無縫接著打字。

已驗證：逐字輸入 `-`／`-`／`-`（每個字元都是真實的 `input` 事件，非一次貼上），打完第三個字元的當下立即轉成分隔線、焦點正確移到新的可編輯段落；`***`／`___` 同樣正確觸發；只打兩個字元不會誤觸發；標題的即時轉換不受影響。Python 測試 71 個維持通過（純前端功能，未變動解析/序列化邏輯）。

## Risks / Trade-offs

- [Python 3.8 已停止官方安全更新] → 僅作為本機離線工具使用，不對外部網路開放服務，降低此風險的實際影響；於文件中註明此限制。
- [第三方套件版本可能於後續釋出中放棄 Win7/舊版 wheel 支援] → 將相依套件數量降到最低（僅 Flask 及其核心相依），並於專案文件中明確釘選（pin）已驗證可在 Win7 上運作的版本號。
- [自訂大綱 ⇄ Markdown 序列化規則覆蓋語法有限] → 明確定義並文件化支援的區塊型態（標題/清單/段落），非支援語法以純文字段落保留，避免使用者資料遺失。
- [路徑安全檢查若實作不慎可能被跳脫] → 統一透過單一共用的路徑正規化與範圍檢查函式處理所有檔案系統 API，不允許個別端點自行組合路徑。
- [中文檔名/內容在 Win7 舊版檔案系統下的編碼疑慮] → 一律以 Python 3 的 Unicode 路徑 API 與 UTF-8 讀寫檔案內容，不依賴系統 ANSI 預設編碼。
- [樹狀拖曳搬移使用 HTML5 原生拖放 API，觸控裝置（無滑鼠）不支援拖放手勢] → 右鍵選單的「搬移」（手動輸入目標路徑）維持保留作為替代操作方式，觸控裝置使用者仍可完成搬移。
- [前端（JS）與後端（Python）各自維護一份 Markdown 解析/序列化邏輯，可能因修改不同步而產生行為落差] → 兩者的規則刻意保持極簡（僅標題/清單/段落三種型態），並在測試中涵蓋相同案例；未來若擴充語法支援，需同時更新 `noteapp/markdown_blocks.py` 與 `static/js/markdown.js`。
- [行內字級以內嵌 HTML `<span>` 存檔，不是標準 Markdown 語法] → 大多數 Markdown 檢視器都支援內嵌 HTML 直接渲染，相容性風險低；但若使用者拿去不支援內嵌 HTML 的檢視器開啟，會直接看到原始的 `<span>` 標籤文字，已於 README 的已知限制中註明。

## Migration Plan

全新專案，無既有系統或資料需要遷移。初次部署步驟：
1. 在目標機器安裝 Python 3.8（Win7 相容版本）。
2. 安裝已釘選版本的相依套件（`pip install -r requirements.txt`）。
3. 設定筆記根目錄（環境變數或設定檔），或使用預設的 `notes/` 資料夾。
4. 啟動本機伺服器，於瀏覽器開啟 `http://127.0.0.1:<port>` 使用。

無需回滾（rollback）機制：本工具不修改既有系統，移除即完成復原。
